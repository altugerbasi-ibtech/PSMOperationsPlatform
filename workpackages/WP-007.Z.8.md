## Objective

Extend the standard operational validation toolkit with comprehensive,
read-only validation of Execution History persistence, projection integrity,
query contracts, retention policy, cleanup safety, failure isolation,
Monitoring boundaries, and History-versus-Audit separation. Repository
capability and live database readiness remain distinct.

## Business and Product Value

Execution History is operationally useful only when its durable schema,
projection, query, and retention behavior agree with the approved contracts.
This package gives operators deterministic preflight evidence without reading
business payloads, deleting history, changing SQL, or treating repository tests
as production database proof.

Repository facts at specification approval time:

- `ExecutionHistorySchemaVersion.Value` is 1 and is not an assembly version;
- migration `20260729191745_WP0088ExecutionHistory` creates six tables in the
  `history` schema: run, step, attempt, transition, artifact and policy;
- offset paging defaults to 50 and permits at most 200;
- ordering is `CompletedAt` descending then `ExecutionRunId`, with documented
  child ordering;
- retention version 1 is 180 days for run aggregate data, 90 days for
  transitions, 90 days for failed projection diagnostics, default batch 500,
  and policy validation permits 1–5000;
- cutoff calculation uses `TimeProvider`; the cleanup service performs bounded
  deletes and has no production scheduler;
- no retention dry-run contract/method exists;
- WP-008.8 defines no new History metric; existing Monitoring remains
  independent and no exporter is configured;
- a pre-existing `audit.AuditLog` capability exists outside WP-008.8. Its mere
  existence is not a History boundary violation. Validation must prove that
  WP-008.8 migration/history schema did not introduce or depend on Audit;
- History has no raw JSON event table, EAV model, outbox, broker, event source,
  monitoring-history table, or automatic migration behavior.

The validator must report deviations from these authorities, not invent new
rules or silently implement missing dry-run/monitoring behavior.

## Architectural Boundaries

- Extend WP-007.Z.3; no second validation framework or configuration format.
- Observe existing C#/EF/SQL contracts. PowerShell must not implement history
  projection, idempotency, paging, retention, or health algorithms.
- Reuse WP-009 schema/permission validation and WP-007.Z.5 connection safety;
  narrowly scoped read-only history catalog queries may add evidence not
  exposed by those artifacts.
- Runtime, Dispatcher, Execution State, Monitoring, History, and Audit
  ownership/dependency direction remains frozen.
- History is a terminal durable projection and can lag. It does not reconstruct
  or control active State. Monitoring is current/non-durable. Audit is separate.
- Retention validation is metadata/source/test observation. The command never
  calls `DeleteExpiredAsync`, issues DELETE, or schedules cleanup.
- No ADR/Architecture Exception is expected. Any requirement for schema,
  runtime, feature, Audit, scheduler, exporter, or destructive test changes is
  an architecture conflict and stops implementation.

## Validation Result Contract

Every result uses the WP-007.Z.3 fields: `CheckId`, `Category`, `Name`,
`Description`, `Target`, `Status`, `Severity`, `StartedAt`, `CompletedAt`,
`DurationMilliseconds`, `Expected`, `Actual`, `Message`, `Recommendation`,
`Evidence`, `ExceptionType`, and `ExceptionMessage`.

Statuses are `PASS`, `WARNING`, `FAIL`, `SKIPPED`, `NOT_APPLICABLE`;
severities are `INFO`, `LOW`, `MEDIUM`, `HIGH`, `CRITICAL`. Stable
target-prefixed CheckIds use deterministic ordinal ordering. Duplicate IDs
fail assertion. Common aggregation owns target/category/overall status.

## Functional Requirements and Validation Categories

### 1. History Configuration

Validate the HistoryValidation object, enabled gates, exact schema/profile,
batch 1–5000 and exact profile expectation, unsupported dry-run false, one
enabled Operations database target, selector, no conflicts and no secrets/SQL
Authentication. Fail before SQL contact where appropriate.

### 2. SQL Connectivity

Reuse WP-007.Z.5 DNS/TCP/open/endpoint/Windows Authentication/Kerberos/
encryption/database ONLINE/timeout/disposal results for only the Operations
database. Require Windows Authentication, encrypted connection and no fallback.
Never create or modify objects.

### 3. History Schema Version

Observe `ExecutionHistorySchemaVersion.Value=1`, configured version, migration
manifest and database migration metadata. Require
`20260729191745_WP0088ExecutionHistory`; fail missing or unsupported future
schema. Do not use assembly/product version as schema authority.

### 4. History Tables

Reuse WP-009 schema evidence and read-only catalog metadata for the six
`history` tables. Validate schema, PK/FK, required columns, max lengths,
`datetime2(3)`, nullability and delete behaviors against EF/migration authority.
Detect arbitrary JSON/EAV/event-source/monitoring-history tables within the
`history` boundary. Do not flag the pre-existing separate `audit.AuditLog` as
WP-008.8 leakage; instead prove the WP-008.8 migration created no Audit table.

### 5. Indexes and Constraints

Validate authoritative EF/migration unique keys and lookup/filter/order
indexes: run ID; run/step; run/step/attempt; transition logical sequence;
artifact logical key; policy run/step; completed date and approved run filters.
Validate named critical check constraints. Detect missing/duplicate/conflicting
metadata and unindexed approved paths without changing indexes or inventing
thresholds.

### 6. History Projection Model

Observe the existing projector/contracts/tests for run, step, attempt,
transition, artifact and policy/plugin/strategy provenance; Completed/Partial;
bounded codes; and exclusion of raw exception, artifact body, command output,
credentials, connection strings, paths and secret URLs. Use repository-only
fixtures/fakes; no Collector workload or new mapping.

### 7. Idempotency

Validate writer Duplicate no-op, deterministic handling, and database logical
unique constraints for all aggregate elements. Exactly-once is not claimed.
Live duplicate execution is `NOT_APPLICABLE` unless separately authorized
synthetic non-production data exists; this package supplies none and performs
no write.

### 8. Partial History

Validate Partial status, `HistoryFactsIncomplete`-style safe reason,
preservation of known terminal outcome, no fabricated intermediate facts or
unknown-as-zero substitution, queryability, and distinction from Failed.
Never alter rows.

### 9. State Transition History

Validate positive deterministic sequence, ordering, bounded states/event/reason,
explicit typed mapping, safe invalid/out-of-order classification, and no JSON
fallback/replay/event sourcing. Confirm State remains active authority and
History is diagnostic only.

### 10. Artifact Metadata History

Validate approved bounded metadata, stable IDs, schema version, nonnegative
counts/sizes, logical uniqueness, and absence of content, bodies, local paths,
secret URLs, credentials and arbitrary metadata. Do not read/export payloads.

### 11. Policy and Plugin Provenance

Validate timeout, retry, throttling, parallel and batching codes/versions and
values; plugin/strategy/SDK/Runtime/plan/state/event/history/artifact schema
provenance. Treat records as immutable execution facts, never mutable policy or
secret configuration.

### 12. Query Contract

Observe exact run and child reads plus bounded date-range/ManagedServerId/
strategy/plugin/outcome/failure/reason filters. Validate both date bounds,
`AsNoTracking`, cancellation, deterministic ordering/null behavior, bounded
projection/includes, no `IQueryable` escape, N+1 avoidance where tests/source
prove it, and no dynamic query language. Live probes use metadata or bounded
TOP/page queries only; never unbounded production reads or raw rows in reports.

### 13. Pagination

Validate default 50, maximum 200, page >=1, page size 1–200, stable
`CompletedAt DESC` then `ExecutionRunId`, child ordering, TotalCount and
HasNextPage behavior. Use code authority; do not invent paging values.

### 14. Retention Policy

Validate `ExecutionHistoryRetentionPolicy.Version1`: run aggregate 180 days,
transitions 90, failed diagnostics 90, batch 500; all positive; TimeProvider
cutoffs; profile consistency; and exclusion of active State, Audit and
Monitoring. Do not create a second policy.

### 15. Retention Cleanup Safety

Observe the existing cleanup contract/source/tests for stable cutoff, batch
1–5000/default 500, child-before-parent removal, referential integrity,
cancellation, idempotent rerun, committed counts, no active State, bounded
transaction, and no target/external call. Confirm no scheduler/SQL Agent/
Scheduled Task. Do not invoke `DeleteExpiredAsync` or issue mutations.

### 16. Retention Dry Run

The repository has no dry-run API. Return `NOT_APPLICABLE` with a stable reason
and recommendation; require configuration false. Do not invent a planner,
candidate query/output or deletion simulation.

### 17. Retention Query Performance Readiness

Validate sargable cutoff/date predicates, approved indexes, bounded `Take`,
stable order and child-first design from repository evidence. Without
authorized live SQL plans, report live query-plan/lock/throughput evidence as
`NOT_APPLICABLE` or `WARNING`. Do not enable statistics, clear caches, alter
indexes or claim production performance.

### 18. History Failure Isolation

Observe tests/contracts proving writer/query/retention failure does not alter
Runtime/Dispatcher results, State, Plan, ExecutionContext, retry or
cancellation, and does not break Monitoring. Validate SQL exception
sanitization. No live failure injection.

### 19. Monitoring Integration

WP-008.8 requires no new History metric. Validate that History does not add a
parallel metric catalog, persistence or exporter and that existing Monitoring
remains independent. If safe history projection/duplicate/retention metrics are
not implemented, mark them `NOT_APPLICABLE`; do not invent them. If observed,
validate code-owned bounded tags and prohibit ExecutionRunId,
ManagedServerId, exception text and other high-cardinality dimensions.

### 20. History versus Audit

Validate documented meanings and dependency/schema boundaries: History answers
what executed; Audit answers who changed configuration; Windows identity alone
does not turn provenance into Audit; logs are not authoritative Audit;
Monitoring is not History; History is not active State. Confirm the WP-008.8
migration/history namespace introduced no Audit table/service/event. Do not
claim the repository contains no pre-existing Audit capability.

### 21. History and Retention Readiness

Aggregate mandatory blockers/warnings/information and distinguish repository
ready/schema deployed, repository ready/schema absent, schema mismatch, query,
retention, cleanup, permission defects, unmeasured live performance, absent dry
run and no authorized destructive test. Output PASS/WARNING/FAIL, but never
production readiness without actual approved SQL evidence.

## Domain and Application Contracts

Validation introduces no production domain/application type. It reads existing
immutable projection/query/page/retention/result contracts and converts only
sanitized observations into common validation results. No EF entity,
`DbContext`, `IQueryable`, configuration, service locator, raw row/event/
artifact, mutable collection or secret crosses the result boundary.

## Persistence and Migration Impact

No persistence/model/schema/index/constraint or EF migration change is
authorized. Existing migration and snapshot are read-only authorities. Do not
regenerate or apply migrations. Any schema mismatch produces a finding and is
remediated only through separately approved forward work/deployment.

## SQL Query and Safety Contract

All added query text must pass the existing WP-007.Z.5 safety guard and an
automated source scan. Allowed: bounded `SELECT`, catalog/metadata functions,
`HAS_PERMS_BY_NAME`, `SERVERPROPERTY`, `DATABASEPROPERTYEX`, and existing
read-only WP-009 scripts. Parameterize values/identifiers through approved
bounded adapters; avoid dynamic SQL.

Prohibit `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE`, `ALTER`, `DROP`,
`TRUNCATE`, `GRANT`, `DENY`, `REVOKE`, `RECONFIGURE`, migration application,
retention execution, cleanup job creation, DBCC cache-clearing, `KILL`, service
or scheduler commands. Static tests scan SQL catalog and PowerShell AST/text.

## Failure Classification

Use stable validation CheckIds/categories and existing History reason/failure
authority. Configuration/selector errors exit 3 before SQL. Top-level
unexpected failure exits 4. Isolate SQL, schema, table, index, projection,
idempotency, partial, transition, artifact, provenance, query, pagination,
retention, dry-run, performance, isolation, Monitoring and boundary findings.
Never relabel History failure as target/plugin/Runtime/authentication success or
failure. Unavailable destructive/live evidence is not fabricated.

## Security and Read-Only Requirements

- Current process/approved service identity, Windows Integrated Security,
  encryption and hostname/certificate validation only.
- No username/password/token/connection string/SQL login/credential object,
  authentication fallback, trust bypass or secret field.
- Connect only to the configured Operations database and dispose every SQL

- Read only catalogs, bounded aggregate counts and safe metadata. Do not read,
  persist or report raw history rows, IDs, private plugin values, artifact

- No deletion, cleanup invocation, migration, permission/schema/index change,
  target/Collector/Runtime operation, scheduler, exporter or remote mutation.
- Sanitize exception/server/connection/identity details through common rules.

## Determinism and Immutability

Use ordinal stable identifiers/order, code-owned schema/profile/version values,
configuration hash and common status rules. Repository tests use fixed
TimeProvider and synthetic bounded fixtures. Same normalized evidence yields
the same checks, cutoffs, status, recommendations and exit. Do not use random
logical values, current culture, reflection order, dictionary order, hash code,
unbounded current time, live row content or plan text as logical identity.
Validation does not mutate child evidence, projections, entities or state.

## Cancellation and Resource Bounds

SQL connections/commands/readers use explicit bounded timeouts and deterministic
disposal. Queries use bounded metadata/aggregate/page limits. Repository async
contracts propagate cancellation. Validator cancellation closes resources and
does not continue dependent SQL checks, call cleanup, trigger Runtime
cancellation or fabricate a result. No automatic retry hides timeout/failure.
