## Objective

Produce a deterministic, versioned SQL Server deployment package from the
existing EF Core migrations without changing runtime behavior or allowing
automatic migration.

## Business and Product Value

DBAs require a reviewable, hash-verifiable release artifact that can be
approved and executed independently of the application identity. Packaging the
existing migration chain makes schema deployment reproducible while preserving
least privilege and operational change control.

## Existing Repository Context

The authoritative inputs are `OperationsDbContext`, its model snapshot, the 17
existing migrations, `PSMOperationsDatabaseSchemaExpectation.json`,
Engineering Standards, Architecture Freeze v1.0, Development Process Freeze
v1.0, database validation tooling, and the WP-007.Z golden baseline.

## Architectural Boundaries

This package adds build/release tooling only. The application never calls
`Database.Migrate()` or `EnsureCreated()`. EF migrations remain source
artifacts; generated SQL is a release artifact for separate DBA execution.
No project reference, runtime registration, entity, configuration, migration,
snapshot, Collector responsibility, or security boundary changes.

## In Scope

- `Release/Database` generated-output location and usage documentation.
- PowerShell build and release entry points.
- Idempotent `dotnet ef migrations script` generation.
- Pending-model, native-command, empty-output, source-state, checksum, and
  manifest validation.
- GitHub Actions build and artifact publication.
- Deterministic offline tests and release documentation.
- Required Architecture, Implementation, and Repository reviews.

## Out of Scope

Database connection, SQL execution, migration application, rollback SQL,
automatic migration, schema changes, migration creation, runtime changes,
deployment, credentials, infrastructure modification, WP-007.Z execution, and
production certification are prohibited.

## Functional Requirements

1. The build entry point accepts an explicit version matching
   `^[0-9]+\.[0-9]+\.[0-9]+(?:-[0-9A-Za-z.-]+)?$`.
2. Output names are `PSMOperations-v{Version}.sql`,
   `PSMOperations-v{Version}.sql.sha256`, and
   `PSMOperations-v{Version}.manifest.json`.
3. The builder restores and builds Release, then executes
   `dotnet ef migrations has-pending-model-changes`.
4. Any pending model change or failed native command stops packaging.
5. SQL generation uses `dotnet ef migrations script --idempotent`.
6. Empty or whitespace-only SQL stops packaging.
7. SQL is normalized to UTF-8 without BOM and CRLF with one terminal newline.
8. SHA256 is uppercase hexadecimal and the checksum file uses the generated
   SQL filename rather than an absolute path.
9. The manifest is ordered deterministic JSON with no generation timestamp,
   machine name, user name, local path, or secret.
10. The manifest records version, source commit, SQL filename, checksum
    filename, SHA256, exact ordered migrations, and latest migration.
11. Dirty source state fails packaging so the source commit is reproducible.
12. CI publishes only the three release-package files as one artifact.

## Domain and Application Contracts

No Domain or Application contract changes. The release manifest schema version
is `1.0`; fields and migration ordering are repository-owned and ordinal.

## Persistence and Migration Impact

No migration, designer, snapshot, entity, configuration, index, constraint, or
delete behavior changes. The package is generated only from existing
migrations and never applies them.

## Failure Classification

Stable build failures are invalid version/root/output, dirty source,
restore/build failure, pending model change, migration-script failure, empty
SQL, invalid migration expectation, checksum failure, manifest failure, and
unexpected failure. Failures must not leave a successful-looking package.

## Security and Read-Only Requirements

Generation supplies no connection string or credentials and contacts no SQL
Server. Output contains no secrets or environment-specific server names.
Application and Collector identities gain no DDL permission.

## Determinism and Immutability

Identical version, source commit, migration set, EF tooling, and repository
state produce byte-identical SQL normalization, checksum text, and manifest.
File enumeration and migration ordering are ordinal. No current time,
environment, random identifier, or absolute path enters the package.

## Cancellation

PowerShell native processes honor process termination by the caller. No
runtime asynchronous behavior is introduced.

## Logging, Events and Observability

Build output identifies phases and safe filenames only. It does not emit
connection strings, credentials, environment values, SQL Server details, or
arbitrary local paths into package metadata.

## Test Requirements

Deterministic Pester tests cover version validation, exact EF arguments,
`--idempotent`, pending-model failure, native failure, empty SQL, clean-source
requirement, stable checksum, deterministic manifest, file naming, absence of
timestamps/local paths/secrets, no SQL access, no automatic migration, and CI
artifact configuration.

## Validation Commands

Run Release restore/build/test, all Pester tests, the release-package targeted
tests, EF pending-model validation, offline package generation from a clean
source state where available, documentation links, secret/prohibited-pattern

SQL Server or execute generated SQL.

## Acceptance Criteria

- The three deterministic versioned package files are generated.
- SQL generation uses `dotnet ef migrations script --idempotent`.
- Pending model changes, failed generation, and empty SQL fail.
- CI publishes the package as an artifact.
- Runtime behavior and persistence model are unchanged.
- Automatic migration remains prohibited and statically guarded.
- Tests and documentation pass with no infrastructure contact.

## Integration-Pending Items

## Remaining Risks

EF tool-version changes can legitimately change SQL bytes. Idempotent SQL
reduces repeat-execution risk but does not replace DBA review, backup,
transaction, rollback, compatibility, or environment validation.
