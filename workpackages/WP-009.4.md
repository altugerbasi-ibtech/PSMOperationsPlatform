## Objective

Validate effective SQL permissions required by the Collector, Portal, and SQL
Collector gMSA database users.

## Architectural Boundaries

The package reports effective permissions and never grants, denies, or revokes
them. It creates no principal, changes no runtime behavior, and preserves
separate Windows Collector, Portal, and SQL Collector identities.

## In Scope

- `Release/Database/PermissionValidation.sql`.
- `Release/Database/PermissionValidation.md`.
- Mandatory environment-supplied database-user names.
- `HAS_PERMS_BY_NAME()` checks for `CONNECT`, `SELECT`, `INSERT`, `UPDATE`,
  `DELETE`, `EXECUTE`, `VIEW DATABASE STATE`, and required schema permissions.
- One overall `PASS` or `FAIL` plus deterministic detailed diagnostics.
- Offline completeness and mutation-safety tests.

## Out of Scope

Login/user creation, AD/gMSA provisioning, permission mutation, credentials,
target SQL Server instance permissions, runtime changes, database deployment,
and production certification.

## Permission Profiles

- Collector: database connect and application read/write; schema read/write on
  `configuration`, `collection`, `inventory`, `monitoring`, `operations`,
  `runtime`, and `history`; no database execute or view-database-state.
- Portal: database connect and read; schema read on the eight application
  schemas; no database write, execute, or view-database-state.
- SQL Collector: database connect, read/write, and view-database-state; schema
  read/write on `collection`, `inventory`, and `monitoring`; no database
  execute.

These are Operations Database profiles. Permissions against managed SQL Server
targets remain separately approved and are not inferred by this package.

## Security and Read-Only Requirements

The script uses SQLCMD principal inputs, validates mapped database users,
temporarily switches session context with `EXECUTE AS USER`, evaluates
`HAS_PERMS_BY_NAME()`, and immediately executes `REVERT`. Session impersonation
does not mutate data, schema, principals, or permissions. The script contains
no target-data DML, DDL, permission mutation, credential, or connection string.

## Output Contract

The first result is one `OverallResult`: `PASS` or `FAIL`. On failure, the
second result lists `PrincipalRole`, `PrincipalName`, `Securable`,
`PermissionName`, `ExpectedValue`, `ActualValue`, and `Diagnostic` in
deterministic order.

## Acceptance Criteria

- All three parameterized gMSA database users are validated.
- Every required database and schema permission is checked with
  `HAS_PERMS_BY_NAME()`.
- Missing users, missing permissions, and prohibited effective permissions
  produce `FAIL` diagnostics.
- The package does not modify data, schema, principals, or permissions.
- No runtime or production-code changes occur.
