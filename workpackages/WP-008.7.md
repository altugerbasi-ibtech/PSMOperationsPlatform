## Objective

Complete the approved SDK quality metadata and implement non-durable Execution
Monitoring as an independent subscriber to existing typed Dispatcher and
Runtime events. Monitoring records standard .NET metrics and activities and
maintains a bounded current-health projection without controlling execution or
becoming authoritative state.

## Business and Product Value

Operators and developers need bounded, safe signals that show current pipeline
activity, outcomes, latency, retries, timeouts, cancellations and dispatch
rejections. Plugin authors also need deterministic compatibility presentation,
package metadata, certification metadata, release notes and complete examples.
These facilities make repository-built execution diagnosable without adding a
monitoring backend, durable history or target access.

## Existing Repository Context

Implementation must preserve ADR-0001 through ADR-0006, the Architecture and
Development Process freezes, `IExecutionEventSink`, `ExecutionEvent`,
`ExecutionEventSchemaVersion`, `ExecutionDispatcher`, `CollectorRuntime`,
`LoggingExecutionEventSubscriber`, `PSMOperationsPlatform.CollectorSdk`,
Runtime–SDK compatibility matrix, immutable policy/context/artifact contracts,
and current Runtime state. Existing WP-008.5 and WP-008.6 reviews and tests are
regression authority.

## Architectural Boundaries

The existing flow remains Dispatcher/Runtime → typed events → independent
logging and monitoring subscribers. Monitoring observes and never controls.
Runtime and Dispatcher reference only the event contract and must not reference
monitoring implementations. Execution State remains authoritative. Monitoring
must not execute plugins, resolve handlers, modify policies, retry/cancel work,
mutate plans, contexts, results or state, or persist history. The SDK quality
work remains inside the existing Collector Plugin SDK boundary. No new
architectural layer, event bus, broker, outbox, generic rules engine or vendor
exporter is authorized.

## In Scope

- SDK compatibility badge derived solely from the compatibility matrix.
- Advisory certification and validated package metadata.
- SDK changelog and complete deterministic sample plugins/tests.
- `ExecutionMonitoringSchemaVersion = 1`.
- Explicit event projection using `ActivitySource` and `Meter`.
- Code-owned metric catalog, units and bounded-cardinality policy.
- Run, step, attempt, retry, dispatch, compatibility, policy, artifact and
  warning instruments supported by available typed events.
- A bounded, TimeProvider-based current-health projection and alert signals.
- Independent, failure-isolated logging and monitoring subscribers.
- A health-check adapter because the Windows Collector already uses standard
  .NET health checks; no endpoint is added.
- Contracts, documentation, ADR review, tests and three work-package reviews.

## Functional Requirements

1. Badge schema version 1 produces deterministic label/message/Markdown from
   the authoritative compatibility result; Unknown is never compatible.
2. Certification schema version 1 supports Experimental, Verified and
   Certified as advisory metadata. Samples are Experimental.
3. Package metadata is optional, immutable, length-bounded, deterministically
   normalized and rejects secrets, local/executable paths and unsafe schemes.
4. Hello, NoData, Failure, LongRunning and Cancellation samples are unique,
   read-only, deterministic, cancellation-aware, infrastructure-neutral and
   test/sample registered only.
5. Monitoring accepts only event schema version 1 and explicitly maps known
   event types. Unsupported, duplicate and invalid ordering are diagnosed
   conservatively and never thrown into execution.
6. Instrumentation identity is `PSMOperationsPlatform.Execution`, version 1.
7. Counters and histograms use the catalog named in the launch specification,
   seconds for durations, bytes for sizes and count for counters/gauges.
8. Metric tags are restricted to the code-owned allowlist. Managed server,
   plan/run/step identity, FQDN, address, artifact identity/name/path, URL,
   exception text and arbitrary plugin metadata are prohibited.
9. Activities cover dispatch, run, step, attempt, retry, validation and
   compatibility where the actual events prove those scopes. Parentage is not
   fabricated. Terminal status distinguishes success, error, timeout,
   cancellation and rejection.
10. The health projection retains counts and bounded timestamp queues for the
    most recent 15-minute window, with a maximum of 256 observations per
    category. Status is Unknown before a valid event; Healthy when pipelines
    are healthy and no recent adverse signal exists; Degraded for recent
    execution failures/timeouts/cancellations/rejections; Unhealthy for a
    subscriber/instrumentation failure. Successful events prune expired data
    and permit deterministic recovery.
11. Alert signals are bounded projections only: repeated Runtime failures
    (3), excessive timeouts (3), excessive dispatch rejections (3), and
    monitoring subscriber failure (1) within the health window. They never
    notify or control execution.
12. A composite sink invokes subscribers independently in registration order,
    propagates caller cancellation, isolates subscriber faults, and makes no
    exactly-once claim. State remains authoritative.

## Domain and Application Contracts

Add immutable `SdkCompatibilityBadge`, `PluginCertificationMetadata`,
`PluginPackageMetadata`, related versions/status, and deterministic generation
to the SDK. Extend the plugin descriptor with optional certification/package
metadata while preserving explicit registration and compatibility rules.

Application monitoring contracts include the positive schema constant,
monitoring status/failure/diagnostic/alert enums and records, immutable
`ExecutionMonitoringSnapshot`, `IExecutionMonitoring`, and explicit subscriber
contract. Monitoring input is `ExecutionEvent` only. It receives no
`DbContext`, `IServiceProvider`, `IConfiguration`, credentials, raw results,
artifacts, command output, mutable entities or plugin metadata dictionaries.

## Persistence and Migration Impact

No schema change or migration is authorized. Metrics, activities, events,
health snapshots and alerts are in-process and non-durable. Do not create
monitoring, time-series, event-history, alert-history or health-history tables.

## Failure Classification

Use stable categories: `MonitoringEventInvalid`,
`MonitoringSchemaUnsupported`, `MetricRecordingFailure`,
`ActivityCreationFailure`, `ActivityCorrelationFailure`,
`HealthProjectionFailure`, `MonitoringSubscriberFailure`,
`MonitoringPipelineUnavailable`, `DuplicateEventObserved`,
`EventSequenceInvalid`, `Cancellation`, and `Unexpected`. Monitoring failures
must not be relabeled as target, connectivity, plugin, handler or SQL failures
and cannot alter Dispatcher, Runtime or plugin results.

## Security and Read-Only Requirements

Monitoring and samples perform no target-side work. Metrics and activities
exclude credentials, secrets, connection strings, tickets, tokens, raw
commands/output/artifacts/files, stack traces and high-cardinality target
identifiers. Existing Kerberos-only authentication, `IncludePortInSPN`,
Windows PowerShell 5.1 target compatibility and Collector PowerShell 7.x
compatibility remain unchanged.

## Determinism and Immutability

The same ordered events and TimeProvider values produce the same logical
metrics, terminal activity outcomes, projection, alerts, reason codes and safe
messages. Collections are bounded and deterministically ordered with ordinal
comparison. Reflection order, dictionary business order, current culture,
`GetHashCode`, random values and machine environment values are prohibited.
Trace/span/event IDs and timestamps are not logical equality inputs.

## Cancellation

Asynchronous sinks accept and propagate explicit `CancellationToken`.
Pre-cancelled publication performs no monitoring update. Composite publication
does not convert caller cancellation into subscriber failure. Monitoring does
not initiate Runtime cancellation.

## Logging, Events and Observability

Typed lifecycle events remain the observation boundary and Execution State
remains authoritative. Delivery is in-process, best effort and non-durable;
duplicates and process loss are possible and exactly-once delivery is not
claimed. Logging is one subscriber and Monitoring another. No remote exporter
is configured. Subscriber failures are safely diagnosed and isolated.

## Test Requirements

Deterministic tests must cover all 145 behaviors listed in the approved launch
instruction, grouped as: SDK badge/certification/package/changelog and five
samples; monitoring version/input/schema; every supported counter/histogram and
unit; prohibited/allowed cardinality; dispatch/run/step/attempt/retry
activities and statuses; explicit subscriber mapping, duplicate/order handling
and isolation; bounded health and recovery; bounded alert thresholds; delivery
semantics; security/prohibited dependencies; and Dispatcher/Runtime/event/state
regressions. Tests use listeners, fake subscribers and TimeProvider without
network, SQL, WinRM, PowerShell, process, filesystem mutation or target access.

## Acceptance Criteria

- The SDK badge, advisory certification, changelog, safe package metadata and
  complete non-production samples are implemented and tested.
- The badge never overrides compatibility; certification never changes
  eligibility; package metadata performs no loading or installation.
- Monitoring schema version 1, explicit event projection, standard .NET
  ActivitySource/Meter instrumentation, metric catalog/units/cardinality,
  isolated subscriber, bounded health and bounded alert signals are present.
- Runtime and Dispatcher depend only on the event boundary and remain
  unchanged in ownership; monitoring cannot mutate state or results.
- Logging and monitoring coexist independently; failures are isolated.
- No high-cardinality target identifiers are metric dimensions.
- No exporter, backend, notification, durable monitoring/history, production
  collector, dynamic loading, infrastructure operation, migration, deployment,
  commit or push is introduced.
- Architecture Freeze v1.0 remains Approved and Active.
- All tests, validation, documentation and three human-review documents pass.

## Remaining Risks

In-process monitoring can lose events on process termination. Duplicate events
can affect cumulative metrics because no durable deduplication store exists.
The bounded projection describes monitoring pipeline/current execution signals,
not target health or an SLA. External exporter behavior remains unvalidated.
