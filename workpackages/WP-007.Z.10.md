## Objective

Consolidate repository, release, deployment, infrastructure, security,
validation and operational evidence and answer whether the product is ready for
controlled production deployment. Repository readiness, artifact readiness,
live environment readiness and production certification remain separate.

The validator cannot turn repository completion, mocked tests or synthetic
performance into live production evidence. Missing mandatory evidence blocks a
READY decision. No feature, architecture, deployment or environment mutation is
authorized.

## Primary Command

Create:

```text
tools/validation/production/Invoke-ProductionReadinessValidation.ps1
tools/validation/production/ProductionReadiness.Checks.ps1
tools/validation/production/ProductionReadiness.Evidence.ps1
```

Parameters:

- mandatory `-ConfigurationPath`, `-OutputPath`, `-EvidenceRoot`,
  `-ReleaseVersion`, and `-GoldenBaselineCommit`;
- optional `-SkipLiveEvidenceChecks` and common `-Verbose`.

The command validates repository configuration and safe local paths before
evidence access. `ReleaseVersion` must be semantic and match deployment/release
metadata. `GoldenBaselineCommit` must be a full 40-character commit and resolve
locally. `EvidenceRoot` must be an existing explicit directory outside committed
sample/live report paths; it cannot be a wildcard, repository root or inferred
production location.

The command is read-only except local report creation under `OutputPath`. It
does not invoke child live validators, RAT, build, deployment, Collector,
network, SQL, WinRM or retention operations. It consumes their approved output.

Exit codes:

| Exit | Meaning |
|---:|---|
| 0 | `READY_FOR_CONTROLLED_PRODUCTION_DEPLOYMENT` |
| 1 | `READY_WITH_WARNINGS` |
| 2 | `NOT_READY_FOR_PRODUCTION` or `INSUFFICIENT_LIVE_EVIDENCE` |
| 3 | Invalid configuration/arguments |
| 4 | Execution error |

`INSUFFICIENT_LIVE_EVIDENCE` deliberately exits 2 because deployment is not
authorized. Common structured results are reused; no second framework.

## Readiness and Gate Model

Every gate record contains `GateId`, `Area`, `Requirement`, `EvidenceClass`,
`EvidenceSource`, `Mandatory`, `Expected`, `Actual`, `Status`, `Severity`,
`Owner`, `Risk`, `Remediation`, `RetestRequirement`, `EvidenceHash`,
`ObservedAt`, `ExceptionType`, and sanitized `ExceptionMessage`.

Evidence classes are `REPOSITORY`, `RELEASE_ARTIFACT`, `LIVE_ENVIRONMENT`, and
`HUMAN_APPROVAL`. Gate statuses are `PASS`, `WARNING`, `FAIL`, `MISSING`,
`SKIPPED`, and `NOT_APPLICABLE`. Duplicate GateId values fail validation.

Readiness states:

- `READY_FOR_CONTROLLED_PRODUCTION_DEPLOYMENT`;
- `READY_WITH_WARNINGS`;
- `NOT_READY_FOR_PRODUCTION`;
- `INSUFFICIENT_LIVE_EVIDENCE`.

Deterministic precedence:

1. Any repository/security integrity failure or absent mandatory production
   capability produces `NOT_READY_FOR_PRODUCTION`.
2. Otherwise, missing/invalid mandatory live evidence, RAT, human approval or
   unaccepted mandatory risk produces `INSUFFICIENT_LIVE_EVIDENCE`.
3. Otherwise, accepted non-blocking warnings produce `READY_WITH_WARNINGS`.
4. Only all mandatory gates PASS with approvals/evidence aligned produces
   `READY_FOR_CONTROLLED_PRODUCTION_DEPLOYMENT`.

`-SkipLiveEvidenceChecks` marks mandatory live gates `SKIPPED` and final state
`INSUFFICIENT_LIVE_EVIDENCE`; it never relaxes a gate. Missing live evidence is
never warning-only. Risk acceptance must be supplied as approved evidence; the
validator cannot accept a risk or sign off.

## Validation Categories

### 1. Source Baseline Integrity

Validate repository identity, approved branch policy, clean tree, no
uncommitted/untracked files, baseline and release commits, tag existence/target,
current commit ancestry/relationship, release metadata alignment and no branch
divergence evidence. Use read-only Git commands. Never create/move tags.

### 2. Architecture and Governance

Validate active Architecture and Development Process freezes, ADR catalog and
accepted ADR source files, completed required work-package lifecycle/reviews,
no required Draft/placeholder/conflicting source, WP-008.9 remediation and no
unapproved architecture change. Draft Z.10 itself is exempt only during spec
validation; implementation requires Approved for Implementation.

### 3. Repository Quality

Aggregate current restore/build/solution-test/Pester evidence, documentation
links, secrets, prohibited operations, authentication, SQL safety,
cardinality, generated output, diff and clean state. Command may inspect signed
or run-local evidence but does not silently execute mutable workflows.

### 4. Release Artifact Integrity

Validate release bundle, `Manifest.json`, `Checksums.sha256`, `Version.txt`, SQL
package, deployment/verification/RAT packages, hashes, version/commit alignment,
allowlisted files and absence of build/local output. Reuse WP-009 bundle and
checksum rules; do not define a release format.

### 5. Deployment Configuration Readiness

Validate the shared schema and configuration, mandatory servers/identities,
identity separation, ports, Kerberos-only, IncludePortInSPN, Windows
Authentication, no SQL Authentication/secrets and release/environment
alignment. A committed sample/template is not live configuration. Missing
approved live configuration is mandatory missing evidence.

### 6. Operations Database Readiness

Aggregate deployment package/report, WP-009 schema/permission validation,
migration manifest, idempotency, backup/recovery/compatibility decisions and
runtime-identity connectivity. Require aligned live evidence. No live evidence
means insufficient evidence, never database-ready.

### 7. Collector Host Readiness

Aggregate WP-007.Z.3 repository completion and live report for gMSA, Kerberos,
WinRM, DNS, time, .NET, PowerShell, disk/filesystem, SQL connectivity and
security. Repository completion is not host readiness.

### 8. IIS Target Readiness

Require all configured targets to have aligned live WP-007.Z.4 results covering
DNS/WinRM/Kerberos, IIS role, pools, workers, .NET, logging, security,
filesystem and Collector compatibility. Missing any enabled target is missing
mandatory evidence.

### 9. SQL Target Readiness

Require every enabled SQL target to have aligned live WP-007.Z.5 results for
Windows Authentication, KERBEROS when required, encryption, version, metadata
permissions, DMV access, bounded inventory scope and compatibility. Reject SQL
Authentication and unsafe query evidence.

### 10. Collector End-to-End Readiness

Require a successful live WP-007.Z.6 path for Collector Host → IIS → SQL →
Operations Database → Monitoring → History. Repository aggregation or mocked
evidence does not prove the path.

### 11. Portal Readiness

Aggregate WP-007.Z.7 live host/endpoint `/health`, configuration, Operations DB,
version, process and authentication evidence. Windows Authentication not being
composed is a mandatory production capability defect under current authority
and produces `NOT_READY_FOR_PRODUCTION`; the validator cannot hide or fix it.

### 12. Monitoring Readiness

Aggregate instrumentation, metrics, Activities, subscriber, snapshot, health,
isolation, cardinality and exporter/backend expectation. No exporter/backend is
explicit. When configuration expects none and an approved risk/operations
decision confirms internal monitoring suffices for v1.0, classify as accepted
non-blocking limitation; otherwise missing required external observability is a
blocker. Never claim external Monitoring operational.

### 13. Execution History Readiness

Aggregate WP-007.Z.8 schema/migration/six tables/projection/idempotency/Partial/
queries/paging/isolation/History-Audit boundaries and aligned live database
evidence. Repository tests alone are insufficient.

### 14. Retention Readiness

Aggregate policy, cutoffs, batch limits, cleanup safety, cancellation,
child-first behavior, absence of scheduler, approved execution plan and live
metadata. No destructive execution occurs. No dry-run API is an explicit risk;
it cannot be invented or silently accepted.

### 15. Performance and Scale Readiness

Aggregate Smoke, profile availability, Runtime/Dispatcher boundedness,
Monitoring budgets, History/retention readiness, scale matrix and live status.
Preserve `Live performance validation: NOT EXECUTED` and `Production scale
readiness: NOT PROVEN` until controlled evidence exists. Synthetic PASS is not
production proof.

### 16. Security Readiness

Validate Kerberos-only, no NTLM/Negotiate success fallback, Basic, CredSSP or
TrustedHosts, IncludePortInSPN, Windows Authentication, distinct gMSAs, no SQL
Authentication/secrets/unsafe logging/certificate bypass/excess permissions or
raw sensitive evidence. Security failures produce NOT_READY.

### 17. Operational Readiness

Validate deployment/rollback/backup decisions, ownership, support/incident/log/
retention procedures, maintenance window, change record, CAB evidence, release
and DBA operators and rollback authority. Do not prefill or invent approval.
Missing mandatory operational approval is insufficient evidence.

### 18. Release Acceptance Test

Require intended-environment live RAT with integrity, registered mandatory
modules, OverallResult, ProductionReadinessStatus, exit, configuration hash,
release version, commit, timestamps and evidence references. Repository RAT
tests and sample PASS reports are explicitly rejected as live RAT evidence.

### 19. Known Limitations and Accepted Risks

Emit risk records for Portal Windows Authentication, exporter/backend, every
missing live validation, production scale, retention dry-run/scheduler,
end-to-end and environment gaps. Each record requires unique RiskId, severity,
owner role, impact, workaround, acceptance status/evidence, blocking flag and
retest. No risk is auto-accepted; missing owner/acceptance on a required
non-blocking exception remains blocking.

### 20. Production Readiness Decision

Apply only the deterministic precedence above. Report repository, artifact,
live, approval and risk summaries independently. Exactly one final state and
matching console line/exit are allowed.

## Evidence Contract

Evidence manifests must include schema version, evidence type, release version,
Git commit, configuration hash, target identity key (sanitized in reports),
started/completed UTC timestamps, result, producing command/version, file list
and SHA-256 hashes. Reject missing, future-schema, stale, duplicate, mismatched,
sample-path, modified, secret-bearing or unreferenced mandatory evidence.

Default staleness is not invented: live evidence requires an approved release
or operational policy specifying its acceptable window. If no authority exists,
the gate remains missing approval/evidence rather than assuming a duration.
