## Objective

Extend the WP-007.Z.3 operational validation toolkit with deterministic,
read-only validation of every enabled SQL target explicitly named by the
shared deployment configuration, before SQL Collector execution. Determine
whether each selected endpoint is reachable, uses the approved Windows
authentication and encryption model, exposes required metadata, satisfies
documented SQL Collector prerequisites, and can participate safely in future
inventory and performance collection without making any environment change.

## Business and Product Value

SQL Collector execution depends on target reachability, identity, encryption,
metadata visibility, and narrowly scoped permissions. A repeatable preflight
identifies target, network, authentication, TLS, version, metadata, database,
capacity, backup-observability, availability, and permission gaps before an
authorized collection cycle. Structured evidence supports remediation and
release decisions while preserving the SQL Collector security boundary.

validation, an explicit timeout, and read-only metadata SQL. WP-007.Z.5 must
extend these existing contracts without introducing another framework or an
application data-access pattern.

## Architectural Boundaries

- WP-007.Z.3 remains the single operational validation framework. Reuse its
  configuration, result, status, exit-code, timing, sanitization, DNS, TCP,
  service, registry, filesystem, exception, report, and evidence behavior.
- SQL-specific orchestration, query definitions, checks, and narrowly scoped
  helpers live under `tools/validation/sql/`.
- Use `System.Data.SqlClient`, already present in the common toolkit, unless
  human review approves a repository dependency change. Do not add an
  unapproved package download or second client stack.
- SQL validation runs under the current process identity, intended to be the
  approved SQL Collector service identity. It never accepts another identity,
  username, password, or credential object.
- Windows Collector target permissions and SQL Collector target permissions
  remain under separate identities. `ComputerName` identifies the source host
  for evidence; it does not authorize the Windows Collector identity to
  acquire SQL Collector privileges.
- Runtime projects, Collector behavior, database model, migrations, decision
  rules, execution runtime, monitoring, and history remain unchanged.
- No Generic Repository, Unit of Work, ORM, reflection discovery, plugin,
  automatic retry, or generic PowerShell application framework is introduced.
- No new architectural layer or Architecture Exception is expected. Stop and
  raise any discovered conflict before implementation continues.

## Configuration Contract

Add required top-level `SqlTargets` to the existing deployment configuration.
It is a non-empty array. Existing consumers remain compatible after adding the
new required section to the repository template/sample; controlled older
copies must be amended and revalidated before WP-007.Z.5 use.

Each item has `additionalProperties=false` and exactly these fields:

| Field | Contract |
|---|---|
| `Name` | Required stable operator-facing target key; 1-64 safe label characters; unique case-insensitively |
| `Server` | Required DNS/server name only; no port, instance separator, connection-string syntax, username, or credential |
| `Instance` | Required SQL instance; `MSSQLSERVER` for default or a safe SQL identifier for named instances |
| `Port` | Required static TCP port from 1 through 65535 |
| `ExpectedRole` | Required enum: `ManagedSqlTarget` or `OperationsDatabase` |
| `ExpectedVersion` | Optional non-secret version prefix used only when an approved environment expectation is supplied; absence is informational |
| `ExpectedEdition` | Optional non-secret exact edition expectation; absence is informational |
| `Encrypt` | Required Boolean and must be `true` under the current approved repository policy |
| `TrustServerCertificate` | Required Boolean and must be `false` under the current approved repository policy |
| `DatabasesToValidate` | Required array of unique safe database identifiers; may be empty for server-only managed-target validation |
| `RequiredPermissionsProfile` | Required enum: `SqlCollectorMetadataV1` or `OperationsDatabaseValidationV1` |
| `ValidationEnabled` | Required Boolean; only `true` targets are contacted; disabled targets produce explicit `NOT_APPLICABLE` configuration results |

Cross-field validation must:

- reject empty arrays, duplicate `Name`, duplicate normalized
  `Server`/`Instance`/`Port` endpoints, invalid/duplicate databases, embedded
  credential/connection-string syntax, and unknown fields;
- reject `OperationsDatabaseValidationV1` unless `ExpectedRole` is
  `OperationsDatabase` and the endpoint/database values align with the
  existing `SqlServer` Operations database section;
- require `SqlCollectorMetadataV1` for `ManagedSqlTarget`;
- reject SQL authentication, username, password, credential, connection
  string, access token, certificate bypass, or retry fields;
- keep the committed template unpopulated and the sample limited to reserved
  `.invalid` hosts, example names, and synthetic values.

`TargetName` selects the configured `Name`, not a hostname supplied outside
configuration. Only enabled configured endpoints and ports may be contacted.

## Functional Requirements

### Primary command and target selection

Create `tools/validation/sql/Invoke-SQLTargetValidation.ps1` with
`CmdletBinding` and:

- mandatory `-ConfigurationPath`;
- optional `-ComputerName`, defaulting to the local source machine name and
  used only as source-host evidence;
- optional `-TargetName`, constrained case-insensitively to exactly one
  configured SQL target;
- mandatory `-OutputPath`;
- `-SkipDatabaseChecks`;
- `-SkipPermissionChecks`; and
- common `-Verbose` support.

Configuration validation must complete before DNS, TCP, SQL, AD, registry,
service, filesystem, or network access. With no `TargetName`, process all
enabled targets in deterministic case-insensitive ordinal `Name` order. An
unknown, duplicate, or disabled selected target returns exit code `3` without
contact. Independent checks and targets continue after safe failures.

Skip switches never convert missing mandatory evidence to `PASS`.
`SkipDatabaseChecks` marks database inventory, Operations compatibility,
file/capacity, and backup categories `SKIPPED`; `SkipPermissionChecks` marks
permission and permission-dependent performance probes `SKIPPED`. Because
these categories may contain required prerequisites, mandatory skipped checks
produce at least an overall `WARNING` through the shared status rules.

Exit codes remain: `0 PASS`, `1 WARNING`, `2 FAIL`,
`3 INVALID_CONFIGURATION`, and `4 EXECUTION_ERROR`.

### Authentication and connection contract

- Build connection strings programmatically with
  `System.Data.SqlClient.SqlConnectionStringBuilder`; never accept a connection
  string as input.
- Set `Data Source` from configured server and static port; for the default or
  named instance, validate the observed instance after connection rather than
  invoking SQL Browser discovery or silently switching endpoint.
- Set `Integrated Security=true`, `Encrypt` and `TrustServerCertificate` from
  validated allowed configuration, explicit bounded `Connect Timeout`,
  `Application Name='PSM Operations SQL Target Validation'`, and
  `ApplicationIntent=ReadOnly` where the approved client/server supports it.
- Do not set user ID, password, credential, access token, attach database,
  failover partner, or retry properties. Do not retry automatically.
- Open the minimum number of short-lived connections. Dispose every reader,
  command, and connection in `finally`/`using`-equivalent PowerShell control.
- Set bounded command timeouts. Do not silently fall back to another server,
  instance, port, protocol, authentication mechanism, or encryption policy.

### 1. Target Configuration

Validate target presence, enabled state, safe server/instance/name, port,
unique endpoint, allowed encryption values, safe unique database list,
profile/role alignment, and absence of SQL authentication or secret-bearing
fields. Connection-blocking defects fail before target contact. Disabled
targets are reported without contact when validating all targets.

### 2. DNS and Network Connectivity

Reuse common forward DNS and TCP checks. Attempt reverse DNS only for resolved
addresses and warn when unavailable. Record bounded source interface/route
diagnostics sufficient for troubleshooting without enumerating unrelated
routes or interfaces. Test only configured server/port pairs; no discovery,
ping sweep, UDP Browser query, dynamic-port probing, or arbitrary scanning.

### 3. SQL Connection

Validate a Windows Integrated connection and collect actual server/machine,
instance, current login, `auth_scheme`, `net_transport`, safe local/remote
endpoint fields, and connection timing. Confirm the session uses the expected
endpoint where metadata permits and that command/connection timeouts are
bounded. Connection refusal, timeout, wrong endpoint, or non-Windows
authentication fails required checks. Close the connection immediately after
the bounded check sequence.

### 4. SQL Server Identity and Version

Use `SERVERPROPERTY`, `@@SERVERNAME`, and supported metadata views to collect
machine name, server name, instance name, product version/level, edition,
engine edition, process architecture where queryable, cluster status, Always
On capability, and host platform/OS where supported. Enforce only configured
`ExpectedVersion`/`ExpectedEdition` or repository-approved requirements.
Otherwise report informationally; do not invent a minimum SQL version.

### 5. SQL Service and Protocol

Prefer active-session and SQL metadata. Where approved read-only remote
service/registry access is available to the executing SQL Collector identity,
reuse common service/registry helpers to observe service presence/state,
service account, instance, configured static/dynamic ports, and SQL Browser
dependency. Confirm TCP for the active session and compare the observed port
when queryable. Never start/stop a service, change registry/protocols, or
require extra target permission merely for optional evidence. Unavailable
optional service/registry evidence is `WARNING` or `SKIPPED` with reason.

### 6. Kerberos and SPN

Require `auth_scheme='KERBEROS'` when repository policy requires Kerberos and
fail detected NTLM fallback. Derive the expected static-port form
`MSSQLSvc/<FQDN>:<Port>` from validated configuration and DNS. Use only
read-only approved tooling for missing/duplicate SPN and owner observations
when installed and permitted. Compare observable SQL service account/SPN owner
without exposing unbounded directory data. Missing tooling/permissions yields
structured `WARNING`/`SKIPPED`; no SPN or delegation mutation is authorized.

### 7. Encryption and TLS

Validate active `encrypt_option`, configured `Encrypt=true`, configured
`TrustServerCertificate=false`, and hostname/certificate validation behavior.
Collect certificate/protocol metadata only where exposed safely by supported
SQL metadata or the approved client without trust bypass. Compare certificate
expiration only when available; no expiration threshold is invented unless
documented. Encryption or trust-policy mismatch fails. Never weaken TLS,
install certificates, change Force Encryption, or alter trust stores.

### 8. Server Configuration

Read documented `sys.configurations` values for max/min server memory, max
degree of parallelism, cost threshold, remote admin connections, backup
compression default, optimize for ad hoc workloads, blocked process threshold,
default trace, and contained database authentication. Apply an expected value
only when repository documentation/configuration supplies it; otherwise emit
an informational observation. Never execute `sp_configure` or `RECONFIGURE`.

### 9. Database Inventory

For configured `DatabasesToValidate` only, collect visibility/existence, ID,
state, user access, read-only state, recovery model, compatibility, collation,
containment, owner, create date, permitted backup metadata, data/log file
counts, permitted file paths, sizes, used/free space, growth, and max size.
Do not enumerate unrelated databases beyond a bounded existence/visibility
check necessary to diagnose permission. Do not read tables or business data.

### 10. Operations Database Compatibility

Apply only to `ExpectedRole='OperationsDatabase'`. Validate existence/ONLINE,
and compare compatibility, collation, recovery, and database name to the
existing `SqlServer` configuration. Execute the authoritative WP-009.3
`SchemaValidation.sql` in read-only mode with its documented variables. Invoke
the authoritative WP-009.4 permission validator only where its execution under
the current identity is applicable and `SkipPermissionChecks` is absent.
Capture structured output and exit behavior; do not copy/reimplement those
validators. If deployment is not expected/complete, use documented stage rules
to return `NOT_APPLICABLE`, `WARNING`, or `FAIL`. Never run migrations.

### 11. Collector Metadata Permissions

Use `HAS_PERMS_BY_NAME`, current-login role membership, and bounded metadata
probes to validate only permissions required by approved SQL Collector scope:
server connect plus visibility/access to documented instance metadata,
databases, sessions, connections, blocking, waits, database files, and
performance views. Classify each permission as required, optional,
version-dependent, or unavailable. Validate `VIEW SERVER STATE` and, on
versions where required, `VIEW SERVER PERFORMANCE STATE`; determine whether
`VIEW ANY DATABASE`, `CONNECT ANY DATABASE`, `VIEW DATABASE STATE`, or `SELECT`
access is actually necessary from repository queries before marking required.
Never assume `sysadmin`/`db_owner`, grant rights, create principals, or use
impersonation. Emit one diagnostic per missing required permission.

The WP-009.4 Operations database runtime permission profile is not the managed
target metadata profile. Reuse its result conventions where useful but do not
silently apply its write permissions to managed targets.

### 12. Performance Metadata Availability

Use single, bounded existence/permission or `TOP (1)` probes only for metadata
sources actually required by the documented SQL Collector scope, including
applicable members of `sys.dm_exec_connections`, `sys.dm_exec_sessions`,
`sys.dm_exec_requests`, `sys.dm_os_performance_counters`, `sys.dm_os_sys_info`,
`sys.dm_os_process_memory`, `sys.dm_os_wait_stats`,
`sys.dm_io_virtual_file_stats`, `sys.databases`, and `sys.master_files`.
Version-inapplicable sources are `NOT_APPLICABLE`. Do not collect/persist an
inventory, repeat expensive queries, clear counters/caches/waits, inspect SQL
text, or expose user workload data.

### 13. Database File and Capacity Checks

For configured databases and permitted tempdb observations, report data/log
file size, used/free space, growth value/type, max size, safe file location,
multiple-data-file layout, and tempdb layout/capacity. Apply thresholds only
from approved configuration/documentation; otherwise informational. Do not
grow, shrink, move, create, delete, or alter files.

### 14. Backup and Recovery Observability

When permitted, observe configured-database recovery model and most recent
full/differential/log backup metadata from bounded backup history. Evaluate
recency only against an approved threshold; otherwise informational. Missing
permission is classified explicitly. Do not apply Operations-database policy
to managed application databases without documentation. Never initiate,
inspect file contents, restore, verify, or modify a backup.

### 15. Availability Features

Collect applicable cluster status, availability-group membership, replica
role, synchronization health, listener, mirroring, log-shipping, or standalone
status through bounded metadata. When the repository/configuration has no HA
requirement, findings are informational. Do not fail over, join, remove,
suspend, resume, or modify availability features.

### 16. Security Posture

Confirm Windows authentication, no secret/SQL-auth fields, Kerberos result,
encryption/trust behavior, and current execution identity. Report `sysadmin`
membership as `WARNING` because validation should prove least privilege, not
depend on broad rights. Observe relevant TRUSTWORTHY, cross-database ownership
chaining, owner suitability, and public grants only for configured databases
and documented metadata scope. This is not a general security audit. Never
expose credential hashes, definitions containing secrets, or unrelated grants.

### 17. SQL Collector Compatibility

Produce one per-target `PASS`, `WARNING`, or `FAIL` decision that cites every
constituent mandatory check ID. A failed mandatory prerequisite yields `FAIL`;
an unresolved/skipped mandatory prerequisite or non-blocking concern yields
`WARNING`; otherwise `PASS`. Version/topology-inapplicable checks do not fail.
Recommendations identify the specific missing configuration, connectivity,
identity, TLS, metadata, or permission prerequisite. No decision starts or
authorizes the SQL Collector.

## Domain and Application Contracts

- Reuse the complete WP-007.Z.3 result contract and allowed statuses/severities
  without adding parallel result types.
- Every result contains `CheckId`, `Category`, `Name`, `Description`, `Target`,
  `Status`, `Severity`, `StartedAt`, `CompletedAt`,
  `DurationMilliseconds`, `Expected`, `Actual`, `Message`, `Recommendation`,
  `Evidence`, `ExceptionType`, and `ExceptionMessage`.
- Check IDs are stable, unique, machine-readable, target-prefixed by
  deterministic ordinal, and never embed a live hostname/database/account.
- Duplicate/malformed results are execution errors. Results order by target,
  category, and check ID deterministically.
- SQL operations and environment access are injected as explicit PowerShell
  callables for mocking. Do not hide SQL in a generic repository abstraction.
- Define immutable query descriptors containing stable ID, category, minimum
  supported version/topology, command text, timeout, permission dependency,
  and result mapping. Query text is static and repository-reviewed.

## Persistence and Migration Impact

No product persistence, entity, DbContext, migration, schema, SQL package, or
database modification is authorized. Writes are limited to fixed report files
inside the operator-selected output directory and sanitized committed evidence
templates. No connection may execute product writes or validation history.

## Query Safety

All SQL must be demonstrably read-only and static. Allowed statement/query
constructs are bounded `SELECT`, `SERVERPROPERTY`, `DATABASEPROPERTYEX`,
`HAS_PERMS_BY_NAME`, safe metadata functions, and approved read-only release
validation artifacts. Read-only DBCC is prohibited unless separately justified
in the approved specification amendment; it is not required by this package.

Automated AST/token-aware or conservative lexical safety tests must reject,
outside comments/string literals where correctly parsed, all executable forms
of: `INSERT`, `UPDATE`, `DELETE`, `MERGE`, `CREATE`, `ALTER`, `DROP`,
`TRUNCATE`, `GRANT`, `DENY`, `REVOKE`, `EXECUTE AS`, `RECONFIGURE`, `BACKUP`,
`RESTORE`, `SHRINK`, `CHECKPOINT`, `DBCC FREEPROCCACHE`,
`DBCC DROPCLEANBUFFERS`, and `KILL`. They must also reject PowerShell service,
registry, firewall, SPN, permission, SQLCMD deployment, and SQL mutation APIs.

Do not use dynamic SQL. The existing WP-009 validators are separately approved
artifacts and may contain table-variable population or bounded impersonation
needed for effective-permission validation; they are invoked unchanged and
excluded from the new-query `SELECT`-only catalog scan, while their existing
safety tests remain mandatory.

## Failure Classification

Use shared result statuses/severities and these stable operational classes:

- `INVALID_CONFIGURATION`: schema/cross-field/selection defect before contact;
- `DNS_OR_NETWORK_FAILURE`: configured endpoint cannot resolve or accept TCP;
- `CONNECTION_TIMEOUT`: bounded connection deadline expires;
- `AUTHENTICATION_FAILURE`: Integrated Security connection fails or is not
  Windows authentication;
- `KERBEROS_DOWNGRADE`: actual session is NTLM/non-Kerberos when required;
- `ENCRYPTION_FAILURE`: session/configuration/trust behavior mismatches policy;
- `ENDPOINT_MISMATCH`: connected server/instance/port differs from configured;
- `METADATA_UNAVAILABLE`: required metadata/query cannot be accessed;
- `PERMISSION_MISSING`: a required effective permission is absent;
- `PREREQUISITE_FAILURE`: documented required version/database/schema state;
- `OBSERVATION_WARNING`: optional/broad privilege/unknown evidence concern;
- `DEPENDENCY_SKIPPED`: upstream failure or operator skip prevents safe check;
- `NOT_APPLICABLE`: version, topology, role, or deployment stage excludes check;
- `EXECUTION_ERROR`: malformed result, unsafe query, disposal/report failure, or
  unexpected framework exception.

Do not report access denied as target absence, optional metadata as mandatory,
or live environment failure as a repository defect without supporting evidence.

## Security and Read-Only Requirements

- Execute as the current approved SQL Collector identity only. Never accept or
  construct alternate credentials, usernames, passwords, tokens, or secrets.
- Use Integrated Security, approved encryption/certificate validation, static
  configured endpoints, bounded timeouts, and no retry/fallback.
- Configuration and reports contain no credential, access token, ticket,
  private key, sensitive connection string, business data, SQL text/plan,
  credential hash, secret definition, or unbounded topology/permission output.
- Reports store configuration SHA256, never raw configuration. Sanitize target,
  endpoint, identity, path, SPN-owner, and exception evidence through the
  common protection rules.
- Never mutate SQL, Windows, AD, DNS, network, firewall, registry, service,
  filesystem, certificate, SPN, delegation, availability, or backup state.
- Broad privilege (`sysadmin`) is a warning, never a prerequisite. Do not use
  `db_owner`/`sysadmin` assumptions or validate by performing a write.
- Query only configured databases and documented system metadata. Do not read
  application tables, SQL text, query plans, or business records.

## Determinism and Immutability

- Validate/load configuration once and treat it as immutable.
- Normalize target names and endpoint/database keys case-insensitively for
  comparison while preserving configured display values only in sanitized
  evidence.
- Sort targets, databases, categories, checks, permission diagnostics, and
  report output deterministically with explicit tie-breakers.
- DNS answer order, DMV order, database ID, session ID, timestamps, durations,
  query timing, backup time, file ordering, or availability topology must not
  affect status except where an approved rule explicitly uses the value.
- Time and duration are evidence only unless an approved timeout/recency
  threshold applies. Use repository timestamp conventions.

## Cancellation and Resource Cleanup

Windows PowerShell 5.1 exposes no `CancellationToken` contract. Respect
operator interruption at target, DNS/TCP, connection-open, command, reader,
artifact-validator, and report boundaries. Do not start another target after
interruption. Dispose readers, commands, and connections deterministically in
all success/failure paths. Preserve completed results when safe reporting is
possible; never convert interruption to `PASS` and perform no compensation
because no change was made.

## Logging, Events and Observability

- Reuse common structured JSON, Markdown, log, timing, sanitization,
  recommendation, skipped-reason, and exception behavior.
- Record product/release identity, Git commit, configuration hash, source
  machine/current identity, configured target key and endpoint, sanitized
  actual endpoint, SQL version/edition, auth scheme, encryption state,
  category/check results, duration, recommendations, and per-target/aggregate
  outcomes.
- Emit no product runtime event, metric, database record, monitoring signal,
  execution history, or live inventory artifact.
- Never log raw connection strings, configuration content, query dumps,
  business data, IP topology beyond bounded result needs, SPN ownership lists,
  or unsanitized exceptions.

## Reporting Requirements

Produce only these fixed files in the selected output directory:

- `SQLTargetValidationReport.json`;
- `SQLTargetValidationReport.md`; and
- `SQLTargetValidation.log`.

Use the common report model with SQL-specific title/base name. Multi-target
reports include aggregate status, per-target status, category status, and
check status. Required header/evidence fields include timestamp, product
version, Git commit, source machine, current identity, configuration hash,
configured target/server/instance/endpoint, sanitized actual endpoint,
version/edition, auth scheme, encryption, duration, recommendations, skipped
reasons, and sanitized exceptions.

Console output ends exactly with `SQL TARGET VALIDATION: PASS`,
`SQL TARGET VALIDATION: WARNING`, or `SQL TARGET VALIDATION: FAIL`.

## Test Requirements

Create focused Pester tests following existing validation conventions. Mock
every SQL, DNS, TCP, AD/SPN, WinRM, route/interface, service, registry,
filesystem, and clock boundary. No live infrastructure is required or allowed.

Tests cover at minimum:

1. valid configuration; invalid/missing/duplicate/disabled target; invalid
   server/instance/port/database; endpoint duplicate; and profile/role mismatch;
2. rejection of SQL-auth, credential, password, token, connection-string,
   certificate-bypass, unknown, and secret-bearing fields;
3. all-target and one-target selection, deterministic order, source
   `ComputerName`, skip switches, and configuration-before-contact;
4. connection success, refusal, timeout, wrong endpoint, disposal, Windows
   auth, Kerberos, detected NTLM fallback, and bounded no-retry behavior;
5. encryption/trust success and mismatch;
6. version, edition, engine, platform, service/protocol, SPN, and unavailable
   optional evidence mappings;
7. server configuration values as informational absent approved expectations;
8. configured database inventory, Operations database missing/not deployed,
   authoritative schema-validator integration, and no duplicated schema logic;
9. required/optional/version-dependent permission present/missing/unavailable,
   broad-privilege warning, and no write-based permission probes;
10. bounded performance metadata, files/capacity, backup/recovery, availability,
    security, and version/topology `NOT_APPLICABLE` behavior;
11. all seventeen categories and compatibility `PASS`/`WARNING`/`FAIL` with
    constituent check identifiers;
12. skipped categories, independent failure isolation, multi-target
    aggregation, deterministic exit codes, duplicate IDs, malformed results,
    exception sanitization, and deterministic ordering;
13. JSON/Markdown/log names/content and final console summary;
14. Windows PowerShell 5.1 parsing of every new/changed script;
15. new SQL query-catalog safety, prohibited-statement detection (including
    whitespace/case/comment variants), and absence of dynamic SQL;
16. prohibited PowerShell operation, authentication-policy, secret-pattern,
    environment-value, and generated/build-output scans; and
17. regression of the complete WP-007.Z.3/WP-007.Z.4 validation and WP-009
    release suites after any shared-code change.

Coverage is reported by behavioral case and check category. Do not invent a
numeric coverage threshold unless an approved repository standard defines one.

  permissions may require an explicit specification amendment when production

  authorize broader rights.

  tooling. No recency failure exists without an approved threshold.
