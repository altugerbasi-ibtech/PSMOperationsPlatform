## Objective

Create the Release SQL generation infrastructure for the product by generating
a deterministic SQL Server deployment package from the existing EF Core
migrations.

## Business and Product Value

A source-identifiable, integrity-verifiable SQL package gives DBAs a reviewable
deployment input while keeping schema execution out of application startup and
preserving least privilege.

## Existing Repository Context

The package adapts the repository's existing WP-007.1 PowerShell, Pester, and
GitHub Actions baseline. EF migrations, `OperationsDbContext`, the current
model snapshot, Architecture Freeze v1.0, and Engineering Standards remain
authoritative. This package changes the release artifact contract, not the
database model.

## Architectural Boundaries

Release Engineering owns generation and publication. DBAs own review and
execution. The application must never call `Database.Migrate()`. Automatic EF
Core migrations remain prohibited. No runtime project, production behavior,
business logic, EF model, migration, snapshot, or Collector identity changes
are authorized.

## In Scope

- `Release/Database` generated-output structure.
- PowerShell build and release entry points.
- `dotnet ef migrations script --idempotent` generation.
- Pending-model, failed-command, missing-output, and empty-output guards.
- Deterministic manifest and SHA256 catalog generation.
- GitHub Actions Release artifact publication.
- Offline tests and operator/deployment documentation.

## Out of Scope

SQL execution, database connectivity, automatic migration, migration creation,
schema changes, runtime or production-code changes, permission changes,
deployment, rollback execution, infrastructure modification, and production
certification are prohibited.

## Functional Requirements

1. The package accepts a validated semantic product version.
2. SQL is named `PSMOperations-v{Version}.sql`.
3. Generation uses `dotnet ef migrations script --idempotent`.
4. SQL is normalized deterministically to UTF-8 without BOM, CRLF, and one
   terminal newline.
5. `Manifest.json` contains exactly `ProductVersion`, `BuildDate`,
   `GitCommit`, `SQLScriptName`, and `SHA256`.
6. `BuildDate` is the Git commit timestamp normalized to UTC so identical
   source and version inputs remain deterministic.
7. `SHA256` is the uppercase SHA256 of the SQL artifact.
8. `Checksums.sha256` contains uppercase SHA256 entries for the SQL and
   manifest payload artifacts. It does not hash itself.
9. Build fails if EF migration generation fails, SQL is missing or empty,
   pending model changes exist, source metadata cannot be resolved, or an
   integrity artifact cannot be created.
10. CI publishes the three files as one versioned Release artifact.

## Domain and Application Contracts

No Domain or Application contracts change. The release manifest is an
ordered JSON release-infrastructure contract with the five required fields.

## Persistence and Migration Impact

None. No migration, designer, snapshot, entity, mapping, index, constraint,
default, or database object may change.

## Failure Classification

Stable failure areas are invalid input, dirty or unresolved source, restore or
build failure, pending model changes, EF generation failure, missing or empty
SQL, invalid manifest metadata, and checksum failure. Any failure terminates
the package build and CI publication.

## Security and Read-Only Requirements

Generation contacts no SQL Server, supplies no credential or connection
string, applies no migration, and grants no permission. Windows and SQL
Collector security boundaries remain separate. Generated metadata contains no
secret, machine name, user name, or absolute local path.

## Determinism and Immutability

Identical product version, Git commit, migrations, repository tooling, and EF
tool version produce byte-identical normalized artifacts. Build date comes
from immutable source metadata. Field and checksum ordering is fixed.

## Cancellation

The calling PowerShell or CI process owns cancellation. No runtime asynchronous
behavior is introduced.

## Logging, Events and Observability

Build output reports phases, safe artifact names, and hashes only. It must not
log credentials, connection strings, environment secrets, or target details.

## Test Requirements

Pester tests cover version validation, filenames, deterministic normalization,
manifest fields, source-derived UTC build date, checksum coverage, idempotent
EF arguments, pending-model failure, generation failure, empty SQL, prohibited
runtime migration/database execution, and CI artifact paths.

## Documentation Requirements

Update `Release/Database/README.md`, create
`docs/deployment/WP-009.1-Release-SQL-Package.md`, and update documentation,
roadmap, release, and work-package indexes where status or ownership changes.

## Validation Commands

Run targeted Pester tests, Release build and all .NET tests, prohibited-pattern
searches, artifact-contract searches, `git diff --check`, and diff inspection.
Do not connect to SQL Server or execute generated SQL.

## Acceptance Criteria

- Build and release scripts generate the three required artifacts.
- SQL is produced only through idempotent EF migration scripting.
- Required failure gates stop packaging and CI publication.
- Manifest and checksum contracts match this specification.
- CI publishes the complete package as a Release artifact.
- Documentation explains generation, determinism, DBA ownership, and deferrals.
- No runtime, production-code, EF model, migration, or business-logic changes.

## Integration-Pending Items

DBA review and execution, real SQL validation, permissions evidence, upgrade
rehearsal, rollback execution, deployment, and production certification remain
under WP-007.Z or later approved WP-009 children.

## Remaining Risks

EF tool-version changes can legitimately change generated SQL. Idempotent SQL
does not replace DBA review, backup, transaction, compatibility, rollback, or
environment validation.

## Final Report Requirements

Report files, artifact contract, commands, test counts, CI behavior,
model/runtime impact, prohibited operations, diff state, and review status.
