## Objective

Implement the stable public developer-facing contract inside the frozen Collector Plugin Boundary. Repository-built plugins declare identity, SDK versions, capabilities and artifact support; validate without infrastructure access; execute asynchronously with immutable context/policy and explicit cancellation; and return immutable bounded results. Dispatcher validates descriptors, SDK/runtime compatibility, plugin validation, and policy compatibility before Runtime submission.

## Business and Product Value

The SDK makes collector authoring predictable and reviewable without weakening security or introducing dynamic loading. Version and compatibility contracts prevent incompatible plugins from reaching mutable Runtime execution.

## Existing Repository Context

WP-008.5 already provides explicit StrategyCode resolution, immutable prepared dispatch, Runtime-owned mechanics, bounded artifacts, events, and fake handlers. WP-008.6 promotes the minimal handler surface into a dedicated SDK project and preserves the established plan, Dispatcher, Runtime, and state boundaries.

## Architectural Boundaries

- Execution Plan Engine defines immutable intent.
- Dispatcher resolves and validates plugins, SDK/runtime compatibility, policy compatibility, context and prepared dispatch.
- Runtime executes the supplied plugin and owns timeout, retry, throttling, dependencies, cancellation, events and mutable state.
- Plugins perform one read-only operation and never control Runtime mechanics.
- The SDK is a contract inside the existing plugin boundary, not a new layer.
- No reflection scanning, dynamic loading, service locator, infrastructure access or architecture exception is permitted.

## In Scope

- `PSMOperationsPlatform.CollectorSdk` with version, descriptor, validation, context, policy, result, artifact and plugin contracts.
- Explicit registration and deterministic startup validation.
- Runtime–SDK compatibility matrix and Dispatcher enforcement.
- Safe normalized rejection diagnostics.
- Hello Collector sample and deterministic tests.
- Separate timeout, retry, throttling, parallel and batching policy documentation.
- Narrow architecture, contract, runtime, SDK and review documentation updates.

## Out of Scope

Production collectors, third-party binaries, assembly/directory scanning, dynamic loading, installation, marketplace, signing/trust, hot reload, downloads, NuGet publishing, production artifact storage, OpenTelemetry, monitoring, history, distributed execution, queues, real WinRM/PowerShell/SQL/target access, deployment, migration application, service/process/registry/IIS/feature/runtime/AD/SPN/firewall operations, WP-008.7, WP-008.8 and WP-007.Z are prohibited.

## Functional Requirements

1. Introduce validated `CollectorPluginSdkVersion` 1.0 with ordinal deterministic comparison.
2. Every descriptor declares minimum and target SDK versions plus supported artifact schema versions.
3. Implement an explicit code-owned Runtime–SDK compatibility matrix with typed status, reason and safe explanation. Unknown is never compatible.
4. Finalize `ICollectorPlugin` with immutable descriptor, deterministic validation and asynchronous execution accepting immutable context, immutable policy and explicit `CancellationToken`.
5. Descriptor validation rejects missing identifiers, non-positive versions, unsupported schemas, duplicate subjects/capabilities/artifact schemas, non-read-only plugins and timeout without cancellation.
6. Validation returns immutable status, reason, explanation, issues, warnings and compatibility; normal failure does not throw or access infrastructure.
7. Explicit registration rejects duplicate PluginId and StrategyCode and is independent of registration order for business ordering.
8. Dispatcher performs descriptor, compatibility, plugin validation and policy-capability checks before Runtime. Rejection invokes no Runtime and creates no attempt state.
9. Rejection diagnostics retain safe strategy/plugin/SDK/runtime/policy provenance, failed checks and stable reason codes.
10. Result and artifact contracts validate non-negative metrics, deterministic ordering and safe bounded metadata. Result bytes/objects must equal the sums of file sizes/object counts when those artifact groups are present.
11. Hello Collector returns deterministic fake object data, honors cancellation and is registered only in sample/test composition.

## Domain and Application Contracts

The SDK owns `CollectorPluginSdkVersion`, `CollectorPluginDescriptor`, `CollectorPluginValidationContext`, `CollectorPluginValidationResult`, `ExecutionContext`, `ExecutionPolicy`, `CollectorExecutionResult`, `ExecutionArtifacts`, warning/diagnostic contracts and `ICollectorPlugin`. Application owns the explicit registry, compatibility orchestration, Dispatcher, prepared dispatch and Runtime. SDK public types expose no Application or Infrastructure implementation.

## Persistence and Migration Impact

No persistence or migration is expected. Execution State continues storing approved aggregate metrics and references only. Plugin inventory, package, artifact payload and history tables are prohibited. If an unforeseen durable field becomes essential, work stops for explicit specification amendment and migration review.

## Failure Classification

Use stable SDK/dispatch categories without duplicating Runtime target failures: invalid/unsupported SDK version, runtime incompatibility, invalid descriptor/registration, duplicate plugin/strategy, validation failure, artifact/result contract failure, cancellation violation, event failure and unexpected. Compatibility failure is not connectivity, timeout, collection or handler-execution failure.

## Security and Read-Only Requirements

All plugins are read-only and cancellation-aware. SDK and plugin surfaces contain no credentials, connection strings, tickets, secrets, `DbContext`, `IServiceProvider`, `IConfiguration`, unrestricted shell/process/filesystem/registry access, WinRM session, mutable state, registry/catalog or Dispatcher internals. Kerberos-only behavior, `IncludePortInSPN`, Windows PowerShell 5.1 target compatibility and Collector PowerShell 7.x compatibility remain unchanged.

## Determinism and Immutability

SDK versions, descriptors, contexts, policies, validation, results and artifacts are immutable. Collections are copied, normalized and read-only. Compatibility, validation, registration and sample results use ordinal comparison and stable reason/explanation text. Culture, reflection order, DI order, hashes, randomness and machine environment values cannot affect logical output.

## Cancellation

Every executable plugin declares and honors cancellation. `CancellationToken` is an explicit execution argument. Dispatcher propagates pre-submission cancellation. Runtime remains responsible for active attempt, timeout, retry-delay and run cancellation. Plugins cannot create or control retry state.

## Logging, Events and Observability

Dispatcher emits existing lifecycle events with safe SDK/plugin provenance. Runtime events remain authoritative lifecycle notifications and logging remains an event subscriber. No raw exception, command output, artifact payload or secret enters diagnostics. Monitoring/export/history remain deferred.

## Test Requirements

Tests cover version validation/comparison; compatible, incompatible, unknown and invalid matrix cases; immutable public contracts; descriptor invariants and normalization; explicit registration, duplicate identifiers and order independence; no scanning/loading/service locator; deterministic validation without infrastructure; all result outcomes and metric consistency; artifact validation/order/duplicates; safe Dispatcher explanations for SDK/descriptor/artifact/capability failures; Hello Collector validation, cancellation, deterministic artifact/result, infrastructure neutrality and absence from production composition; and Runtime/Dispatcher ownership regressions. Architecture/security tests verify no prohibited project references, APIs, authentication change or mutable-state leakage.

## Acceptance Criteria

- A dedicated dependency-minimal SDK project builds and exposes the approved immutable contracts.
- SDK version 1.0 and explicit deterministic Runtime compatibility rules exist.
- Unknown/incompatible SDK versions reject before Runtime and create no attempts.
- Dispatcher owns SDK, descriptor, validation and policy compatibility checks with stable safe diagnostics.
- Runtime executes prepared plugins and retains all mutable mechanics.
- Registration is explicit and duplicate-safe; no reflection, dynamic loading or service locator exists.
- Hello Collector is deterministic, read-only, cancellation-aware, infrastructure-neutral and absent from production startup.
- Separate implemented-policy documents and required reviews exist.
- No migration, infrastructure contact, deployment, commit, push or future-package implementation occurs.
