## Objective

Extend the WP-007.Z.3 Operational Validation Toolkit with a read-only Portal
and Execution Monitoring validator. It must assess the configured Portal host,
the repository-implemented Portal surface, Operations database prerequisites,
standard .NET monitoring instrumentation, subscriber integration, immutable
snapshot, advisory health, and exporter/backend expectations without changing
runtime behavior or claiming live success without evidence.

## Business and Product Value

Operators need one deterministic preflight that distinguishes a prepared host,
a deployed and reachable Portal, repository-only Portal capability, working
in-process Monitoring contracts, and unvalidated external integration. Honest
status prevents an ASP.NET health response, repository unit test, or configured
exporter name from being mistaken for production Portal or observability
readiness.

the missing Portal or exporter functionality.

## Architectural Boundaries

- Extend the WP-007.Z.3 toolkit; do not create a second framework.
- PowerShell owns environment preflight and composition only. It must not
  reimplement C# Monitoring calculations, metric definitions, event mapping,
  health scoring, or Portal configuration rules.
- Repository-safe Monitoring validation invokes existing solution tests or a
  narrowly scoped test harness through existing public/internal contracts. It
  does not add validation behavior to runtime assemblies.
- Runtime, Dispatcher, Execution State, Monitoring, History, Portal, IIS, and
  SQL ownership/dependency directions remain unchanged.
- Monitoring observes typed events and never controls Runtime, Dispatcher,
  eligibility, policy, execution, state, or results.
- Execution State remains authoritative. Snapshot/health remain bounded,
  current, non-durable advisory projections and do not replace History.
- Windows Collector, SQL Collector, and Portal identities/permissions remain
  separate. No credential bridging or impersonation is introduced.
- No ADR or Architecture Exception is expected. Any discovered requirement to
  add a Portal feature, public endpoint, exporter, persistence, or new health
  algorithm is an architecture conflict and stops implementation.

## Configuration Contract

Continue to use only
`Release/Deployment/DeploymentConfiguration.schema.json`. Retain the existing
singleton `Portal` object for backward compatibility; do not introduce a
parallel `Portals` collection or second configuration format. `PortalName`
selects the configured Portal by its stable `Name`; the current contract can
therefore validate zero or one enabled Portal. Report aggregation must still
use target-aware common reporting.

Extend `Portal` with these secret-free fields:

| `ValidationEnabled` | Required Boolean |
| `DeploymentExpected` | Required Boolean stage gate |
| `HostingModel` | Required enum; repository-supported value `AspNetCoreIIS` |
| `Scheme` | Required enum `https`; no certificate bypass |
| `Port` | Required integer 1–65535 |
| `BasePath` | Required normalized absolute path, `/` for current host |
| `HealthPath` | Required normalized absolute path, `/health` for current code |
| `AuthenticationMode` | Required enum `Windows` |
| `ExpectedProductVersion` | Optional SemVer string; absent means observe only |
| `ApplicationPath` | Required absolute Windows path when deployment is expected |
| `ConfigurationPath` | Required absolute Windows path when deployment is expected |
| `LogPath` | Required absolute Windows path when deployment is expected |

Add a top-level `MonitoringValidation` object:

| Field | Contract |
|---|---|
| `InstrumentationName` | Required; must match code authority |
| `InstrumentationVersion` | Required; must match code authority |
| `HealthValidationEnabled` | Required Boolean |
| `MetricsValidationEnabled` | Required Boolean |
| `ActivityValidationEnabled` | Required Boolean |
| `SnapshotValidationEnabled` | Required Boolean |
| `ExporterExpected` | Required Boolean; default repository expectation is false |

The schema/template/sample/documentation and configuration validator tests
must be updated together. The sample uses reserved `.invalid` names and
synthetic paths. The template remains environment-neutral. Reject passwords,
tokens, client secrets, connection strings, private keys, certificate content,
SQL Authentication, URI userinfo, secret query parameters, unknown fields,
duplicate JSON keys, conflicting endpoint definitions, invalid paths, scheme,
port, or monitoring combinations.

`PortalName` cannot introduce an endpoint outside configuration. Because the
contract is singleton, duplicate Portal objects are structurally prohibited;
duplicate raw `Portal` keys and conflicting Portal/IIS endpoint definitions
must be rejected before contact.

## Result Contract

Every check uses the WP-007.Z.3 structured result model with `CheckId`,
`Category`, `Name`, `Description`, `Target`, `Status`, `Severity`, `StartedAt`,
`CompletedAt`, `DurationMilliseconds`, `Expected`, `Actual`, `Message`,
`Recommendation`, `Evidence`, `ExceptionType`, and `ExceptionMessage`.

Allowed statuses are `PASS`, `WARNING`, `FAIL`, `SKIPPED`, and
`NOT_APPLICABLE`. Allowed severities are `INFO`, `LOW`, `MEDIUM`, `HIGH`, and
`CRITICAL`. Duplicate `CheckId` values fail assertion. Target IDs use stable
ordinal prefixes and deterministic ordinal ordering. Common aggregation owns
overall status; no category invents a second calculation.

## Functional Requirements and Validation Categories

### 1. Portal Target Configuration

Validate the singleton definition, enabled/deployment stage, stable name,
server, scheme, port, base/health paths, hosting model, authentication mode,
optional version, Windows paths, endpoint conflicts, raw duplicate keys, and
absence of credentials/tokens/secret query parameters. Configuration defects
prevent dependent contact.

### 2. DNS and Network Connectivity

Reuse common forward DNS, optional reverse DNS, configured TCP port, bounded
route/source-interface evidence, and exception sanitization. Probe only the
configured endpoint. Endpoint reachability is the bounded HTTP probe in
category 5; do not scan or change DNS, firewall, or route state.

### 3. Portal Host Prerequisites

Reuse approved WinRM/IIS/host primitives for supported Windows Server, x64,
.NET 10 ASP.NET Core runtime, Hosting Bundle, IIS role, required World Wide Web
Publishing Service observation, application/config/log paths, readable
access, free space observation, time synchronization, and domain membership.
No threshold beyond repository authority is invented. When
`DeploymentExpected=false`, deployment-only checks are `NOT_APPLICABLE` and
the consolidated Portal result cannot claim deployed operation.

### 4. Portal Process or Service

Validate the actual `AspNetCoreIIS` model: configured IIS site/application,
application pool state, deployed assembly/executable, process identity versus
Portal gMSA, and optional product version. Reuse WP-007.Z.4 IIS collection;
do not assume a Windows service. Missing deployment is stage-aware. Never
start, stop, recycle, restart, or terminate anything.

### 5. Portal HTTP Endpoint

Use a bounded request to the configured HTTPS base and `/health` endpoints,
with integrated current identity where supported, explicit timeout, maximum
five redirects, and default certificate/hostname validation. Record sanitized
status, content type, latency, redirect count, and optional supported version
header. Do not store response bodies. Base `/` currently has no Portal feature
and a non-success response must be reported honestly; `/health` is the only
repository-implemented endpoint. No certificate bypass or remote content dump.

### 6. Portal Authentication

Require configured `Windows` policy, Basic disabled, no form/token mechanism,
and no embedded credential. Reuse read-only IIS authentication evidence where
deployed. The current Web composition does not register Windows
Authentication; repository evidence must therefore report the implementation
gap rather than claim success. Authenticated/unauthenticated HTTP behavior is
tested only when live deployment and approved identity permit it. No password
prompt, token, credential object, or IIS change.

### 7. Portal Configuration

Check configured file presence/readability, bounded JSON parse, required
environment marker/reference, database reference shape, encrypted Windows
Authentication expectations, `TrustServerCertificate=false`, logging, health
configuration, production-safe environment, and AllowedHosts policy. Never
emit full files or values. The repository `AllowedHosts=*` observation is a
WARNING until an approved deployment-specific restriction is evidenced; this
validator does not edit it.

### 8. Portal Database Connectivity

Reuse the configured Operations SQL target, WP-007.Z.5 connection primitives,
WP-009.3 schema adapter, and WP-009.4 Portal permission profile. Validate DNS,
port, current Portal identity evidence, Windows Authentication, encryption,
database existence/readiness, schema, compatibility, and Portal read
permissions. Do not duplicate SQL or run migrations/grants. Skip or stage-gate
when Portal deployment is not expected.

### 9. Monitoring Instrumentation Identity

Observe source/public contracts and validate the code-owned name
`PSMOperationsPlatform.Execution`, version `1.0`, Meter/ActivitySource
consistency, `ExecutionMonitoringSchemaVersion=1`, snapshot schema version 1,
and uniqueness. No vendor replacement or redefinition.

### 10. Monitoring Metrics

Read `ExecutionMetricCatalog.Definitions` through repository-safe tests.
Validate unique names, instrument types, units, instrumentation version,
allowed tags, prohibited high-cardinality dimensions, duplicate and negative
measurement policies. Use a local `MeterListener` with bounded synthetic typed
events/measurements. No exporter or remote service.

### 11. Monitoring Activities and Traces

Use a local `ActivityListener` and existing typed test events to observe only
implemented dispatch/run/step/attempt/retry/validation/compatibility scopes.
Validate status mapping, safe tags, supported correlation, and absence of raw
exception/artifact/credential/high-cardinality payload. Do not fabricate
parentage or claim distributed tracing.

### 12. Monitoring Subscriber

Validate approved composition of logging and monitoring subscribers, stable
registration order, explicit schema/event mapping, unsupported-event safety,
subscriber isolation, and non-mutation of Runtime results or Execution State.
Use repository/in-process tests only; no Collector workload.

### 13. Monitoring Snapshot

Reuse `IExecutionMonitoringSnapshotProvider`. Validate immutable snapshot
shape, synchronous bounded read, thread-safe concurrent reads, schema version,
status, bounded counts/queues/diagnostics/reasons, safe codes, and absence of
raw event/artifact/credential data. Prove reads do not change monitoring or
Runtime state through existing deterministic tests.

### 14. Monitoring Health

Invoke the existing advisory health logic; never recalculate it in PowerShell.
Validate score range 0–100, deterministic rating mapping, initial Unknown,
pipeline/subscriber effects, bounded pressure signals, recovery, advisory-only
behavior, and no Runtime/Dispatcher/target-health effect.

### 15. Health Check Integration

Validate the Windows Collector registration named `execution-monitoring` and
its safe, bounded adapter mapping. Validate the Portal host's implemented
`/health` registration separately; it is a generic host health endpoint and
does not currently expose Execution Monitoring. Confirm no target access or
migration occurs. Do not add an endpoint.

### 16. Monitoring Exporter and Backend Expectations

When both expectations are false, report `PASS` or `NOT_APPLICABLE` with the
repository fact that no exporter/backend exists. Expected-but-unconfigured is
`FAIL`. Configured exporter with no approved live backend evidence is
`WARNING`; backend validation remains integration-pending. Validate endpoint
shape/TLS/no secrets and absence of silently enabled vendor defaults. Never
activate or contact an exporter/backend.

### 17. Collector-to-Monitoring Integration

Use fake events/subscribers to validate Dispatcher and Runtime typed event
boundaries, explicit monitoring mapping, independent logging, isolated
monitoring failure, no event bus/broker/outbox/persistence/history
substitution, and no Runtime dependency on the implementation. No plugin or
Collector workload executes.

### 18. Portal Monitoring Readiness

Produce target and overall PASS/WARNING/FAIL using common aggregation. Evidence
must distinguish Portal deployed/operational, repository host present but not
deployed, authentication/configuration/database defect, Monitoring
repository-ready without exporter, missing health exposure, instrumentation/
integration defect, and unavailable live evidence. Repository-only Monitoring
tests may prove repository readiness, never production signals. Portal or
Monitoring production readiness requires actual separately authorized live
evidence.

## Failure Classification

Use stable category/check IDs and common result statuses. Configuration and
selector defects exit 3 before contact. Unexpected top-level execution errors
exit 4. Individual DNS/TCP/host/IIS/HTTP/auth/config/database/instrumentation/
metric/activity/subscriber/snapshot/health/exporter/integration failures remain
isolated structured results. Monitoring failures are never relabeled target
health or Collector failures; an unimplemented feature is not a passing live
check.

## Security and Read-Only Requirements

- All target and repository observation is read-only except local report files.
- Portal HTTP uses the current approved identity; no username/password/token,
  `PSCredential`, credential prompt, or plaintext secret is accepted.
- IIS remote access retains approved Kerberos-only WinRM, configured port,
  `IncludePortInSPN=true`, and no NTLM/Negotiate/Basic/CredSSP/TrustedHosts.
- SQL retains current-identity Windows Authentication, encryption, hostname
  validation, no SQL Authentication, and deterministic disposal.
- HTTP retains platform certificate/hostname validation; no bypass callback.
- Reports contain no response body, configuration dump, connection string,
  certificate material, metric values from live systems, traces, identity
  secrets, topology, raw exception, event, result, or artifact payload.
- Prohibit service/IIS/config/ACL/firewall/certificate/SPN/SQL/database changes,
  migration, write query, exporter/backend provisioning or activation, alert
  delivery, dashboard creation, Collector execution, Runtime control, process
  termination, and remote modification.

Automated AST/text safety scans cover PowerShell command names, HTTP certificate
bypass, authentication fallback, SQL mutation, exporter calls, and prohibited
runtime commands.

## Determinism and Immutability

Targets and categories use ordinal ordering and stable IDs. Configuration hash,
status/severity, target/category summary, recommendations, skip reasons, and
exit code are deterministic for the same normalized evidence. Repository-safe
Monitoring tests use fixed time and bounded synthetic events. Do not use hash
codes, random data, reflection order, culture-sensitive comparison, response
body order, or live metric values as logical result identity. Validation reads
must not mutate snapshots, Runtime, state, configuration, or child results.

## Cancellation and Resource Bounds

PowerShell operations use explicit bounded DNS/TCP/HTTP/WinRM/SQL timeouts and
dispose sessions, responses, streams, SQL objects, Meter/Activity listeners,
and test hosts deterministically. Redirects are capped at five. No automatic
retry hides failure. In-process async test boundaries propagate cancellation;
validation cancellation performs cleanup and does not initiate Runtime
cancellation or continue remote checks.

## Integration-Pending Items

The WP-007.Z integration gate owns all live Portal DNS/TCP/IIS/HTTPS/TLS,
authentication, identity, deployed file/version/config/log, Operations DB
connectivity/schema/permission, and health endpoint evidence. It also owns live
Monitoring signal/exporter/backend verification if a separately approved

Production Portal UI/root functionality, completed Windows Authentication
composition, exporter/backend/dashboard/notification implementation, or a new
Monitoring/Portal endpoint requires separately approved feature scope and is
not silently deferred as implementation debt of this package.

## Remaining Risks

- Current Portal code exposes only generic `/health`; it does not prove Portal
  application, database, authentication, or Monitoring readiness.
- Documented Windows Authentication policy is not currently composed in the
  Web host, so deployed authentication readiness may fail until independently
  approved feature work exists.
- `AllowedHosts=*` requires deployment-policy evidence and is not remediated by
  validation.
- In-process Monitoring is best-effort/non-durable and loses signals on process
  termination; repository listeners do not prove production export.
- No exporter/backend exists by default. Enabling expectation without approved
  implementation/evidence must fail or warn, never fabricate success.
- Remote privilege limitations can make optional IIS/config/TLS/SQL evidence
  unavailable; broader permissions are not authorized.
