## Objective

Extend the WP-007.Z.3 operational validation toolkit with deterministic,
read-only validation of every IIS target named by the shared deployment
configuration, before Collector execution. Determine whether each selected
server satisfies documented PSM IIS inventory prerequisites, report `PASS`,
`WARNING`, or `FAIL` with recommendations, and make no target, IIS, database,
Collector, or runtime change.

## Business and Product Value

PSM must establish that configured IIS servers are reachable through the
approved Kerberos-only WinRM path and expose the operating-system, IIS,
runtime, logging, security, filesystem, and endpoint facts needed for safe
inventory. A repeatable preflight reduces failed collection attempts and
preserves auditable evidence without changing managed servers.

The current deployment schema has no IIS target collection. WP-007.Z.3

WP-007.Z.4 must extend that same contract; it must not create a second
configuration document or validation framework.

## Architectural Boundaries

- The WP-007.Z.3 common validation and reporting scripts remain the single
  operational validation framework. General improvements needed by IIS must
  be made there and remain compatible with Collector-host validation.
- IIS-specific orchestration and checks live under `tools/validation/iis/`.
  Do not duplicate common configuration, result, status, reporting, timing,
  sanitization, DNS, TCP, WinRM, Kerberos, SQL-endpoint, or filesystem logic.
- Validation runs from the operator/Collector side and contacts targets only
  through the approved WinRM architecture. No target-side agent, scheduled
  task, copied script, temporary file, or persistent session artifact is
  introduced.
- The Windows Collector identity is the only target-validation identity.
  SQL Collector permissions remain separate. Application-pool identities are
  observations and are never used to run validation.
- Runtime projects and runtime behavior are unchanged. No Collector execution,
  inventory persistence, handler registration, decision rule, runtime policy,
  monitoring, or history behavior is added or changed.
- This package adds no architectural layer and requires no Architecture
  Exception if implemented within these boundaries. Any discovered conflict
  stops implementation for Architecture review.

## Functional Requirements

### Command and target selection

Create `tools/validation/iis/Invoke-IISTargetValidation.ps1` with
`CmdletBinding` and these parameters:

- mandatory `-ConfigurationPath`;
- optional `-ComputerName` accepting one configured IIS target name;
- mandatory `-OutputPath`; and
- common `-Verbose` support.

Configuration validation must finish before any DNS, network, WinRM, SQL, or
target contact. If `ComputerName` is omitted, validate every configured IIS
target in deterministic, case-insensitive ordinal order. If supplied, it must
match exactly one configured target under a case-insensitive comparison;
otherwise return invalid configuration/input without contacting it. Empty and
duplicate targets are invalid. One target failure must not prevent independent
remaining configured targets from being evaluated.

All remote PowerShell must use the configured WinRM port, explicit
`Authentication='Kerberos'`, `IncludePortInSPN=$true`, and TLS exactly when
`Security.UseTLS=true`. Configuration must require
`WindowsAuthentication=true`, `KerberosOnly=true`, and
`IncludePortInSPN=true`. The implementation must not use `Negotiate`, NTLM,
Basic, CredSSP, TrustedHosts, implicit fallback, DCOM, WMI/DCOM, SSH, or local
execution substituted for the named target.

### 1. Connectivity

For each target, validate forward DNS, reverse lookup when available, TCP
reachability on the configured WinRM port, WSMan endpoint reachability,
Kerberos authentication, and establishment of a constrained read-only remote
PowerShell session. Missing reverse DNS is a documented warning when forward
DNS and Kerberos identity remain unambiguous. Authentication or remote-session
failure is blocking for checks that require target access; those dependent
checks produce structured `SKIPPED` results rather than misleading failures.

### 2. Operating System

Through the approved session, collect and validate the repository-supported
Windows Server version, x64 architecture, uptime/last boot, pending-reboot
signals, domain membership, time zone, and locale. Apply only support rules
already documented by the repository; do not invent minimum uptime or locale,
time-zone, or reboot thresholds.

### 3. IIS Installation

Validate that the IIS Web Server role is installed, the IIS service exists and
is running, the IIS version is observable, required IIS management APIs are
available, and `Microsoft.Web.Administration` can be loaded read-only. Do not
install roles, start services, register assemblies, or alter module paths.

### 4. IIS Configuration

Collect sites, applications, virtual directories, bindings, protocols, host
headers, HTTP bindings, and HTTPS bindings through IIS management APIs. Check
only repository-documented expectations and structural validity. Do not infer
that HTTP is prohibited, require a host header where none is documented, or
change bindings. Certificate metadata may be reported only when safely
available; private keys and secret material are prohibited.

### 5. Application Pools

Collect pool name, managed runtime version, pipeline mode, configured identity
type, sanitized identity name when policy permits, whether the identity is in
gMSA form, current state, auto-start, and recycling configuration. Validate
only documented PSM expectations. Do not request credentials, impersonate an
identity, start/stop/recycle a pool, or modify its configuration.

### 6. Worker Processes

Collect active worker-process identifiers, application-pool mapping, and
running state through read-only IIS APIs. A site or pool with no current worker
process is an observation unless a repository rule makes it a warning or
failure. Never start an application, generate traffic, attach a debugger, or
terminate a process.

### 7. .NET Runtime

Collect installed .NET Framework versions and installed .NET runtimes using
read-only registry/filesystem/runtime discovery already permitted by the
repository. Correlate hosted-application requirements only when those
requirements are directly observable from IIS configuration or a documented
repository prerequisite. Unknown requirements must be reported as unknown;
do not guess, install, repair, or execute an application.

### 8. IIS Logging

Validate whether logging is enabled for each applicable site, resolve the
configured log directory without expanding into an unapproved location,
check directory existence/read accessibility, and report available volume
space. Apply no invented retention or capacity minimum. Inaccessible required
logs are reported with actionable recommendations; no directory or probe file
is created.

### 9. Security

Report effective/configured Windows Authentication, Anonymous Authentication,
Basic Authentication, client-certificate settings, application-pool identity
types, sanitized account names, and gMSA form where used at applicable IIS
configuration scopes. Basic Authentication enabled is at least a warning and
must never be used by the validator. Evaluate other settings only against
explicit repository expectations. Do not retrieve credentials, certificates'
private keys, tokens, tickets, connection strings, or protected configuration
plaintext.

### 10. Filesystem

Validate configured IIS physical paths, application roots, virtual-directory
paths, and IIS log directories for valid local/UNC form, existence, readable
metadata/access where permitted, and free space on the containing volume.
Record inaccessible permissions as bounded evidence without changing ACLs,
impersonating application identities, mapping drives, creating files, or
enumerating application content.

### 11. Connectivity to SQL

For repository-approved SQL endpoints present in the shared deployment
configuration, run only the existing bounded DNS/TCP connectivity checks from
the validation host. Do not open an application database connection, inspect
connection strings, authenticate as an application pool, query metadata or
data, or infer application-to-database authorization.

### 12. Collector Compatibility

Aggregate required prerequisite results for each target into `PASS`,
`WARNING`, or `FAIL` and provide recommendations. Every compatibility decision
must cite its constituent check identifiers and use only documented Collector
inventory prerequisites. A required failed prerequisite yields `FAIL`; an
unresolved required prerequisite or non-blocking concern yields `WARNING`;
otherwise the target yields `PASS`. The run aggregates targets using the same
precedence. No result authorizes Collector execution automatically.

### Status, failure isolation, and reports

Retain WP-007.Z.3 result fields, validation, ordering, status/severity values,
sanitization, exception treatment, timing, overall status precedence, and exit
codes. Report files must be IIS-named equivalents rather than overwriting
Collector-host reports. Output must include target summaries and a run summary.
The output directory may be created; only fixed report/evidence files may be
written there. Console output ends with `IIS TARGET VALIDATION: PASS`,
`WARNING`, or `FAIL`.

## Domain and Application Contracts

- Reuse `New-OperationalValidationResult`, `New-OperationalObservation`,
  `New-OperationalExceptionResult`, `Assert-OperationalResults`,
  `Get-OperationalOverallStatus`, and the common report contract.
- Every check retains `CheckId`, `Category`, `Name`, `Description`, `Target`,
  `Status`, `Severity`, start/completion timestamps, duration,
  expected/actual values, message, recommendation, evidence, and sanitized
  exception type/message.
- Check identifiers are stable, unique, machine-readable, and prefixed by an
  IIS category. Target identity participates in uniqueness without leaking
  environment values into the identifier definition.
- Remote operations are injected/wrapped behind explicit PowerShell callables
  so Pester tests replace all environment access. Do not introduce a generic
  application framework, reflection discovery, or plugin registration.
- Collections and report output use deterministic target/category/check
  ordering. Returned report objects are not mutated after report construction.

## Persistence and Migration Impact

No product persistence, entity, DbContext, migration, schema, SQL package, or
database change is authorized. The only writes are fixed sanitized report
files in the operator-selected evidence directory and committed empty/template
evidence guidance under `artifacts/validation/WP-007.Z.4/`.

## Failure Classification

Use the shared result status and severity model plus these stable operational
classes in messages/evidence:

- `INVALID_CONFIGURATION` for invalid JSON, schema/cross-field errors, empty
  or duplicate target lists, or an unconfigured `ComputerName`;
- `CONNECTIVITY_FAILURE` for DNS/TCP/WSMan reachability;
- `AUTHENTICATION_FAILURE` for Kerberos or session authentication failure;
- `PREREQUISITE_FAILURE` for a documented required OS/IIS/runtime/security/
  filesystem prerequisite;
- `OBSERVATION_WARNING` for non-blocking or unavailable optional evidence;
- `DEPENDENCY_SKIPPED` when an upstream blocking check prevents safe inquiry;
- `EXECUTION_ERROR` for malformed/duplicate results, unsafe unexpected
  exceptions, or report failure.

Do not misclassify unknown application requirements as success, environment
access failure as repository defect, or optional unavailable evidence as a
required failure without an authoritative prerequisite.

## Security and Read-Only Requirements

- Run under the approved Windows Collector identity and use Kerberos-only
  WinRM with the configured port and port-qualified SPN.
- Configuration and output contain no credentials, passwords, tokens, ticket
  material, private keys, secret connection strings, or application data.
- Protect/sanitize exception text, paths, identities, host details, binding
  metadata, and configuration values consistently with WP-007.Z.3. Store the
  configuration SHA256, not its content, in reports.
- Remote script blocks contain read-only queries only. Static tests must reject
  IIS setters/commit operations and service/process/IIS/registry/file/ACL/
  package/firewall/SPN mutation commands.
- Do not use `ServerManager.CommitChanges`, AppCmd mutations, WebAdministration
  setters, `Set-*`, `New-*`, `Remove-*`, `Start-*`, `Stop-*`, `Restart-*`,
  `Restart-WebAppPool`, `Start-Web*`, `Stop-Web*`, service-control, process
  termination, registry writes, or remote file writes. Test-fixture and
  report-object construction are excluded only where demonstrably local and
  non-operational.
- Reported identity and permission data is the minimum required to explain a
  result. Never enumerate application content or unrelated ACL principals.

## Determinism and Immutability

- Normalize configured target names for comparison while preserving their
  configured display value in sanitized evidence.
- Reject duplicate targets case-insensitively and order targets by
  case-insensitive ordinal comparison with a deterministic tie-breaker.
- Order categories and check identifiers deterministically before aggregation
  and serialization. No current time, hash-table enumeration, DNS answer
  ordering, worker PID, or remote return order may alter status decisions.
- Timestamps and durations are evidence, not decision inputs. Use the common
  timing approach and repository timestamp rules.
- Configuration is loaded and validated once per invocation and treated as
  read-only thereafter.

## Cancellation

PowerShell 5.1 compatibility provides no `CancellationToken` contract. Respect
operator interruption at command, DNS/TCP, WSMan, session, remote-command,
and report boundaries; close every session in `finally`. Do not begin another
target after interruption. Preserve already completed in-memory results when
safe reporting remains possible, never convert interruption into `PASS`, and
perform no compensating remote action because validation makes no remote
change.

## Logging, Events and Observability

- Reuse WP-007.Z.3 report timing, safe exception handling, and structured
  JSON/Markdown/log conventions.
- Record release version/commit, configuration hash, source identity/host,
  selected targets, per-check timing/status/severity, recommendations, skipped
  reasons, sanitized exceptions, per-target outcome, and aggregate outcome.
- Emit no product runtime event, metric, monitoring signal, execution history,
  or database record. These reports are operator evidence only.
- Do not log raw configuration, remote script text/output dumps, application
  content, environment variables, connection strings, credentials, tickets,
  certificate private material, or unbounded registry/filesystem data.

## Test Requirements

Create focused Pester coverage that runs without live IIS, WinRM, AD, DNS,
network, registry, filesystem, or SQL infrastructure. Mock every such boundary.
Tests must cover:

1. shared configuration acceptance/rejection, required security constants,
   target-only source, empty/duplicate targets, and selected-target rejection;
2. all-target and one-target selection plus deterministic ordering;
3. Kerberos-only session parameters, configured port, TLS behavior,
   `IncludePortInSPN`, session cleanup, and explicit absence of fallback;
4. success, warning, failure, unavailable evidence, exceptions, and dependent
   skip behavior for all twelve categories;
5. IIS site/application/virtual-directory/binding/pool/worker collection
   mapping using fake `Microsoft.Web.Administration` objects;
6. runtime, logging, security, filesystem, and SQL-endpoint boundaries;
7. result contract validation, duplicate IDs, sanitization, report filenames,
   JSON/Markdown content, exit codes, console summary, and aggregation;
8. no configuration/runtime/database mutation and no live access;
9. regression of the complete WP-007.Z.3 suite after common-code changes; and
10. static prohibited-command and secret-pattern scans.

Coverage must be reported as checks and behavioral cases exercised. No numeric
coverage threshold is invented unless an approved repository standard already
defines one.

## Remaining Risks

- The exact IIS estate and hosted-application runtime requirements are
  environment inputs; the validator cannot certify facts absent from approved
  configuration or observable IIS metadata.
- Permissions may prevent complete security, filesystem, identity, or remote
  registry evidence. Such gaps remain warnings/failures according to whether
  the underlying documented prerequisite is required.
- A successful point-in-time read-only validation cannot guarantee later
  availability or application health and does not authorize Collector start.
- IIS API/version differences across supported Windows Server releases require
  mocked variants and later live validation.
- Reverse DNS, stopped pools, and absent worker processes can be legitimate;
  the implementation must preserve the specified observation-versus-failure
  boundary.
