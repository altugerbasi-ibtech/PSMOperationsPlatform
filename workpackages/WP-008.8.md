## Objective

Implement a durable, queryable, versioned projection of terminal execution
facts. History explains completed runs, steps, attempts, transitions, safe
artifact metadata, resolved policy, and plugin/strategy provenance without
becoming current Runtime state, Monitoring, Audit, event sourcing, or raw
payload storage.

## Business and Product Value

Operators and future reporting surfaces need bounded durable answers after
current state and in-memory monitoring have moved on. The projection provides
safe troubleshooting and operational provenance while preserving the current
state authority and target security boundary.

## Existing Repository Context

Runtime owns `ExecutionRunState`, step/attempt state, retry, timeout,
cancellation, and typed events. Dispatcher owns immutable handler and policy
resolution. Monitoring independently consumes events and remains non-durable.
`OperationsDbContext`, explicit EF configurations, `AsNoTracking`, forward-only
migrations, row constraints, and SQL Server idempotent-script review are the
applicable persistence conventions. Execution History versus Audit is governed
by `docs/architecture/Execution-History-vs-Audit.md`.

## Architectural Boundaries

The frozen dependency flow is typed terminal state and events to an explicit
history projector/writer, Operations Database, then a read boundary. Runtime
and Dispatcher do not depend on the Infrastructure history implementation.
Execution State remains current authority; History may lag and is a durable
projection; Monitoring remains current observation; Audit remains separate.
No new layer, event bus, broker, outbox, event sourcing, generic repository,
Unit of Work, dynamic mapping, or generic reporting language is authorized.

The selected consistency model is **terminal-write preferred**. A complete
immutable projection is constructed after terminal state is available and
written in one short transaction. Explicit `Partial` projections are allowed
when terminal truth exists but non-authoritative events or artifact facts are
missing. No target or plugin execution occurs in the transaction.

## Functional Requirements

1. Projection input must be terminal, schema-compatible, provenance-complete,
   non-negative, and deterministically ordered.
2. Run history records terminal outcome, safe counts/times/failure codes,
   source identifiers, schema/runtime/SDK versions, and artifact summary.
3. Step history follows immutable plan step ordinal and records timing,
   outcome, throttle/skip/cancel/timeout flags, counts, and policy provenance.
4. Attempts are positive and ordered by attempt number.
5. Typed known events map to safe transitions ordered by explicit sequence.
   Unsupported events are classified; no JSON fallback exists.
6. Artifacts retain only bounded identity/type/logical name/content type/counts
   and sizes. Unsafe paths, URLs, content, and metadata are rejected.
7. Duplicate logical projection is a safe no-op returning `Duplicate`; database
   uniqueness remains the authoritative concurrency backstop.
8. A terminal projection lacking intermediate facts is `Partial`, keeps known
   terminal outcome, and uses stable reason codes without fabricated zeroes.
9. Queries support exact run lookup and bounded filters for dates, server,
   strategy, plugin, outcome, failure, and reason plus child retrieval.
10. Lists use offset paging: default 50, maximum 200, page number at least one.
    Ordering is `CompletedAt` descending, null last, then `ExecutionRunId`.
11. Retention v1.0 is runs/steps/attempts/artifacts/policies 180 days,
    transitions and failed projection diagnostics 90 days. Cutoffs use
    `TimeProvider`; deletion is bounded, cancellation-aware, idempotent, and
    never touches active Execution State.
12. History and monitoring failures are mutually isolated. Exactly-once
    delivery is not claimed.

## Domain and Application Contracts

Contracts include explicit enums for projection status and history failures;
immutable run/step/attempt/transition/artifact/policy records; immutable
`ExecutionHistoryProjection`; `IExecutionHistoryWriter`;
`IExecutionHistoryQueryService`; `IExecutionHistoryRetentionService`; page
request/result; query filter; retention policy/result; and projector.
Collections are copied, bounded, and ordinally ordered. Application contracts
contain no EF, `DbContext`, `IQueryable`, `IServiceProvider`, or configuration.
Public diagnostics contain bounded reason codes, not exception text.

## Persistence and Migration Impact

Add schema `history` tables `ExecutionRunHistory`, `ExecutionStepHistory`,
`ExecutionAttemptHistory`, `ExecutionStateTransitionHistory`,
`ExecutionArtifactHistory`, and `ExecutionPolicyHistory`. Use application
logical GUID keys, foreign keys to the run, cascade only within the history
aggregate, bounded strings, `datetime2(3)`, tick durations, check constraints,
and deterministic unique keys:

- run: `ExecutionRunId`;
- step: run plus execution step;
- attempt: run plus step plus attempt number;
- transition: run plus entity type/entity identity/sequence;
- artifact: run plus step plus artifact ID;
- policy: run plus step.

Indexes cover completed time and approved filters without indexing diagnostics.
Create one forward-only WP-008.8 migration and update the model snapshot.
Generate but do not apply idempotent SQL. Prior migrations remain unchanged;
startup migration behavior remains unchanged.

## Failure Classification

Stable categories are `HistoryInputInvalid`, `HistorySchemaUnsupported`,
`HistoryProjectionFailure`, `HistoryPersistenceFailure`,
`HistoryConcurrencyConflict`, `HistoryDuplicateObserved`,
`HistorySequenceInvalid`, `HistoryArtifactMetadataInvalid`,
`HistoryPolicyProvenanceInvalid`, `HistoryQueryInvalid`,
`HistoryUnavailable`, `Cancellation`, and `Unexpected`. They must never be
reported as target, plugin, connectivity, authentication, or Runtime timeout
failures. History faults never rewrite Runtime or Dispatcher results.

## Security and Read-Only Requirements

Persist only internal identifiers, bounded codes, versions, timestamps,
durations, counts, policy provenance, and approved logical artifact metadata.
Reject credentials, connection strings, tokens, Kerberos material, raw
PowerShell/commands/artifacts, file contents, private keys, stack traces,
exception messages, unrestricted URLs/paths, arbitrary plugin metadata, and
unapproved user identity. No target-side or administrative operation occurs.

## Determinism and Immutability

The same terminal state, prepared dispatch, ordered events, artifacts, and
`TimeProvider` produce the same logical projection, query order, retention
cutoffs, reasons, and classifications. Use explicit mapping, ordinal ordering,
positive sequences, immutable copied collections, and stable logical keys.
Do not use reflection ordering, culture sorting, hashes, random logical IDs,
dictionary enumeration, hidden wall time, or arbitrary serialization.

## Cancellation

Writer, query, and retention asynchronous boundaries accept and propagate
`CancellationToken`. Cancellation before persistence creates no partial write.
Query cancellation returns no fabricated result. Retention stops between
bounded batches and reports only committed counts. Cancellation never becomes
a target or Runtime failure.

## Logging, Events and Observability

History consumes typed version-1 events explicitly and exposes safe projection
status/reasons. Existing Monitoring remains independent. No new history metric
is required for v1.0; this avoids duplicating the authoritative metric catalog.
State is persisted independently from best-effort event delivery. Process loss
can prevent projection, and no exactly-once/outbox guarantee is claimed.

## Remaining Risks

history projection. Offset paging can become slower at deep pages. Repository
tests cannot prove SQL Server query plans, lock behavior, migration duration,
or retention throughput. These limitations are explicit and do not authorize
new infrastructure.
