## Objective

Implement a read-only orchestration layer over the existing WP-007.Z.3
Collector-host, WP-007.Z.4 IIS-target, WP-007.Z.5 SQL-target, and WP-009
Operations-database validators. Evaluate every documented prerequisite and
required communication edge for a configured Collector workflow, then produce
a deterministic advisory readiness decision without starting the Collector or
performing inventory collection.

## Business and Product Value

Individual host and target checks do not by themselves prove that the complete
configured workflow is coherent. Operators need one command and one evidence
package that validates configuration, source host, all configured IIS and SQL
targets, the Operations database, required communication paths, and execution
identity before an approved collection window. This reduces fragmented
evidence and prevents Collector execution when any mandatory prerequisite is
failed, skipped, inconsistent, or unavailable.

configuration and DNS consistency unless a later approved amendment adds an
explicit endpoint contract.

## Architectural Boundaries

- WP-007.Z.3 remains the single validation framework. WP-007.Z.6 is a thin
  orchestrator and readiness policy, not another framework.
- Invoke the existing check functions in-process with shared configuration and
  injected operation maps. Do not shell out to child validator entry points,
  parse their console text, or duplicate their checks/queries.
- Reuse the existing result objects. Namespace copied/composed check IDs with
  stable `HOST`, `IIS`, `SQL`, `MATRIX`, `IDENTITY`, `DATABASE`,
  `PREREQUISITE`, and `READINESS` segments so one aggregate report contains no
  duplicate `CheckId`.
- Existing child result status/severity/mandatory meaning is preserved. The
  orchestrator may add only cross-component consistency, dependency, matrix,
  and readiness results that no child package owns.
- Existing child operation factories remain the production boundary; tests
  inject complete fake operation maps and make no environment contact.
- Windows Collector and SQL Collector identities/permissions remain separate.
  End-to-end validation must not merge, impersonate, or transfer them.
- No runtime project, Collector handler, decision rule, execution policy,
  database model/migration, monitoring, history, deployment, or product
  behavior is changed.
- No architecture layer, generic workflow engine, graph framework, plugin,
  process supervisor, Generic Repository, Unit of Work, or retry framework is
  introduced.
- Raise any architecture/security conflict instead of bypassing it.

## Functional Requirements

### Primary command

Create `tools/validation/collector/Invoke-CollectorEndToEndValidation.ps1`
with `CmdletBinding` and:

- mandatory `-ConfigurationPath`;
- mandatory `-OutputPath`;
- optional `-TargetCollector` selecting the configured `Collector.Server`;
- `-SkipRemoteChecks`; and
- common `-Verbose` support.

`TargetCollector` defaults to `Collector.Server`. A supplied value must match
that configured server case-insensitively; otherwise return exit code `3`
before environment access. This package does not select `SqlCollector.Server`.

Validate configuration once before constructing any operation map or running
any check. Hash the same file once and treat its parsed content as immutable.
Use the shared exit codes: `0 PASS`, `1 WARNING`, `2 FAIL`,
`3 INVALID_CONFIGURATION`, and `4 EXECUTION_ERROR`.

### Execution order and failure isolation

Execute these phases in fixed order:

1. deployment configuration and cross-section consistency;
2. Collector host;
3. IIS targets;
4. SQL targets, including Operations database;
5. connectivity matrix;
6. identity consistency;
7. Operations database summary;
8. Collector prerequisite aggregation; and
9. end-to-end readiness.

Configuration-blocking defects stop before contact. Later phases consume
available results and continue independently after child check failures.
Unexpected failure in one target/phase produces a structured framework result
and must not erase prior evidence or prevent safe independent phases.

### Result composition and namespaces

Create new aggregate result objects rather than mutating child results.
Preserve every child field/value after applying common sanitization. Prefix
child IDs deterministically:

- `HOST.<child-id>` for WP-007.Z.3;
- `IIS.Tnnn.<child-id-without-child-target-prefix>` for WP-007.Z.4 targets;
- `SQL.Tnnn.<child-id-without-child-target-prefix>` for WP-007.Z.5 targets.

New cross-component IDs use stable category prefixes. Reject malformed or
duplicate composed IDs before reporting. Sort phases/targets/checks
deterministically; do not depend on hashtable, DNS, DMV, or remote-return order.

### SkipRemoteChecks contract

`SkipRemoteChecks` is a repository/operator diagnostic mode, never proof of
readiness. It:

- passes through to WP-007.Z.3 remote-check handling;
- does not construct/invoke IIS or SQL production operation maps;
- emits one mandatory `SKIPPED` summary for every configured IIS target and
  every enabled configured SQL target;
- emits mandatory skipped matrix edges dependent on those targets; and
- forces readiness to `COLLECTOR NOT READY`.

Local configuration, Collector-host checks that require no target contact,
identity/configuration consistency, reporting, and evidence checks still run.

### 1. Deployment Configuration

Reuse `Get-OperationalConfiguration` and the shared validator. Add only
end-to-end cross-section checks:

- selected Collector equals `Collector.Server`;
- Collector, Portal, and SQL Collector service accounts remain distinct;
- Collector, Portal, SQL Collector, IIS, and SQL endpoint definitions retain
  their shared validator uniqueness rules;
- at least one IIS target exists;
- at least one enabled SQL target exists;
- exactly one enabled SQL target has `ExpectedRole='OperationsDatabase'` and
  remains aligned with the existing `SqlServer` section;
- Windows authentication, Kerberos-only, and port-qualified WinRM SPN policy
  remain enabled; and
- release/product/Git identity is present and safe.

Any cross-section defect is `INVALID_CONFIGURATION` before contact. Do not
extend the shared schema unless implementation discovers a concrete missing
field that is required by this approved scope; such discovery requires an
explicit specification amendment and review before implementation continues.

### 2. Collector Host

Dot-source and invoke the existing WP-007.Z.3 check groups with the same
configuration, selected Collector host, output path, skip flag, and injected
Collector operation map. Preserve category and mandatory semantics. Add one
`CollectorHost` phase summary referencing constituent IDs. Do not execute the
WP-007.Z.3 entry-point process or parse its reports.

### 3. IIS Targets

When remote checks are enabled, invoke `Invoke-IisTargetChecks` for every
configured IIS target in its established deterministic order, using the
existing IIS operation map and no copied IIS logic. Compose/namescape results
and add one `IISTargets` target summary per server plus a phase summary. When
skipped, do not call DNS, TCP, WSMan, Kerberos, session, IIS, filesystem,
registry, or network operations.

### 4. SQL Targets

When remote checks are enabled, invoke `Invoke-SqlTargetChecks` for every
enabled configured SQL target in its established deterministic order, using
the existing SQL operation map. Database and permission checks are not skipped
by the end-to-end command. Compose/namescape results and add target/phase
summaries. Disabled SQL targets are configuration observations and are not
contacted. Do not copy SQL queries or open a separate orchestration connection.

### 5. Connectivity Matrix

Produce deterministic edge results from authoritative child check IDs rather
than repeating probes:

| Edge | Evidence source |
|---|---|
| Collector -> IIS target | WP-007.Z.4 forward DNS, configured WinRM TCP, WSMan, and Kerberos session |
| Collector -> managed SQL target | WP-007.Z.5 forward DNS, configured SQL TCP, Windows connection, endpoint, Kerberos, and TLS |
| Collector -> Operations database | Operations-role WP-007.Z.5 endpoint plus database ONLINE/schema/permission results |
| Collector -> Portal | shared Portal configuration and WP-007.Z.3 Portal DNS result only |

The user-provided logical sequence `Collector -> IIS -> SQL -> Operations
Database -> Portal` is a readiness dependency view, not authorization for IIS
hosts to connect to SQL or for SQL Server to connect to Portal. Do not invent
or probe undocumented lateral flows. Because no Portal TCP port exists in the
approved configuration, Portal TCP/application reachability is
`NOT_APPLICABLE`; DNS/configuration consistency may be reported, and the
limitation must remain explicit.

Each required edge includes constituent IDs. A failed constituent fails the
edge; mandatory skipped/unavailable evidence makes the edge `SKIPPED` and
blocks readiness; otherwise warnings propagate before `PASS`.

### 6. Identity Validation

Validate from configuration and existing child evidence:

- current process identity versus `Collector.ServiceAccount` for live
  execution (case-insensitive domain-qualified comparison);
- Collector host/service-account consistency from WP-007.Z.3;
- SQL connection identity versus `SqlCollector.ServiceAccount` from
  WP-007.Z.5, without requiring the end-to-end process to become both
  identities;
- Portal identity remains distinct and configuration-only;
- gMSA syntax for configured service identities;
- WinRM Kerberos/port-qualified SPN expectations for IIS paths; and
- SQL Kerberos/MSSQLSvc expectations for SQL paths.

One process cannot simultaneously be the distinct Windows Collector and SQL
Collector gMSAs. Therefore a complete live evidence package may be produced by
approved executions under the appropriate identity boundary and then composed
from signed/hash-bound child reports, or by an approved orchestrator host that
can launch separately authorized identity contexts without receiving their
credentials. Repository implementation uses injected child results only.
WP-007.Z.6 must not request credentials, impersonate, merge accounts, or treat
one identity as satisfying both boundaries.

If direct live orchestration under one identity cannot obtain both child
evidence sets, report `COLLECTOR NOT READY`/blocked evidence rather than
weakening the identity architecture. Any external evidence-import design not
already present requires a reviewed specification amendment; do not invent it
during implementation.

### 7. Operations Database

Identify the single enabled `OperationsDatabase` SQL target. Reuse its
WP-007.Z.5 results, which in turn invoke the authoritative WP-009 schema and
permission validators. Aggregate connectivity, ONLINE, configuration,
migration/schema, and effective permission results. Do not invoke another SQL
connection, duplicate SQL, execute migrations, deploy/repair the database, or
silently downgrade a failed/missing validator.

### 8. Collector Prerequisites

Define a stable mapping table in code/documentation from each documented
prerequisite to constituent result IDs. At minimum it covers valid immutable
configuration, release identity/artifacts, Collector host OS/runtime/service/
identity/logging/security, IIS target reachability/prerequisites, SQL target
reachability/metadata/permissions, Operations database readiness, required
matrix edges, and identity-boundary consistency.

Every prerequisite result contains its constituent IDs and classification:
mandatory blocker, warning, or informational. Do not infer a prerequisite not
documented by child specifications or repository authorities. Missing
constituent mapping is an execution error, not success.

### 9. End-to-End Readiness

Compute the advisory decision after validating the complete composed result
set:

- `COLLECTOR NOT READY` when any result is `FAIL`, any mandatory result is
  `SKIPPED`, a required constituent is absent/unavailable, configuration is
  invalid, `SkipRemoteChecks` is used, or identity boundaries cannot be proven;
- `COLLECTOR READY WITH WARNINGS` when no blocker exists and at least one
  non-blocking `WARNING` exists; or
- `COLLECTOR READY` only when every mandatory prerequisite is present and
  `PASS`, with no warning.

This readiness policy is intentionally stricter than the common diagnostic
overall rule, which maps mandatory skipped evidence to `WARNING`. Add
`ReadinessDecision`, `BlockedExecutionReasons`, and constituent IDs to the
aggregate report without changing child/common status semantics.

Readiness never starts, enables, schedules, or authorizes the Collector.

## Domain and Application Contracts

- Reuse the WP-007.Z.3 result contract and allowed statuses/severities exactly.
- Every composed/new result contains `CheckId`, `Category`, `Name`,
  `Description`, `Target`, `Status`, `Severity`, timestamps/duration,
  `Expected`, `Actual`, `Message`, `Recommendation`, `Evidence`, sanitized
  exception fields, and `Mandatory`.
- Add a report-level readiness extension only: `ReadinessDecision` and ordered
  `BlockedExecutionReasons`. Do not create a parallel check model.
- Child operations are passed through an explicit aggregate operations object
  containing Collector, IIS, and SQL operation maps. Tests replace all three.
- Readiness inputs are immutable arrays after composition. No child result is
  modified in place.
- A stable phase/category order precedes check-ID ordering in reports.

## Persistence and Migration Impact

No product persistence, entity, DbContext, migration, schema, SQL package, or
database change is authorized. Writes are limited to the three fixed aggregate
report files in the selected output directory and sanitized repository
evidence templates. Child validators must not emit their separate report files
when invoked in-process by WP-007.Z.6.

## Failure Classification

Preserve child classifications and add:

- `INVALID_CONFIGURATION` for shared/cross-section/selection defects;
- `PHASE_FAILURE` for an unexpected isolated phase error;
- `CONSTITUENT_MISSING` when a required mapped child result is absent;
- `DEPENDENCY_BLOCKED` when a prerequisite/edge cannot be evaluated after an
  upstream failure or authorized skip;
- `IDENTITY_BOUNDARY_UNPROVEN` when required evidence cannot be obtained
  without violating separate-identity architecture;
- `READINESS_BLOCKED` for the final deterministic non-ready decision; and
- `EXECUTION_ERROR` for malformed/duplicate composition, unsafe mutation, or
  report failure.

Do not convert target failures to warnings, absence to not-applicable, skipped
required evidence to readiness, or repository mocks to live success.

## Security and Read-Only Requirements

- Reuse Kerberos-only WinRM/IIS and Windows-authenticated encrypted SQL child
  behavior without fallback, credential input, or trust bypass.
- Never accept/store username, password, token, credential, ticket, private
  key, embedded connection string, raw configuration, or unsanitized child
  output.
- Preserve Windows/SQL Collector identity separation and Portal identity
  distinctness. Do not impersonate or grant rights.
- No command may start/stop/restart/recycle/kill a service, process, site, pool,
  or Collector; mutate IIS/SQL/database/registry/file/ACL/firewall/SPN/
  delegation/certificate/network; deploy; migrate; collect inventory; or write
  remotely.
- The orchestrator runs no SQL text and creates no remote session directly; all
  environment operations remain child-owned and safety-tested.
- Reports store only configuration hash and sanitized bounded evidence.

## Determinism and Immutability

- Load/hash configuration once. Compare names case-insensitively and preserve
  configured display values only in sanitized evidence.
- Use fixed phase order, then deterministic child target/order contracts.
- Namespace IDs from stable target ordinals, not environment values.
- Readiness depends only on validated result status/mandatory/classification
  and required constituent presence, never timestamps, duration, enumeration
  order, DNS order, PID/session IDs, or environment timing.
- Blocked reasons sort by stable check ID and contain no duplicates.

## Cancellation and Cleanup

PowerShell 5.1 has no `CancellationToken` contract. Respect operator
interruption between phases/targets and through existing child boundaries. Do
not begin another phase after interruption. Child modules own their session,
reader, command, and connection cleanup. Preserve completed results when safe
reporting is possible; never turn cancellation into readiness. No compensating
remote action exists because validation is read-only.

## Logging, Events and Observability

- Reuse common timing, sanitization, JSON/Markdown/log, category, target,
  recommendation, skipped, and exception behavior.
- Record timestamp, product/release/Git identity, source/selected Collector,
  configuration hash, duration, validated target summaries, phase/category/
  check outcomes, readiness decision, ordered blocked reasons, recommendations,
  and skipped/not-applicable reasons.
- Emit no runtime event/metric, database record, monitoring/history item,
  inventory, or deployment state.
- Never log raw child reports, configuration, credentials, tickets, connection
  strings, SQL/query output, business data, or unbounded topology.

## Reporting Requirements

Produce only:

- `CollectorEndToEndValidationReport.json`;
- `CollectorEndToEndValidationReport.md`; and
- `CollectorEndToEndValidation.log`.

Use common report generation with title `Collector End-to-End Validation
Report` and base name `CollectorEndToEndValidation`, plus the report-level
readiness extension. Markdown places the readiness decision prominently near
the top and includes blocked reasons. JSON exposes readiness and ordered
reasons as structured fields. The log records readiness and aggregate status.

Console output prints paths/counts and ends with exactly one of:

- `COLLECTOR READY`;
- `COLLECTOR READY WITH WARNINGS`; or
- `COLLECTOR NOT READY`.

The process exit code is derived from readiness: ready `0`, ready-with-warnings
`1`, not-ready `2`, with configuration/framework errors retaining `3`/`4`.
