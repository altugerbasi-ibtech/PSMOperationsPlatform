## Objective

Complete WP-008.7 quality by making the existing bounded monitoring projection
a stable immutable read contract, adding deterministic advisory monitoring
health and plugin-readiness assessments, and completing metric, query,
performance and History/Audit documentation without changing execution
authority or durability.

## Business and Product Value

Future UI, health and exporter integrations need one safe current snapshot
instead of internal projection details. Operators need explainable monitoring
health, plugin authors need a distinct monitoring-readiness signal, and
maintainers need exact metric/query/performance documentation and a protected
boundary between monitoring, Execution History and Audit.

## Existing Repository Context

ADR-0001 through ADR-0007, both freezes, WP-008.6/008.7, the SDK descriptor and
compatibility contracts, `ExecutionEvent`, `ExecutionMetricCatalog`,
`ExecutionMonitoringSubscriber`, existing bounded queues/diagnostics,
`IExecutionMonitoring`, subscriber fan-out, Runtime/Dispatcher event
publication and WP-008.6/008.7 reviews are authoritative.

## Architectural Boundaries

The frozen flow remains Dispatcher/Runtime → typed events → independent
Monitoring subscriber → metrics/Activities/current projection → read-only
snapshot. The snapshot and assessments are observational, advisory,
non-durable and bounded. Execution State remains authoritative. Nothing in
this package controls Runtime/Dispatcher, changes eligibility/policy/state,
implements history/audit, or adds a layer, CQRS framework, report engine, bus,
broker, outbox, exporter, backend or persistence.

## Functional Requirements

1. Snapshot version 1 exposes schema/instrumentation identity, generated/window
   times, status, health score/rating, pipeline flags, current activity,
   bounded recent outcomes/retries/warnings, terminal timestamps and immutable
   ordinal warning/alert/reason collections. It exposes no events, targets,
   artifacts, secrets or mutable internals.
2. The snapshot provider is synchronous, bounded, thread-safe, read-only and
   uses `TimeProvider`; it exposes no mutation/control/infrastructure service.
3. Health assessment schema 1 uses explicit weights totaling 100: subscriber
   25, metric 20, Activity 15, event integrity 10, failure pressure 10,
   timeout pressure 10, rejection pressure 5 and warning pressure 5.
   Insufficient observation returns Unknown. Scores 90–100 are Healthy, 70–89
   Degraded and 0–69 Unhealthy. Each adverse-count pressure loses 2 points per
   observation up to its dimension maximum; duplicate integrity loses 2,
   invalid sequence 5 and unsupported/invalid schema 10. Pipeline false loses
   its full weight. Warning pressure uses bounded diagnostic/warning codes and
   loses one point per code up to five.
4. Readiness assessment schema/badge version 1 validates an explicitly supplied
   descriptor plus evidence. Ready requires a valid read-only descriptor,
   compatible SDK, cancellation, timeout/cancellation consistency, artifact
   schema 1, safe package metadata, documentation reference, explicit contract
   test evidence, explicit safe-failure-result evidence and explicit quality
   assessment availability. Missing optional evidence yields PartiallyReady;
   invalid descriptor/incompatibility yields NotReady; unavailable evidence
   yields Unknown. It never changes dispatch.
5. `ExecutionMetricCatalog.Definitions` is the single authoritative, immutable,
   ordinal metric source. Each unique entry records name, type, unit, meaning,
   source event/condition, allowed/prohibited dimensions, cardinality,
   duplicate/negative/failure behavior and instrumentation version.
6. Query examples use only catalog metrics and allowed dimensions and are
   explicitly unvalidated backend examples.
7. Performance budgets are advisory: metric-only median <1 ms, Activity event
   median <2 ms, health update <1 ms and snapshot <5 ms. Focused local tests
   prove bounded work/memory and report informational timing without becoming
   noisy CI microbenchmark gates.
8. History/Audit documentation reserves WP-008.8 for durable execution
   projection and requires a separate approved Audit package.

## Domain and Application Contracts

Application owns snapshot, provider, health rating/assessment/dimension
results and code metric definitions. SDK owns readiness evidence, status,
dimension result, assessment and badge because they describe SDK plugin
authoring metadata. Public results are sealed immutable records with
read-only copied collections and stable machine codes. Failure classifications
add snapshot, assessment, documentation/performance and input failures only
where needed.

## Persistence and Migration Impact

No database, entity, configuration or migration change is authorized.
Snapshots, assessments, badges and performance measurements are computed
in-process and never persisted. No monitoring, history or Audit table is
created.

## Failure Classification

Use safe codes equivalent to `MonitoringSnapshotGenerationFailure`,
`MonitoringHealthAssessmentFailure`,
`MonitoringReadinessAssessmentFailure`,
`MonitoringDocumentationValidationFailure`,
`MonitoringPerformanceMeasurementFailure`,
`MonitoringSchemaUnsupported`, `MonitoringInputInvalid` and `Unexpected`.
Failures remain observational and cannot affect Runtime, Dispatcher, plans,
contexts, state, plugin results, retries, cancellation or remediation. Public
results never expose exception text.

## Security and Read-Only Requirements

Contracts and documentation contain no credentials, connection strings,
tickets, tokens, raw commands/output/artifacts/files, absolute local paths,
exception/stack text, user/target identity or arbitrary plugin dimensions.
Examples use synthetic identifiers. Kerberos-only authentication,
`IncludePortInSPN`, identity separation and target read-only behavior remain
unchanged.

## Determinism and Immutability

The same explicit inputs and TimeProvider produce the same logical snapshot,
score/rating/reasons, readiness result/badge, metric ordering and budget
classification. Collections are copied, bounded and ordinally ordered.
Reflection/dictionary business order, current culture, `GetHashCode`, random
input, wall clock bypass and assembly scanning are prohibited.

## Cancellation

The new read/calculation operations are bounded synchronous pure/in-memory
operations and need no cancellation parameter. They initiate no asynchronous
work and cannot cancel Runtime. Existing event publication cancellation remains
unchanged.

## Logging, Events and Observability

Typed events and Execution State authority remain unchanged. No new event type,
Audit event, durable event path or direct lifecycle logging is introduced.
Snapshot/score/readiness generation emits no secrets and performs no external
callback. Metric code remains authoritative over documentation.

## Test Requirements

isolation; metric definition uniqueness/document parity/type/unit/cardinality;

readiness evidence, separation, deterministic badge and no loading/network;
