# WP-010.1 Portal Windows Authentication Composition

## 1. Governance Status

Architecture, Security, and Operations granted human approval. The package
entered `Approved for Implementation`, completed repository implementation and
validation, moved to `Ready for Review`, and is now `Approved` following human
review. No individual approver identity is recorded or inferred.

The package follows `Draft` -> `Approved for Implementation` -> `Ready for
Review` -> `Approved`. Repository completion does not establish live IIS or
Kerberos readiness.

## 2. Purpose

Close only the WP-007.Z.10 mandatory repository capability defect that Windows
Authentication is documented but absent from Portal Web-host composition.
Compose standard ASP.NET Core/IIS authentication, deny-by-default authorization,
and an explicit health endpoint exception without implementing roles, Portal
features, deployment automation, or another authentication system.

Repository implementation and live IIS/transport evidence remain separate.

## 6. Selected Authentication Architecture

The production mechanism is ASP.NET Core IIS Integration using
`IISDefaults.AuthenticationScheme`. The Web host will register authentication
and authorization using framework APIs already supplied by the Web SDK/shared
framework. No additional NuGet package is planned.

Conceptual composition:

```csharp
builder.Services.AddAuthentication(IISDefaults.AuthenticationScheme);
builder.Services.AddAuthorization(options =>
{
    options.FallbackPolicy = new AuthorizationPolicyBuilder()
        .RequireAuthenticatedUser()
        .Build();
});

var app = builder.Build();
app.UseAuthentication();
app.UseAuthorization();
app.MapHealthChecks("/health").AllowAnonymous();
app.Run();
```

The exact implementation must compile on repository `net10.0` and use the
framework namespace for IIS Integration. Middleware order is authentication
then authorization, after host construction and before endpoint mapping.

IIS supplies the authenticated Windows principal. Application code must not
construct `WindowsIdentity`, impersonate, store token handles, trust forwarded
user headers, select NTLM, or implement fallback credentials.

## 7. Authorization Policy

The fallback policy requires `RequireAuthenticatedUser`. This makes all current
and future endpoints protected unless explicitly annotated as anonymous.

This package defines no roles, groups, permission claims, or arbitrary-domain
membership rule. Existing authorization documentation describes a future
permission model but is not implementation authority for adding roles here.
An unauthenticated protected endpoint receives 401. A separately denied policy
for an authenticated test principal produces 403. Successful authenticated test
requests prove ASP.NET Core behavior only, not IIS transport authentication.

## 8. Health Endpoint Policy

Selected policy: **anonymous generic liveness health**.

Repository evidence supports this bounded default because current `/health`:

- uses the framework health endpoint with no registered target/database checks;
- exposes only bounded generic health output;
- performs no Collector, SQL, IIS, Monitoring-backend, or migration action;
- is the existing deployment configuration health path.

The endpoint must receive explicit `AllowAnonymous` metadata. No other Portal
endpoint becomes anonymous. Tests must prove the response contains no identity,
configuration, exception, topology, claim, token, or credential material and
that fallback authorization remains active elsewhere.

No `/health/live`, `/health/ready`, or dedicated Monitoring endpoint is added by
this package; doing so would be unrelated feature scope despite baseline future
documentation.

## 9. Actual Host and Blazor Boundary

The current Web project does not compose Blazor services, components, or render
modes. Therefore this package will not add cascading authentication state,
`AuthorizeView`, UI identity display, or an `AuthenticationStateProvider`.

When Blazor is implemented by separately approved scope, the standard server
authentication state must consume `HttpContext.User` without serializing
Windows tokens or sensitive claims. WP-010.1 tests record Blazor-specific items
as not applicable to the actual host rather than inventing components.

## 10. IIS Deployment Contract

Controlled deployment documentation must require:

- IIS Windows Authentication enabled;
- IIS Anonymous Authentication disabled for protected Portal traffic;
- `/health` anonymity handled only by the approved endpoint/application policy
  and deployment arrangement;
- no Basic or Forms Authentication;
- no client certificate requirement unless separately approved;
- ASP.NET Core Hosting Bundle/ANCM compatible with `net10.0`;
- Portal application pool/process identity follows existing dedicated Web gMSA
  architecture;
- HTTPS and normal certificate validation remain enabled.

The SDK-generated publish `web.config` convention remains unchanged. This
package will not commit a duplicate `web.config` unless implementation review
finds an existing repository-owned transform authority. It will not execute
IIS commands or modify a live server.

Because IIS authentication settings apply before ASP.NET Core endpoint
authorization, Operations review must confirm how the intentionally anonymous
`/health` request is supported while protected traffic has IIS Anonymous
Authentication disabled. The implementation must not weaken all Portal traffic
to solve this. If the approved IIS topology cannot express this policy safely,
implementation must stop for an explicit specification amendment.

## 11. Local Development and Tests

Current Kestrel launch profiles do not establish Windows Authentication. This
package will document that Development Kestrel is not production authentication
evidence and will not silently disable the fallback policy.

Functional tests may replace the authentication scheme only inside the test
host with a deterministic test handler. The test handler must not ship in the
Web assembly, accept headers as identity, use credentials, or claim Kerberos.
If production local-Kestrel Windows Authentication becomes mandatory, adding
the standard Negotiate package requires an approved amendment and package
review.

## 12. Claims, Logging, and Failure Safety

The application may observe `IsAuthenticated`, `AuthenticationType`, and a
bounded display name only where later approved. WP-010.1 adds no user display or
identity logging.

It must not log claims collections, SIDs, ticket/token material, authorization
headers, cookies, access-token handles, or raw infrastructure failures.
Authentication failures use framework 401/403 behavior, never HTTP 200, stack
traces, a custom login page, or a database/Monitoring bypass.

## 15. WP-007.Z.10 Integration and Decision Precedence

The Portal capability fact must consume the same bounded composition evidence
as Z.7 rather than a two-token regex. Once all five composition facts pass,
`PRD.11.PORTAL.AUTH` no longer reports `PortalAuthenticationNotComposed`.

The approved Z.10 precedence remains unchanged:

1. any other missing mandatory capability, blocking security defect, required
   Monitoring backend absence, or missing required risk acceptance produces
   `NOT_READY_FOR_PRODUCTION`;
2. only when those defects are resolved, absent mandatory live Portal and other
   live evidence produces `INSUFFICIENT_LIVE_EVIDENCE`;
3. repository composition alone never produces READY.

Therefore tests must prove both:

- composition present + no other capability/risk defect + live evidence absent
  => `INSUFFICIENT_LIVE_EVIDENCE`;
- composition present + Monitoring risk acceptance still required and absent
  => `NOT_READY_FOR_PRODUCTION`.

This preserves the approved Z.10 Monitoring gate. The request's expected
`INSUFFICIENT_LIVE_EVIDENCE` outcome cannot be forced if the required Monitoring
risk acceptance or another mandatory defect is absent. Human approval of this
Draft confirms this interpretation; it does not itself accept the risk.

## 16. Test Plan

### 16.1 Composition and Authorization

Tests will prove authentication/authorization service registration, IIS scheme,
fallback authentication requirement, middleware presence/order, explicit
anonymous health metadata, 401 unauthenticated behavior, authenticated success,
and 403 under a deterministic denying test policy.

Static/architecture tests will reject custom identity headers, custom identity
construction, impersonation, service locator use, Basic, Forms, cookies,
bearer/token login, NTLM-specific selection, custom login routes, role/group
invention, unsafe claims logging, and production test handlers.

### 16.2 Health

Tests will prove anonymous `/health` succeeds, remains bounded/non-sensitive,
does not access target systems or apply migrations, and does not make other
endpoints anonymous.

### 16.3 Windows Identity and Host Boundary

A deterministic authenticated `ClaimsPrincipal` in test composition will retain
a safe authentication type without persistence or wholesale claim logging.
Tests explicitly state that they do not prove IIS, Kerberos, or NTLM transport.

Blazor authentication-state tests are not applicable because no Blazor host is
implemented. A regression test will prevent WP-010.1 from introducing a custom
provider or token serialization.

### 16.4 IIS, Validation, and Readiness

Tests/doc scans will require IIS Windows Authentication, protected-traffic
Anonymous Authentication disabled, Basic/Forms prohibited, no credentials, and
no live IIS mutation. Focused Z.7 tests prove bounded composition detection;
focused Z.10 tests prove the Portal defect closes without creating READY and
without hiding Monitoring, approvals, RAT, scale, or live evidence.
