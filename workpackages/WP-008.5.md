## Objective

Implement the Execution Dispatcher defined by Architecture Freeze v1.0. The
Dispatcher becomes the sole component that resolves an executable plan step to
an explicitly registered handler, validates its descriptor, resolves all plan
policy references into one immutable `ExecutionPolicy`, validates
policy-to-plugin compatibility, constructs an immutable `ExecutionContext` and
`PreparedExecutionDispatch`, submits the prepared dispatch to Collector
Runtime, emits dispatcher lifecycle events, and returns a normalized result.

Collector Runtime must stop resolving StrategyCode, querying the handler
registry, retrieving descriptors, querying the Execution Policy Catalog, or
resolving policy references. Runtime executes the prepared handler under the
prepared policy and retains StrategyCode only as provenance. Dispatcher must
never execute handler business logic directly.

## Business and Product Value

The package creates one auditable preparation boundary between immutable plan
intent and mutable runtime execution. It prevents Runtime from combining
selection and execution responsibilities, rejects incompatible plugins before
attempt state exists, makes policy capability requirements explicit, and
establishes stable event and artifact contracts for later SDK, monitoring, and
history work.

## Architectural Boundaries

The frozen responsibility statement is:

> Dispatcher resolves. Runtime executes. Plugin collects.

- Execution Plan remains immutable.
- Resolved `ExecutionPolicy` remains immutable.
- `ExecutionContext` remains immutable.
- Execution State remains separate and mutable.
- Dispatcher resolves and validates; it does not retry, enforce timeout,
  throttle, execute dependencies, invoke handler business logic, or transition
  Execution State.
- Runtime owns handler invocation, retry, timeout, throttling, dependency
  execution, cancellation, metrics, failure isolation, and mutable state.
- Plugin/handler owns one bounded collection operation.
- Runtime and handlers receive no `IServiceProvider`.
- Handlers receive no `IConfiguration` or `DbContext`.
- Registration is explicit. Reflection scanning, assembly scanning,
  `Assembly.Load`, `Activator.CreateInstance`, and dynamic plugin loading are
  prohibited.
- Policy incompatibility is rejected; no silent downgrade is permitted.
- Any discovered need to change these boundaries requires an ADR or approved
  Architecture Exception before implementation continues.

## Functional Requirements

### Dispatcher flow

For one request, Dispatcher must:

1. validate request identity, schema versions, subject, executable step, plan
   provenance, and cancellation;
2. emit `ExecutionDispatchRequested`;
3. resolve the handler by exact ordinal StrategyCode;
4. retrieve and validate its immutable descriptor and emit
   `ExecutionHandlerResolved`;
5. resolve every timeout, retry, parallel, throttling, and batching reference
   from the plan into one immutable `ExecutionPolicy` and emit
   `ExecutionPolicyResolved`;
6. validate policy compatibility against descriptor capabilities;
7. create one immutable `ExecutionContext` and
   `PreparedExecutionDispatch`;
8. emit `ExecutionDispatchPrepared`;
9. submit the prepared dispatch to Runtime and emit
   `ExecutionDispatchSubmitted`; and
10. return a normalized result that distinguishes Submitted, Rejected,
    Cancelled, and Failed preparation/submission.

Validation or compatibility rejection must not invoke Runtime or create an
attempt state. It emits `ExecutionDispatchRejected` with a stable reason. An
event-publication failure is recorded without exposing exception text and does
not mutate the plan or silently alter the dispatch decision.

### Handler registry and descriptor

The Dispatcher-owned registry must:

- resolve exact StrategyCode with `StringComparer.Ordinal`;
- reject duplicate StrategyCode registrations;
- expose neither `IServiceProvider` nor implementation discovery;
- return an immutable descriptor;
- validate descriptor StrategyCode equality;
- require non-empty stable `PluginId`;
- require positive `PluginVersion`;
- require supported positive `DescriptorSchemaVersion`;
- require `ManagedTargetServer` subject support;
- require `IsReadOnly = true`; and
- contain fake/test registrations only in this package.

After refactoring, Collector Runtime must have no dependency on the registry.

Descriptor capability declarations are immutable booleans:
`SupportsCancellation`, `SupportsRetry`, `SupportsTimeout`,
`SupportsParallelExecution`, `SupportsBatchExecution`, and `IsReadOnly`.

### Resolved ExecutionPolicy

Execution Plan retains its existing immutable policy references. Dispatcher
resolves them into one immutable object containing:

- `PolicySchemaVersion`;
- timeout policy code/version and positive bounded duration;
- retry policy code/version, positive `MaxAttempts`, immutable retryable
  failure categories, and immutable deterministic delay schedule;
- parallel policy code/version and bounded concurrency semantics;
- throttling class/policy code/version and bounded concurrency semantics;
- batching policy code/version and enabled/disabled semantics; and
- every source policy code and version required for auditability.

Resolution is explicit, deterministic, version-aware, infrastructure-free,
configuration-reload-free, and contains no mutable attempt counter. Unknown
codes, unsupported versions, non-positive timeout/attempt values, negative
delays, unbounded concurrency, or internally inconsistent policy values are
rejected.

Runtime receives the resolved policy in `PreparedExecutionDispatch`. Runtime
must not query `IExecutionPolicyCatalog`.

### Policy-to-plugin compatibility

The validator enforces:

- `SupportsTimeout` requires `SupportsCancellation`;
- any positive timeout policy requires `SupportsTimeout`;
- `MaxAttempts > 1` requires `SupportsRetry`;
- parallel concurrency greater than one requires
  `SupportsParallelExecution`;
- enabled batching requires `SupportsBatchExecution`;
- every executable WP-008.5 handler requires `SupportsCancellation`; and
- every executable handler requires `IsReadOnly = true`.

Incompatibility rejects preparation, returns a stable code, emits rejection,
does not invoke Runtime, creates no attempt state, leaves the plan unchanged,
and never downgrades timeout, retry, parallelism, or batching.

### ExecutionContext

Create an immutable narrow context containing only:

- ExecutionRunId, ExecutionPlanId, and ExecutionPlanStepId;
- ManagedServerId and safe TargetFqdn when required;
- StrategyCode and StrategyVersion;
- PluginId and PluginVersion;
- ManagedTargetServer subject;
- source DecisionPlanId, CapabilitySnapshotId, InventoryRunId, and
  InventoryVersion;
- relevant capability, decision, plan, policy, descriptor, event, and runtime
  schema/contract versions;
- `TimeProvider`; and
- a narrow safe execution-event publisher.

`CancellationToken` is passed explicitly to Dispatcher, Runtime, and handler
asynchronous APIs and is not retained ambiguously in the context.

Context must not contain `DbContext`, `IServiceProvider`, `IConfiguration`,
credentials, connection strings, WinRM session, mutable state, mutable plan
entity, policy catalog, handler registry, raw command, or mutable dictionary.

### PreparedExecutionDispatch and result

`PreparedExecutionDispatch` is immutable and binds the validated request,
handler boundary instance, descriptor, resolved policy, and execution context.
It contains no executable delegate, implementation type name, assembly name,
service provider, configuration, persistence context, or credential.

`ExecutionDispatchResult` contains a strongly typed disposition, stable
failure category/reason, safe explanation, relevant identities and versions,
optional Runtime result for a submitted dispatch, and event-publication
warning. It never uses exception text as its machine contract.

### Execution artifacts

Define bounded immutable contracts:

- `CollectedFileArtifact`;
- `CollectedObjectArtifact`;
- `GeneratedMetricArtifact`;
- `ExecutionWarning`; and
- `ExecutionArtifacts`.

Every artifact has `ArtifactSchemaVersion`, stable non-empty `ArtifactId`,
bounded safe metadata, and deterministic ordinal ordering. File metadata may
contain a safe logical reference, non-negative size, and approved hash; it must
not expose unrestricted paths or an open handle. Object artifacts use bounded
safe type/key/count/reference metadata, not arbitrary object graphs. Metric
artifacts use stable names, finite numeric values, and safe units. Duplicate
ArtifactId is invalid.

Empty artifacts are valid, including NoData. Counts and sizes are non-negative
and aggregate consistently with handler result metrics. Contracts contain no
stream, file handle, credential, command, secret, or unbounded binary payload.
Execution State may persist only counts and already-approved safe references.
Production artifact storage is not implemented.

### Events and logging subscriber

Introduce independent `ExecutionEventSchemaVersion = 1`. Dispatcher events are:

- `ExecutionDispatchRequested`;
- `ExecutionHandlerResolved`;
- `ExecutionPolicyResolved`;
- `ExecutionDispatchPrepared`;
- `ExecutionDispatchRejected`; and
- `ExecutionDispatchSubmitted`.

Existing Runtime lifecycle remains event-based and is adapted to the shared
event schema where necessary. A safe logging subscriber consumes events;
direct Runtime lifecycle logging must not become authoritative.

Events contain schema version, EventId, event type, timestamp, execution/plan
provenance, StrategyCode when known, PluginId/PluginVersion after resolution,
deterministic sequence where applicable, stable reason code, and safe message.
They contain no credentials, connection strings, handler instances, artifacts,
payloads, raw command/output, full exception stack, or secret.

State remains authoritative after publication failure. Exactly-once delivery
is not claimed. Durable events and external telemetry remain deferred.

## Determinism and Immutability

Equal request, descriptor, registry, and policy inputs produce equal logical
preparation, resolved policy, context values, artifact ordering, dispositions,
reason codes, and dispatcher event order. Time/EventId may differ only where
explicitly non-logical.

Use ordinal StrategyCode, PluginId, ArtifactId, and reason ordering. Do not use
registration order, dictionary enumeration, culture, reflection order,
database row order, or `GetHashCode` for identity/ordering. Dispatcher,
descriptor, policy, context, prepared dispatch, result, and artifacts expose no
public mutation. Runtime cannot mutate their values.

## Cancellation

Dispatcher accepts `CancellationToken`, checks it before resolution, after
preparation boundaries, before event publication/submission, and passes it
explicitly to Runtime. Cancellation before submission emits safe rejection or
cancellation lifecycle evidence according to the final contract, does not
invoke Runtime, creates no attempt, and propagates
`OperationCanceledException`.

Cancellation after Runtime submission follows existing Runtime ownership.
No retry or preparation continuation occurs after external cancellation.

## Logging, Events and Observability

Strongly typed events are authoritative lifecycle observability. The logging
subscriber logs allowlisted structured fields only and isolates logging
failure. Event publication warning may accompany a normalized result without
rewriting immutable plan/context/policy or mutable state.

Safe fields include execution/plan/run/step identities, StrategyCode,
PluginId/version, policy codes/versions, disposition, reason, schema versions,
sequence, and duration. Sensitive payload and raw exceptions are prohibited.
