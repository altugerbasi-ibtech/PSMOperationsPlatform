## Objective

Create a standalone SQL package that validates an already-deployed PSM
Operations Database and returns one overall `PASS` or `FAIL`, with detailed
diagnostics on failure.

## Architectural Boundaries

The package is release infrastructure only. It changes no runtime code,
production behavior, EF model, migration, snapshot, identity, permission,
database data, or schema. It performs no remediation and does not execute
deployment SQL.

## In Scope

- `Release/Database/SchemaValidation.sql`.
- `Release/Database/SchemaValidation.md`.
- Database existence and connected database-name validation.
- Compatibility level, recovery model, and collation validation.
- Migration-history table, exact migration set, and expected schema version.
- Required tables, indexes, foreign keys, primary keys, unique constraints,
  and default constraints.
- Deterministic overall result and detailed failure diagnostics.
- Offline static safety and completeness tests.

## Out of Scope

Database mutation, schema mutation, permission mutation, automatic migration,
deployment execution, data correctness, capacity, performance, runtime
permission validation, rollback execution, and production certification.

## Functional Requirements

1. SQLCMD variables provide the expected database name, compatibility level,
   collation, recovery model, and schema version.
2. Compatibility level `160` and the repository's latest migration are the
   repository-owned defaults.
3. Collation and recovery model must be provided from the approved deployment
   record and are not invented.
4. The script validates every requested category against explicit repository
   expectations.
5. The first result set contains exactly one `OverallResult` value: `PASS` or
   `FAIL`.
6. On `FAIL`, a second result set returns every detected issue as `Category`,
   `ObjectName`, `ExpectedValue`, `ActualValue`, and `Diagnostic`, ordered
   deterministically.
7. Independent safe checks continue so one defect does not hide other defects.

## Persistence and Migration Impact

None. No migration or database object is created, altered, or removed.

## Security and Read-Only Requirements

The script may read database/catalog metadata and
`dbo.__EFMigrationsHistory`. It contains no target-object DDL, target-data DML,
permission statement, dynamic SQL, transaction mutation, credential, or
connection string. Metadata visibility is required; insufficient visibility
may appear as missing schema and must not trigger automatic permission changes.

## Determinism and Observability

Expectations are immutable ordered literal sets derived from
`PSMOperationsDatabaseSchemaExpectation.json` and approved migrations.
Diagnostics use stable categories and ordinal object ordering. Output contains
no time, machine, user, credential, or target data.

## Test Requirements

Static Pester tests cover the result contract, configuration, exact migration
set, expected version, all required object sets, primary and unique key types,
default constraints, guide completeness, and prohibited mutation statements.
Tests require no SQL Server.

## Documentation Requirements

The guide must document prerequisites, SQLCMD/SSMS execution, required
variables, permissions, result interpretation, validated scope, limitations,
evidence handling, and the WP-007.Z execution boundary. Update package and
planning indexes.

## Acceptance Criteria

- Both standalone release files exist.
- Every requested validation category is present.
- One overall `PASS` or `FAIL` is returned.
- `FAIL` returns complete deterministic diagnostics.
- Static checks prove the script does not modify data, schema, or permissions.
- No runtime, EF model, migration, or production-code changes occur.

## Integration-Pending Items

Real SQL execution, actual configuration values, metadata visibility,
performance, evidence capture, permission validation, deployment approval, and
production certification remain under WP-007.Z or later approved packages.
