## Objective

Resolve only blocking findings B1 through B5 from Repository Readiness Review
v1.0 so the repository can be submitted to the repeated readiness gate without
adding product behavior or changing frozen architecture.

## Business and Product Value

The integration gate requires trustworthy governance, authentication evidence,
database expectations, and repository records. This package removes conditions
that could approve unreviewed work, accept NTLM as Kerberos, validate an old
schema, or rely on a missing accepted decision.

## Existing Repository Context

Architecture Freeze v1.0, Development Process Freeze v1.0, ADR-0001 through
ADR-0008, the historical ADR catalog, Engineering Standards, current contracts,
Runtime/SDK/decision documentation, WP-008.4 through WP-008.8 reviews, all EF
migrations, the model snapshot, readiness/deployment tools, Pester tests, and
the Repository Readiness Review v1.0 are authoritative inputs.

## Architectural Boundaries

This package adds no layer or product capability. Dispatcher resolves, Runtime
executes, plugins collect, Execution State remains current authority,
Monitoring remains non-durable observation, History remains the durable
terminal projection, and Audit remains separate. Windows and SQL Collector
identities remain separate. WP-007.Z remains deferred and not started.

## In Scope

- Record the user's explicit human approval of WP-008.4 through WP-008.8.
- Reconcile their three review records, specifications, and indexes.
- Make readiness WinRM authentication explicitly Kerberos-only.
- Remove active Negotiate instructions from the two named lab documents.
- Add static Kerberos downgrade-prevention tests.
- Define the complete current repository database expectation and validator.
- Repair and strengthen database validation tests.
- Reconcile WP-001 status using repository completion evidence.
- Restore the accepted historical ADR-005 from repository-supported evidence.
- Reconcile only readiness-significant Draft/status conflicts.
- Create WP-008.9 reviews and completion evidence.

## Out of Scope

WP-007.Z, live WinRM, SQL contact, deployment, migration application, service
or process control, target PowerShell, target file/registry/IIS changes, AD,
SPN, firewall or certificate changes, credentials, Audit, monitoring-history
persistence, event bus, broker, outbox, new migration, model change, commit,
push, and all new product capabilities are prohibited.

## Functional Requirements

1. Every WP-008.4 through WP-008.8 review must exist, support approval, record
   `Approved — Integration Pending`, and retain its limitations.
2. WP-008.5 through WP-008.8 specifications must become `Approved`; WP-008.4
   remains a historical package without a retroactive specification.
3. No approval identity is invented and no production evidence is claimed.
4. Readiness must invoke Kerberos explicitly, supply no credentials, preserve
   configured endpoint/port and approved HTTPS/HTTP transport policy, and have
   no Negotiate, Default, NTLM, Basic, CredSSP, TrustedHosts, or certificate
   bypass success path.
5. Kerberos results use safe categories: `KerberosSucceeded`,
   `KerberosAuthenticationFailed`, `EndpointUnavailable`,
   `SPNOrDelegationFailure`, `CertificateOrTransportFailure`,
   `InvalidConfiguration`, and `Unexpected`. SPN/delegation is used only when
   safely inferable.
6. Failure never becomes success through authentication downgrade. Approved
   HTTP transport fallback, when eligible, still uses Kerberos.
7. Lab documentation states that Negotiate is not proof of Kerberos, NTLM
   invalidates readiness, IncludePortInSPN is required, prerequisites include
   SPN/DNS/port/gMSA, and authentication failure never downgrades.
8. Database requirements are immutable repository-owned data with schema
   version, deterministic explicit migration IDs, latest migration, current
   schemas/tables, primary keys, foreign keys, unique constraints, critical
   indexes, and critical check constraints.
9. Static discovery must reject duplicates, order drift, missing, stale, or
   unexpected migrations relative to the expectation.
10. Live validation remains read-only and checks only implemented objects. It
    expects no monitoring-history or new Audit object.
11. WP-001 artifact/index status is consistently `Completed` without a
    production-validation claim.
12. `docs/adr/ADR-005-Turkiye-Local-Time-Standard.md` restores the accepted
    decision using only baseline, ADR-006, implementation, and test evidence.
13. Draft future-facing documents remain Draft unless repository evidence
    supports a readiness-significant status correction.

## Domain and Application Contracts

No Domain or Application product contract changes. PowerShell expectation and
result objects are ordered immutable-by-convention data returned as fresh
objects/arrays. Stable validation identifiers are deterministic and contain no
environment data or secrets.

## Persistence and Migration Impact

No entity, configuration, migration, migration ID, designer, or model snapshot
may change. No migration is added or applied. Database tooling validates the
existing model only. Any need for a model change stops this package.

## Failure Classification

WinRM uses the seven stable Kerberos categories above. Database manifest
failures distinguish missing, unexpected, duplicate, ordering, latest,
schema/table, key, foreign-key, unique, index, and check-constraint failures.
Failures expose safe identifiers only and never raw authentication, SQL,
credential, ticket, connection-string, or exception material.

## Security and Read-Only Requirements

Production and readiness WinRM use Kerberos explicitly with process identity.
IncludePortInSPN remains enabled in production and required by readiness
documentation. No explicit credential, downgrade, trust bypass, target
mutation, or raw security output is permitted. Database validation is
read-only, uses Windows Integrated Authentication, and never migrates.

## Determinism and Immutability

Migration and database expectation order is explicit and ordinal. Equal
repository state produces equal requirements, status checks, and reports.
Governance status edits are narrow and preserve findings. No culture,
filesystem enumeration, environment, live database, or target result defines
the approved manifest.

## Cancellation

No new asynchronous product behavior is introduced. Existing readiness
invocation remains bounded by its caller and preserves cancellation as a
non-success condition. Cancellation never triggers transport or authentication
downgrade.

## Logging, Events and Observability

No product event or metric changes. Readiness reports include only safe
category/evidence text. Raw Kerberos errors, SPN details, tickets, credentials,
connection strings, or database exception text are suppressed.
