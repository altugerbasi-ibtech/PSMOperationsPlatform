# WP-006.2 Controlled Single-Target Execution Runbook

## Purpose and authority

This runbook prepares one approved operator to validate the existing Windows
Collector happy path against exactly one non-production target. It never
authorizes itself and executes nothing automatically.

The authoritative design is
[`../tasks/WP-006-Windows-Collector-Production-Validation.md`](../tasks/WP-006-Windows-Collector-Production-Validation.md).
The package tools are narrow evidence collectors:

- `tools/validation/Invoke-WP0062Preflight.ps1`
- `tools/validation/Get-WP0062SqlEvidence.ps1`
- `tools/validation/Get-WP0062HostEvidence.ps1`
- `tools/validation/Test-WP0062Evidence.ps1`

Server 2019 can produce non-certifying behavior evidence only when its
readiness `WARNING`/exit code `1` is approved and recorded. Production
certification requires Server 2022 or later.

## Safety boundary

The Collector uses continuous `Worker` polling; there is no one-shot mode.
Modules commit independent ownership boundaries. The qualifying happy path
requires all seven modules to succeed. A failed boundary is explicit partial
target success and requires an approved recovery rerun.

The scripts do not start/stop services, change logging, alter targets, contact
WinRM or mutate SQL. Preflight is local-only. SQL evidence contacts only the
approved SQL database when the operator invokes it in the approved window.

## Required values

Complete the execution manifest from
`templates/WP-006.2-Execution-Manifest.template.json`. Do not infer any value.
Required inputs include Collector host/install/service/account, repository and
artifact identity, SQL server/database, target ID/FQDN, transport policy,
readiness path, evidence root, observation time, logging configuration,
migration, warning/fallback approvals, operator, approver, rollback owner and
change reference.

Configuration precedence is `appsettings.json`,
`appsettings.{Environment}.json`, Development-only User Secrets,
`PSM__`-prefixed environment variables, then command line. The required
environment key is `PSM__ConnectionStrings__OperationsDatabase`; record only
whether it exists, never its value.

Before this execution runbook may be used, WP-006.2A deployment must be
completed through the authoritative
`../deployment/WP-006.2A-Windows-Collector-Deployment-Runbook.md`. The
reviewer must approve its deployment report, installed artifact hash, service
metadata, configuration-presence evidence, Operations Database schema
validation report, and CollectorHost readiness result. Database validation
must be `READY`, or an explicitly approved non-blocking `WARNING`; `NOT_READY`
is a stop condition.
Deployment tooling being present in the repository is not deployment evidence.

The SQL evidence command is the only package tool that contacts SQL, and only
when explicitly invoked in the approved execution window.

## Target isolation

Objective proof of exactly one enabled and due target is mandatory. Preferred
options:

1. dedicated lab database containing one enabled/due `ManagedServer`;
2. existing approved configuration where only one target is enabled and due;
3. separately approved operator-managed data change with before/after evidence
   and rollback.

No tool in this package changes `ManagedServer`. Never edit production data.
The Baseline SQL evidence must show the approved ID/FQDN and
`EligibleTargetCount = 1`. Any other result stops execution.

## Logging profile

Current successful cycle/module events require Debug. Manual preparation only:

1. record the active configuration source and original file SHA-256;
2. copy the original file to an approved restricted backup location;
3. record approval for only `Logging:LogLevel:Default = Debug` and any narrower
   Collector category values;
4. ensure no connection string, credential or secret is added;
5. validate JSON syntax and record the changed hash;
6. restart only at the approved execution checkpoint;
7. after execution restore the exact original bytes and verify the original
   hash;
8. validate service state and record restoration evidence.

Do not use this runbook to automate configuration changes.

## Controlled procedure

### Checkpoint 1: approval and environment confirmation

Record the manifest, non-production attestations, maintenance window and named
owners. Confirm exactly one Collector instance is allowed.

### Checkpoint 2: preflight

Run the local preflight on the Collector host. Continue only for `READY`, or an
explicitly approved `WARNING`.

```powershell
.\tools\validation\Invoke-WP0062Preflight.ps1 <ALL-REQUIRED-PARAMETERS>
```

### Checkpoint 3: target isolation

Capture objective SQL proof of one approved enabled/due target. If isolation
requires data changes:

> **OPERATOR ACTION — APPROVAL REQUIRED:** An authorized database operator
> performs the separately approved lab-only change, captures before/after
> evidence and records rollback. This package never performs it.

### Checkpoint 4: SQL baseline

Invoke `Get-WP0062SqlEvidence.ps1 -Phase Baseline` with Integrated
Authentication. Review migration, target identity, eligibility, duplicates and
orphans. Any unexplained defect stops execution.

### Checkpoint 5: logging backup

Record original bytes/hash, approved Debug values, backup path and restoration
procedure. Verify restricted evidence storage.

### Checkpoint 6: service start

> **OPERATOR ACTION — APPROVAL REQUIRED:** Record approval immediately before
> starting the existing Windows Service through the supported SCM procedure.

This runbook does not supply a start command. Immediately capture the `Running`
host snapshot.

### Checkpoint 7: target cycle

Observe one cycle for the approved ID/FQDN. Correlate `PollingCycleId`,
`InventoryCorrelationId`, transport and these modules in order:

1. Computer
2. OperatingSystem
3. Memory
4. Processor
5. Disk
6. Volume
7. NetworkAdapter

All seven must succeed for the qualifying happy path. Record session ownership
evidence from existing tests and any safe external observation; do not claim a
real session count if it was not measured.

### Checkpoint 8: graceful stop

> **OPERATOR ACTION — APPROVAL REQUIRED:** Record approval immediately before
> requesting a graceful SCM stop.

Never kill the process. Capture shutdown logs and the `PostStop` host snapshot.

### Checkpoint 9: post-run evidence

Capture `PostRun` and `Verification` SQL evidence, logs, host/process snapshots,
correlation IDs and file hashes.

### Checkpoint 10: restore logging and state

> **OPERATOR ACTION — APPROVAL REQUIRED:** Restore original logging bytes and
> pre-execution service state. If operator-managed target isolation was used,
> its owner performs the approved rollback.

Verify original logging hash and record rollback-owner signoff.

### Checkpoint 11: offline evidence validation

Run `Test-WP0062Evidence.ps1` against the completed manifest. It must not contact
infrastructure. Review every warning; it cannot prove uncaptured facts.

### Checkpoint 12: reviewer decision

Complete the evidence index. Record `READY_FOR_REVIEW`, `WARNING` or
`NOT_READY`, deviations and reviewer rationale. Do not begin WP-006.3 or failure
injection before happy-path evidence review.

## Stop conditions

Stop and preserve evidence if target isolation is unproven; production scope is
detected; commit/hash is unexpected; database validation or readiness is
`NOT_READY`; a warning lacks
approval; service account/path differs; migration is missing; baseline has
unexplained duplicates/orphans; evidence storage or logging backup fails; a
secret appears; more than one target executes; FQDN/transport differs; the
Collector crashes; cleanup/restoration fails; or unexpected mutation occurs.

## Restoration and cleanup

- Gracefully stop only with approval.
- Restore exact original logging bytes and hash.
- Restore pre-execution service state with approval.
- Roll back operator-managed lab target isolation with before/after evidence.
- Hash all evidence and keep it in access-controlled storage.
- Remove only approved disposable working copies; never delete validation
  evidence.
- Escalate deviations and obtain rollback-owner signoff.

## Evidence completion

The manifest and evidence index must reference readiness, preflight, baseline,
Running/PostStop host snapshots, logs, post-run/verification SQL, restoration,
deviations and redaction review. Generated row IDs are not business identity;
compare singular target keys and collection `StableSourceKey` values.
