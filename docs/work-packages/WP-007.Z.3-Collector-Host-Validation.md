# WP-007.Z.3 Collector Host Validation and Operational Validation Toolkit

The shared result, reporting, sanitization, and deterministic-status contracts
are also reused by the final WP-007.Z.10 production-readiness evidence
aggregator. That aggregator observes existing reports and does not rerun live
infrastructure validation.

## Purpose

Provide a reusable, read-only PowerShell validation toolkit and an operator
entry point for Collector host prerequisites. It changes no host, service,
listener, firewall, SPN, identity, ACL, registry value, execution policy,
database, release artifact, or runtime application behaviour.

## Command

Run from the repository root using Windows PowerShell 5.1 or PowerShell 7:

```powershell
.\tools\validation\collector\Invoke-CollectorHostValidation.ps1 `
  -ConfigurationPath '<CONTROLLED>\DeploymentConfiguration.json' `
  -OutputPath '<APPROVED-EVIDENCE-DIRECTORY>' `
  -ComputerName '<COLLECTOR-HOST>' `
  -SkipRemoteChecks `
  -Verbose
```

`ComputerName` defaults to the local machine. The intended Collector-host
execution is local. An explicit non-local name is used only by the bounded
WSMan endpoint check; environment fact collection does not silently switch to
DCOM, Negotiate, NTLM, Basic, CredSSP, or TrustedHosts. The shared
configuration currently contains no Windows target list, so target-by-target
remote sessions are `NOT_APPLICABLE`. When later supplied by an approved
contract, WinRM must use `Authentication=Kerberos`, the configured port,
`IncludePortInSPN=true`, and TLS only when `Security.UseTLS=true`.

The output directory may be created. The toolkit writes only its three fixed
reports there. It does not run a separate write probe. A future approved probe
may create and immediately delete one unique file only inside an explicit test
directory.

## Configuration

The command consumes the WP-007.Z.2.A contract without introducing another
format:

- `Release/Deployment/DeploymentConfiguration.schema.json`
- `Release/Deployment/Test-DeploymentConfiguration.ps1`

Configuration validation runs before host checks. Invalid JSON or schema/
cross-field violations return exit code `3`. The report stores only the
configuration SHA256, never its contents.

## Exit Codes

| Code | Meaning |
|---:|---|
| 0 | `PASS` |
| 1 | `WARNING` |
| 2 | `FAIL` |
| 3 | `INVALID_CONFIGURATION` |
| 4 | `EXECUTION_ERROR` |

Independent check groups continue after failure. Any `FAIL` produces overall
`FAIL`; otherwise any `WARNING`, including a mandatory skipped check, produces
`WARNING`; otherwise the result is `PASS`. Optional `SKIPPED` and
`NOT_APPLICABLE` checks do not fail the run.

## Result Contract

Every result contains `CheckId`, `Category`, `Name`, `Description`, `Target`,
`Status`, `Severity`, start/completion timestamps, duration, expected/actual
values, message, recommendation, evidence, and sanitized exception type/
message. Status is one of `PASS`, `WARNING`, `FAIL`, `SKIPPED`, or
`NOT_APPLICABLE`; severity is one of `INFO`, `LOW`, `MEDIUM`, `HIGH`, or
`CRITICAL`. Duplicate identifiers and malformed results are execution errors.

Reports are:

- `CollectorHostValidationReport.json`
- `CollectorHostValidationReport.md`
- `CollectorHostValidation.log`

They include release version/commit, source and target, current identity,
configuration hash, duration, category/check outcomes, recommendations,
skipped reasons, and sanitized exceptions. Console output ends with
`COLLECTOR HOST VALIDATION: PASS`, `WARNING`, or `FAIL`.

## Implemented Categories

1. **Operating System** - repository-supported Windows Server policy, x64,
   boot time, pending reboot, uptime, name, domain membership, installation
   type/Core-versus-Desktop observation, locale, time zone, and configured
   drive measurements. Windows Server 2022+ passes; Server 2019 is the
   documented non-certifying warning.
2. **Hardware Capacity** - logical CPUs, total/available memory, and disk
   measurements. No invented minimum is enforced; no approved threshold exists.
3. **PowerShell** - Windows PowerShell 5.1, current edition/version, language
   mode, x64, script execution, built-in modules, and required cmdlets.
4. **.NET** - x64 and the repository-required .NET 10 runtime. The ASP.NET
   hosting bundle is not applicable to the Worker Service Collector.
5. **Windows Services** - WinRM, Windows Time, DNS Client, and an optional
   already-installed Collector service. No state change occurs.
6. **Active Directory and Kerberos** - domain, secure channel, DC discovery,
   Kerberos ticket, time status, gMSA format/local use, optional
   `Test-ADServiceAccount`, local-right evidence warning, and port-specific SPN
   expectation. Missing modules/privilege produce structured skipped warnings.
7. **WinRM** - listener/port/address, Kerberos, Basic, CredSSP,
   `AllowUnencrypted=false`, empty TrustedHosts, and Kerberos-only WSMan.
8. **Network and DNS** - configured SQL/Portal DNS, SQL TCP, source/reverse DNS,
   and bounded route/interface diagnostics. Unconfigured Portal/IIS/WinRM
   target ports are not scanned.
9. **SQL Connectivity** - encrypted Integrated Security metadata query,
   identity, database, version/edition, compatibility, collation, and recovery.
10. **File System** - configured log/output paths, local path format, existence,
    read access, and free space. Unconfigured install/config/work/temp paths are
    not invented. ACLs are never changed and service-account impersonation is
    not attempted.
11. **Logging and Diagnostics** - log/output paths, Application Event Log,
    optional event source, retention applicability, and capacity.
12. **Security Configuration** - Windows authentication, Kerberos-only,
    port-specific SPN, no secrets/SQL credentials/private-key fields, no Basic,
    CredSSP, or TrustedHosts dependency, and documented group applicability.
13. **Release Artifacts** - configuration/schema, release manifest/version/
    checksums/database package when present, verification package, and RAT.
    Validation never regenerates artifacts.

## Reusable Toolkit

`tools/validation/common` contains the result/configuration, sanitization,
DNS/TCP/service/registry/SQL, status, and report primitives.
`tools/validation/collector` contains Collector-specific checks and the entry
point. This deliberately remains smaller than a generic PowerShell application
framework and coexists with the older `tools/readiness` package.

## Safety and Limitations

- All environment queries are read-only; SQL uses Windows Integrated
  Authentication, encryption, certificate validation, and `SELECT` only.
- No live AD, SQL, WinRM, DNS, network, or Collector validation runs in
  repository tests.
- No Collector install/config/work/temp paths, IIS targets, Windows target
  list, Portal port, capacity threshold, or log-retention value exists in the
  approved configuration. Corresponding checks are informational, skipped, or
  not applicable.
- Effective `Log on as a service` and service-account filesystem access require
  separately approved evidence; credentials are never requested.
- Release payload files are generated/transported artifacts and may be absent
  in a source checkout; absence is reported without regeneration.
- No successful live validation may be claimed from offline tests.

## Evidence

Repository templates live under `artifacts/validation/WP-007.Z.3/`. A populated
configuration and raw environment output remain outside source control.
