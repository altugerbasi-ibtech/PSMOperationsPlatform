# WP-007.Z.6 Collector End-to-End Validation

## Purpose and boundary

The command composes the WP-007.Z.3 Collector host, WP-007.Z.4 IIS target,
and WP-007.Z.5 SQL target checks into one deterministic readiness assessment.
It validates prerequisites only. It never executes a Collector, performs
inventory, deploys a database, changes IIS or SQL, modifies services or SPNs,
or remediates a finding.

Repository tests use injected, mocked child operations. Their success is not
evidence that any live execution path is ready.

## Execution

Run from an approved Windows Collector host with the controlled shared
deployment configuration:

```powershell
.\tools\validation\collector\Invoke-CollectorEndToEndValidation.ps1 `
  -ConfigurationPath '<CONTROLLED>\DeploymentConfiguration.json' `
  -OutputPath '<APPROVED-EVIDENCE-DIRECTORY>' `
  -TargetCollector '<CONFIGURED-COLLECTOR>' `
  -Verbose
```

Omit `TargetCollector` to use the configured Collector server. Supplying
`SkipRemoteChecks` prevents IIS and SQL checks; because required evidence is
then absent, the decision is `COLLECTOR NOT READY`.

Configuration is schema-validated before any child operation. Targets come
only from the WP-007.Z.2.A shared contract.

## Validation flow and dependency graph

The orchestrator runs configuration checks, reuses host checks, reuses every
configured IIS and enabled SQL target check, builds the required connectivity
matrix, validates identity boundaries, aggregates WP-009 Operations database
evidence, and calculates readiness.

```text
Collector host -> IIS targets -> SQL targets -> Operations database
       |                |              |                 |
       +-------- shared structured prerequisite evidence-+
                                      |
                                 Portal configuration
```

The arrows describe required evidence, not lateral probes. Portal validation
is configuration/DNS-only because the shared contract defines no approved
Portal TCP endpoint.

## Identity and security model

Windows Collector, SQL Collector, and Portal service identities must remain
distinct. IIS checks retain the approved Kerberos-only WinRM architecture.
SQL checks retain current-identity Windows Authentication, encryption, and
read-only SQL requirements. The command does not accept credentials or bridge
one service identity into another.

A single interactive process cannot prove both Windows Collector and SQL
Collector identity contexts. Required SQL identity evidence must be produced
under the separately approved SQL Collector identity; incomplete or
inconsistent evidence blocks readiness.

## Readiness decision

The result is advisory and deterministic:

| Decision | Rule |
|---|---|
| `COLLECTOR READY` | All mandatory checks pass and no warnings exist. |
| `COLLECTOR READY WITH WARNINGS` | Mandatory checks pass and only non-blocking warnings exist. |
| `COLLECTOR NOT READY` | A check fails or mandatory evidence is skipped/missing. |

The decision does not authorize Collector execution. A separately approved
operational action remains required.

## Reports

The output directory receives:

- `CollectorEndToEndValidationReport.json`;
- `CollectorEndToEndValidationReport.md`; and
- `CollectorEndToEndValidation.log`.

Reports include duration, configuration hash, target/category/check summaries,
recommendations, skipped reasons, blocked execution reasons, and readiness.
The console ends with the exact readiness decision. Exit codes reuse the
toolkit convention: `0` pass, `1` warning, `2` fail, `3` invalid
configuration, and `4` execution error.

## Limitations and troubleshooting

- The tool validates readiness; it does not prove a successful inventory run.
- `SkipRemoteChecks` is diagnostic only and cannot yield readiness.
- Portal TCP readiness is not inferred without an approved configured port.
- Privilege-limited IIS, SQL, AD, or Operations database evidence remains a
  warning, skipped result, or blocker according to whether it is mandatory.
- Correct configuration findings in the controlled configuration and rerun.
- Correct host, IIS, SQL, Kerberos, TLS, permission, or schema findings only
  through the corresponding approved operational process.

Never weaken authentication, combine identities, add TrustedHosts, grant
broad SQL roles, modify SPNs, or change the environment from this validator.

## Evidence and status

`artifacts/validation/WP-007.Z.6/` contains sanitized templates only. Keep live
reports, endpoints, identities, topology, hashes associated with an environment,
and query output outside the repository in the controlled evidence location.

Repository implementation and live end-to-end validation are separate. Live
end-to-end validation status for repository implementation is `NOT EXECUTED`.
