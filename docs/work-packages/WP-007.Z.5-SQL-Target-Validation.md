# WP-007.Z.5 SQL Target Validation

## Purpose and safety boundary

The SQL target validator extends the WP-007.Z.3 operational validation toolkit
with current-identity, read-only SQL preflight. It does not execute the SQL
Collector, deploy a database, run migrations, read business data, change SQL
or Windows, grant permissions, modify SPNs, or remediate findings.

Repository tests mock every endpoint operation. Passing them does not mean a
live SQL target passed connectivity, Kerberos, TLS, metadata, schema,
permission, or compatibility validation.

## Configuration

Use the controlled shared `DeploymentConfiguration.json`. `SqlTargets` is the
only target source. Each entry has a stable `Name`, explicit server/instance/
static port, role, approved TLS settings, configured database list, permission
profile, and contact gate. SQL authentication, credentials, connection
strings, tokens, certificate bypass, endpoint discovery, and retry fields are
rejected.

Current repository policy requires:

- `Encrypt=true`;
- `TrustServerCertificate=false`;
- `SqlCollectorMetadataV1` for managed SQL targets; and
- `OperationsDatabaseValidationV1` for an Operations endpoint aligned exactly
  with the existing `SqlServer` section.

Validate configuration offline first:

```powershell
.\Release\Deployment\Test-DeploymentConfiguration.ps1 `
  -Path '<CONTROLLED>\DeploymentConfiguration.json'
```

## Execution

Run under the approved SQL Collector service identity from the approved source
host. Validate all enabled configured targets:

```powershell
.\tools\validation\sql\Invoke-SQLTargetValidation.ps1 `
  -ConfigurationPath '<CONTROLLED>\DeploymentConfiguration.json' `
  -OutputPath '<APPROVED-EVIDENCE-DIRECTORY>' `
  -Verbose
```

Validate one configured enabled target:

```powershell
.\tools\validation\sql\Invoke-SQLTargetValidation.ps1 `
  -ConfigurationPath '<CONTROLLED>\DeploymentConfiguration.json' `
  -ComputerName '<APPROVED-SOURCE-HOST>' `
  -TargetName '<CONFIGURED-TARGET-NAME>' `
  -OutputPath '<APPROVED-EVIDENCE-DIRECTORY>' `
  -Verbose
```

`ComputerName` is source evidence only. It does not change identity or contact
another host. `TargetName` cannot introduce an endpoint outside configuration.
Use `SkipDatabaseChecks` or `SkipPermissionChecks` only when approved; required
skipped evidence prevents an unqualified `PASS`.

## Connection and encryption model

The validator programmatically builds a `System.Data.SqlClient` connection:

- static configured server and TCP port;
- current-process Windows Integrated Security;
- encryption enabled and certificate trust validation retained;
- ten-second connection and bounded command timeouts;
- application name `PSM Operations SQL Target Validation`;
- read-only application intent; and
- no retry or protocol/authentication fallback.

Every reader, command, and connection is disposed deterministically. Actual
endpoint, login, `auth_scheme`, TCP transport, and encryption are checked after
connection. NTLM downgrade, unencrypted connection, wrong endpoint, or a
non-Windows identity fails required checks.

## Required target permissions

The validator never proves permission by writing. The managed-target profile
requires the least privilege needed for documented SQL Collector metadata,
including Windows login/connect and required server metadata/DMV visibility.
`VIEW SERVER STATE` is currently required; `VIEW SERVER PERFORMANCE STATE`,
`VIEW ANY DATABASE`, and `CONNECT ANY DATABASE` are reported independently as
optional or version-dependent unless current repository queries require them.
Configured database visibility/access may be needed for database-scoped
metadata. `sysadmin` is not required and is reported as a warning.

Operations database schema and runtime permission checks invoke the unchanged
WP-009.3 `SchemaValidation.sql` and WP-009.4 `PermissionValidation.sql`
artifacts. The managed-target metadata profile must not inherit Operations
database write permissions.

## Checks performed

The 17 categories cover target configuration; DNS/network; SQL connection;
server identity/version; service/protocol observations; Kerberos/SPN;
encryption/TLS; server configuration; configured database inventory;
Operations database compatibility; Collector metadata permissions;
performance metadata availability; files/capacity; backup/recovery
observability; availability features; bounded security posture; and aggregate
SQL Collector compatibility.

Queries are static, bounded, and safety-scanned. They use only read-only
metadata. No application tables, business records, SQL text, plans, live
performance inventory, cache/wait resets, backups, file changes, or general
security audit are included. Values without repository-approved expectations
remain informational.

## Reports and exit codes

The selected output directory receives only:

- `SQLTargetValidationReport.json`;
- `SQLTargetValidationReport.md`; and
- `SQLTargetValidation.log`.

Reports include aggregate, target, category, and check outcomes using the
shared contract and sanitized exception/evidence rules. Console output ends
with `SQL TARGET VALIDATION: PASS`, `WARNING`, or `FAIL`.

| Exit | Meaning |
|---:|---|
| 0 | `PASS` |
| 1 | `WARNING` |
| 2 | `FAIL` |
| 3 | `INVALID_CONFIGURATION` or invalid target selection |
| 4 | `EXECUTION_ERROR` |

## Interpretation and troubleshooting

- Configuration errors: correct the controlled file and validate offline.
- DNS/TCP failures: review only the configured endpoint, DNS, route, listener,
  and firewall through approved operations.
- Connection/TLS failures: review identity, SQL availability, certificate,
  hostname, encryption, and static port without trust bypass.
- Non-Kerberos authentication: review FQDN, time, service account, and expected
  `MSSQLSvc/<FQDN>:<Port>` with an authorized AD operator; never modify SPNs
  from this toolkit.
- Metadata/permission failures: grant only documented SQL Collector metadata
  rights through approved DBA/Security change; do not use `sysadmin` or
  `db_owner` shortcuts.
- Operations schema/permission failures: preserve WP-009 output and use the
  approved forward-fix/deployment process; never run EF migrations here.

Version/edition differences can make metadata or permission checks
`NOT_APPLICABLE`, `WARNING`, or unavailable. Missing optional service,
certificate, SPN-owner, backup, or topology evidence does not authorize broader
privilege.

## Evidence and live status

Use `artifacts/validation/WP-007.Z.5/` only as sanitized scaffolding. Store live
reports and operator/DBA/AD evidence externally. Do not commit server/instance,
IP, account, database, connection-string, query-output, SPN-owner, production
topology, or secret data.

Repository implementation and live SQL target validation are separate. Live
SQL target validation status is `NOT EXECUTED` for repository implementation.
