# WP-007.Z.2 Operations Database Deployment

## Purpose

Deploy the checksum-verified WP-009.1 Operations Database release package to
the approved SQL Server and retain auditable evidence. This work package does
not authorize Collector execution, destructive rollback, application-startup
migrations, or changes to runtime code.

## Binding Decisions

- The immutable `PSMOperations-v{Version}.sql`, `Manifest.json`, and
  `Checksums.sha256` payload produced by WP-009.1 is the only schema deployment
  input.
- An authorized deployment/DBA Windows identity executes the package. Runtime
  identities receive no DDL permission and never receive `db_owner`.
- Windows Collector and SQL Collector identities remain separate in accordance
  with ADR-003. Permissions against managed Windows and SQL targets are outside
  this database deployment.
- `Database.Migrate()`, startup migration, new EF migrations, real Collector
  execution, database deletion, and automatic rollback are prohibited.

## Required Approved Inputs

Keep actual infrastructure values in the controlled change record or operator
session, not this repository.

WP-007.Z.2.A defines
`Release/Deployment/DeploymentConfiguration.json` as the authoritative
environment-input file. Populate and validate one controlled copy, then reuse
it for every deployment and validation step below.

| Parameter | Required value or rule |
|---|---|
| `SqlServer` | Approved server and optional instance; do not place in committed evidence |
| `SqlPort` | Approved static TCP port |
| `DatabaseName` | Approved identifier; repository default is `PSMOperationsPlatform` |
| `DataFilePath`, `LogFilePath` | Existing SQL Server service-accessible paths |
| `InitialDataSizeMB`, `InitialLogSizeMB` | DBA capacity decision |
| `DataGrowthMB`, `LogGrowthMB` | Fixed-MB growth; percentage growth is not recommended |
| `CompatibilityLevel` | `160` |
| `RecoveryModel` | `FULL`, `SIMPLE`, or `BULK_LOGGED`, with matching backup plan |
| `Collation` | Exact DBA-approved collation; the repository does not prescribe one |
| `DatabaseOwner` | Approved low-use owner; not a runtime identity |
| `BackupLocation` | Approved protected location, retention, restore owner, RPO and RTO |
| `ReleaseDirectory` | Read-only copy of the three WP-009.1 payload files |
| Runtime principals | Distinct Collector, SQL Collector, and Portal Windows accounts |
| Deployment principal | Dedicated deployment/DBA Windows account |
| Change metadata | Change ID, operator, approvers, window, rollback decision owner |

## Operator Permissions

The deployment identity needs Windows authentication, server metadata access,
database creation/configuration rights when the database does not already
exist, and the DDL rights required by the reviewed migration package. It also
needs permission to create/map the approved Windows logins, grant the approved
database permissions, inspect metadata, impersonate the database users for
permission validation, and read migration history. Temporary elevation must be
approved, time bounded, recorded, removed, and revalidated.

Runtime identities receive the profiles defined by
`Release/Database/PermissionValidation.sql`. That validator is authoritative:

- Collector: database connect and read/write plus read/write on
  `configuration`, `collection`, `inventory`, `monitoring`, `operations`,
  `runtime`, and `history`; no execute or view-database-state.
- Portal: database connect/read plus read on the eight application schemas; no
  write, execute, or view-database-state.
- SQL Collector: database connect/read/write and view-database-state plus
  read/write on `collection`, `inventory`, and `monitoring`; no execute.

The DBA must implement the narrowest grants that make the validator pass.
Because database-scoped DML grants may be broader than the listed schema
profiles, Security must approve the final grant script before execution. Do
not use `db_datareader`, `db_datawriter`, `db_ddladmin`, or `db_owner` as a
shortcut.

## Pre-deployment Gate

Record the raw output under
`artifacts/validation/WP-007.Z.2/PreDeploymentResults/`. Redact only secrets or
confidential infrastructure values and note every redaction.

1. Verify the change approval and that Collector services remain stopped.
2. Parse `Manifest.json`; require the approved product version, Git commit,
   SQL filename, build date, and SHA256.
3. Verify every `Checksums.sha256` entry with `Get-FileHash -Algorithm SHA256`.
   Stop on a missing, extra, renamed, edited, or mismatched payload.
4. Record `SERVERPROPERTY` version, edition, instance name, service state,
   configured TCP port, server collation, and Windows-authentication result.
5. Test TCP connectivity to the approved host and port. Do not substitute a
   dynamically discovered port without change approval.
6. Connect with `sqlcmd -E -N` using the approved certificate policy. Record
   `encrypt_option`, `auth_scheme`, and certificate/hostname validation
   behaviour. Never use `-C` unless the exception is approved and recorded.
7. Record available data/log/backup volume space, default and selected file
   locations, initial sizes, fixed growth, database owner, recovery model,
   compatibility level, database collation, backup retention, RPO, and RTO.
8. If the database exists, run `ValidationQueries.sql` and
   `SchemaValidation.sql` and preserve the baseline. A failed baseline is not
   permission to repair or recreate it.
9. Confirm a usable backup or approved new-database recovery plan and named
   restore decision owner.

Example read-only connection query:

```powershell
sqlcmd -S '<APPROVED-SERVER>,<APPROVED-PORT>' -d master -E -I -N -b -V 16 `
  -Q "SELECT @@SERVERNAME, SERVERPROPERTY('InstanceName'), SERVERPROPERTY('ProductVersion'), SERVERPROPERTY('Edition'), SERVERPROPERTY('Collation'); SELECT encrypt_option, auth_scheme FROM sys.dm_exec_connections WHERE session_id=@@SPID;" `
  -o '<EVIDENCE>\PreDeploymentResults\SqlConnection.txt'
```

## Database Preparation

The EF release SQL does not own environment-specific database files,
collation, recovery, compatibility, owner, or backup policy. An authorized DBA
must review and execute an environment-specific `CREATE DATABASE` or `ALTER
DATABASE` script before the release payload. The script must:

- use `QUOTENAME` or validated identifiers and explicit SQLCMD parameters;
- specify approved data/log paths, initial sizes, and fixed-MB growth;
- set compatibility `160`, approved recovery model, collation at creation, and
  approved owner;
- stop if an existing database differs from the approved configuration; and
- never drop, detach, recreate, shrink, relocate, or overwrite an existing
  database automatically.

Store the approved environment script in the change record. Commit only a
sanitized copy if it contains no confidential infrastructure values.

## Deployment Sequence

All `sqlcmd` executions use Windows authentication, encrypted transport,
`-b -V 16`, and `-o` so original output is retained.

1. Record UTC/local start time, operator, change ID, package version, and Git
   commit.
2. Reverify the manifest and checksums in the execution directory.
3. Run the approved database-preparation script if required.
4. Execute `PSMOperations-v{Version}.sql` once against the approved database.
5. Record finish time, process exit code, and unmodified SQL output.
6. Create approved Windows logins (`CREATE LOGIN ... FROM WINDOWS`) and mapped
   users. Create no SQL-authenticated login and store no password.
7. Apply the Security-approved least-privilege grants matching the repository
   permission profiles.
8. Run `ValidationQueries.sql`.
9. Run `SchemaValidation.sql` with:

```text
ExpectedDatabaseName=<approved database>
ExpectedCompatibilityLevel=160
ExpectedCollation=<approved exact collation>
ExpectedRecoveryModel=<approved model>
ExpectedSchemaVersion=20260729191745_WP0088ExecutionHistory
```

10. Run `PermissionValidation.sql` with the three mapped database-user names.
11. Connect under each intended service identity and prove encrypted Windows
    authentication plus database connectivity. Do not start the services or
    execute a collection cycle.
12. Snapshot object inventory and `dbo.__EFMigrationsHistory`.
13. Execute the same immutable release SQL a second time and retain separate
    output. Repeat schema, permission, migration, and object-inventory checks.
14. Require no object or row-count drift attributable to the second schema
    execution, remove temporary elevation, and record UTC/local finish time.

Release execution example:

```powershell
sqlcmd -S '<APPROVED-SERVER>,<APPROVED-PORT>' -d '<APPROVED-DATABASE>' `
  -E -I -N -b -V 16 -i '<RELEASE>\PSMOperations-v<VERSION>.sql' `
  -o '<EVIDENCE>\Logs\Deployment-Run1.txt'
```

Validation examples:

```powershell
sqlcmd -S '<APPROVED-SERVER>,<APPROVED-PORT>' -d '<APPROVED-DATABASE>' `
  -E -I -N -b -V 16 -i '.\Release\Database\ValidationQueries.sql' `
  -o '<EVIDENCE>\PostDeploymentResults\ValidationQueries.txt'

sqlcmd -S '<APPROVED-SERVER>,<APPROVED-PORT>' -d '<APPROVED-DATABASE>' `
  -E -I -N -b -V 16 `
  -v ExpectedDatabaseName='<APPROVED-DATABASE>' ExpectedCompatibilityLevel='160' `
     ExpectedCollation='<APPROVED-COLLATION>' ExpectedRecoveryModel='<APPROVED-RECOVERY>' `
     ExpectedSchemaVersion='20260729191745_WP0088ExecutionHistory' `
  -i '.\Release\Database\SchemaValidation.sql' `
  -o '<EVIDENCE>\SchemaValidationResults\SchemaValidation.txt'

sqlcmd -S '<APPROVED-SERVER>,<APPROVED-PORT>' -d '<APPROVED-DATABASE>' `
  -E -I -N -b -V 16 `
  -v CollectorPrincipal='<COLLECTOR-DB-USER>' PortalPrincipal='<PORTAL-DB-USER>' `
     SqlCollectorPrincipal='<SQL-COLLECTOR-DB-USER>' `
  -i '.\Release\Database\PermissionValidation.sql' `
  -o '<EVIDENCE>\PermissionValidationResults\PermissionValidation.txt'
```

## Pass Criteria

Status is `COMPLETE` only when package integrity, both release executions,
schema validation, every runtime permission profile, migration history,
expected object inventory, per-identity encrypted connectivity, temporary
elevation removal, and evidence completeness all pass. Confirm by repository
search and architecture tests that runtime migration remains disabled.

Use `COMPLETE WITH WARNINGS` only for accepted, non-blocking observations.
Use `BLOCKED` for missing approvals, inputs, access, package, backup, or
connectivity. Use `FAILED` after an authorized execution or validation fails.

## Failure and Rollback

Stop at the failed stage; preserve the statement/batch identifier, timestamps,
exit code, and original output. Do not continue grants after a schema failure.
Do not drop/recreate the database, edit migration history, manually remove
objects, or automatically run down scripts. The approved choices are a
DBA-led restore of the verified backup or a separately reviewed forward fix.

Classify checksum, migration/model, generated SQL, or expected-object defects
as repository candidates. Classify DNS/TCP/TLS, storage, SQL configuration,
identity mapping, approval, backup, and environment-value mismatches as
environment candidates until evidence proves otherwise.

## Evidence and Completion Report

Use `artifacts/validation/WP-007.Z.2/DeploymentSummary.md` and its sibling
directories. Preserve raw pre/post results, two execution logs, schema and
permission output, service-identity connectivity results, manifest/checksum
copies, checksum-verification transcript, tests, timestamps, diff summary,
risks, and redaction notes.

The repository implementation can be validated without a production
connection by running the release Pester tests, database package tests,
solution build/tests, release bundle generation, checksum verification,
prohibited runtime-migration search, `git diff --check`, `git status -sb`, and
`git diff --stat`.
