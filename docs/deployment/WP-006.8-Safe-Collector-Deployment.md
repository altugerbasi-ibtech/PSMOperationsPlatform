# Minimal Safe Collector Deployment

## Supported flow

The package-first, local-first path is authoritative:

1. Create a validated package on a build machine.
2. Transfer it using an operator-approved mechanism.
3. Run the installer locally on the existing Collector server.
4. Review the deterministic result and deployment log.
5. If startup or health validation fails, the installer restores the sibling
   previous-version directory automatically.

Remote PowerShell deployment is unsupported. Fresh service creation and
WP-006.4 are outside this Work Package.

## Create the package

Run with Windows PowerShell 5.1 or later and the repository-required .NET SDK:

```powershell
.\scripts\deployment\New-CollectorDeploymentPackage.ps1 `
    -Configuration Release `
    -OutputDirectory C:\Temp\PSMPackages `
    -CreateZip
```

The builder runs `dotnet restore`, `dotnet build`, and `dotnet publish`, checks
required runtime files, rejects embedded connection strings and prohibited
content, and creates `deployment-manifest.json`. The manifest records PackageId,
UTC creation time, source commit and branch, dirty-worktree state,
configuration, target framework, every runtime file, its size and SHA256 hash,
and a package summary hash. A dirty worktree completes with warning exit code 1.

Packages exclude credentials, environment-variable values, connection strings,
user secrets, development settings, logs, dumps, diagnostics, previous
deployments, source, and `bin`/`obj` content outside publish output.

## Local dry run

Run in an elevated Windows PowerShell session:

```powershell
.\Install-CollectorPackage.ps1 `
    -PackagePath .\package `
    -ServiceName 'PSM Collector' `
    -WhatIf
```

Dry run parses and hashes the already expanded package, discovers the service
and installation directory, classifies configuration, and prints the deployment
plan. It does not create or expand directories, acquire a lock, stop or start a
service, move or delete files, clean retention directories, or roll back.
`-Force` changes confirmation behavior only and never bypasses validation.

## Local deployment

```powershell
.\Install-CollectorPackage.ps1 `
    -PackagePath .\package `
    -ServiceName 'PSM Collector'
```

`-PackagePath` accepts the extracted package root, its `package` child, or a ZIP
for a real deployment. ZIP expansion is intentionally unavailable in `-WhatIf`
because expansion would mutate the filesystem.

Local administrator rights are required. The default service name is
`PSM Collector`. An explicit name is authoritative. When it is absent, the
installer falls back to exact `PSMOperationsPlatform.WindowsCollector.exe`
matching in `Win32_Service.PathName`; zero or multiple matches fail. Quoted and
unquoted paths are supported. The service definition, PathName, identity, gMSA,
start mode, dependencies, and recovery settings are never changed.

## File ownership and replacement strategy

The active installation directory is treated as mixed ownership. A whole
directory swap is not used.

- Product-managed files are the runtime paths recorded by the current and new
  package manifests.
- Target-owned configuration uses the explicit allowlist below.
- Logs, dumps, diagnostics, certificates, operator-created files, and all other
  arbitrary content remain in the active directory.
- Unknown `appsettings`, logging, or service JSON variants fail as ambiguous
  rather than being overwritten.

Before service stop, the package is copied to a sibling staging directory on the
same volume and revalidated. After graceful stop, only product-managed files are
moved into the previous directory. New product-managed files are moved from
staging into the active installation directory and checked against package
SHA256 hashes. The deployed executable must exist.

Example paths, derived from the discovered installation directory:

```text
C:\PSM
C:\PSM_Staging_<DeploymentId>
C:\PSM_Previous_20260728T061751Z
C:\PSM_Failed_<DeploymentId>
```

No path is hard-coded.

## Preserved configuration

Environment variables are untouched. These local files are preserved:

- `appsettings.Production.json`
- `appsettings.Local.json`
- `appsettings.*.local.json`
- `logging*.local.json`
- `service*.local.json`

The package-owned `appsettings.json` is deployed only after the builder verifies
that it contains no embedded connection string. Development secrets never enter
the package.

## Stop, start, and health validation

If Running, the service receives one graceful stop request and is polled until
`StopTimeoutSeconds`; the installer never kills the process or reboots. If
already Stopped, deployment continues and the original state is recorded.
Failure to stop aborts before active replacement.

After replacement, success requires:

- Running state within `StartTimeoutSeconds`
- non-zero and stable ProcessId through `StabilitySeconds`
- unchanged service PathName
- active runtime hashes matching the package
- no new critical Collector startup errors in the local Application event log

Documented unrelated warnings do not fail health validation. Deployment does not
contact SQL Server, modify ManagedServer records, or invoke migrations.

## Previous versions and rollback

Previous versions are simple rollback directories; there is no backup manifest,
per-file backup hashing, generic backup engine, or archival lifecycle.

`KeepPreviousCount` defaults to 2 and cannot be less than 1. Retention runs only
after successful health validation, matches the strict
`<InstallName>_Previous_yyyyMMddTHHmmssZ` pattern, never deletes the current
rollback directory, and never touches arbitrary sibling directories. Cleanup
failure is a warning.

If replacement, start, or health fails, the installer:

1. gracefully stops the failed instance if needed;
2. moves failed product-managed files to the reported failed directory;
3. restores the previous product-managed files;
4. verifies the previous executable exists;
5. starts the unchanged service; and
6. checks basic Running/ProcessId stability.

If rollback fails, the active, failed, and previous paths remain in the result
for manual recovery. Do not recreate the service. Stop it if state is uncertain,
move the failed product files aside, move the retained previous files back to
the active directory, confirm the executable, then start and validate the
unchanged service.

## Locking and logs

A service-specific exclusive lock is created in the local temporary directory.
An active lock causes a concurrency failure. A lock older than
`StaleLockHours` (default 4) is renamed with a filesystem-safe UTC stale suffix.

Results use explicit phases and are written as JSON under:

```text
%ProgramData%\PSMOperationsPlatform\DeploymentLogs
```

Diagnostics contain phase, exception type and message, error identifier, script
and line details, invocation line, safe stack trace, and safe inner exception.
They do not deliberately read or log credentials, tokens, connection strings,
environment-variable values, or secrets.

## Exit codes

| Code | Meaning |
|---:|---|
| 0 | Success |
| 1 | Success with warning |
| 2 | Package validation failure |
| 3 | Service discovery failure |
| 4 | Configuration preservation failure |
| 5 | Staging failure |
| 6 | Service stop failure |
| 7 | Active deployment failure |
| 8 | Service start or health failure |
| 9 | Deployment failed, rollback succeeded |
| 10 | Deployment and rollback failed |
| 11 | Concurrency conflict |
| 12 | Invalid parameters |
| 13 | Unexpected failure |

The package builder retains its documented codes: 0 success, 1 warning,
2 validation, 3 build, 4 manifest, 5 archive, 6 invalid parameters, and
12 unexpected failure.

## Retired path and security boundaries

`Deploy-Collector.ps1` remains a non-operational retirement notice. There is one
local installer: `Install-CollectorPackage.ps1`.

The installer performs no remote PowerShell, credential collection, service
account change, gMSA change, AD or SPN operation, database access, schema
migration, or Windows/SQL security-boundary change.
