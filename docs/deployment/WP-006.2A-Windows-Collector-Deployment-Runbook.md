# WP-006.2A Windows Collector Deployment

> **Superseded by WP-006.8.** Do not execute the publish, install, update, or
> remote-orchestration commands in this historical runbook. The supported path
> is documented in
> [`WP-006.8-Safe-Collector-Deployment.md`](WP-006.8-Safe-Collector-Deployment.md).

## Status

The repository-supported deployment tooling is implemented and awaiting
review. No Collector Host has been changed and no live deployment has occurred.

## Purpose

This runbook governs a parameterized first installation, in-place upgrade,
validation, rollback, or conservative uninstall of
`PSMOperationsPlatform.WindowsCollector` on an approved Windows Collector
Host. It does not authorize any live action.

## Scope

- Publish the .NET 10 Windows Collector for `win-x64`.
- Configure the authoritative
  `PSM__ConnectionStrings__OperationsDatabase` environment variable.
- Grant the gMSA read and execute access to the installation directory.
- Create or update the `WindowsCollector` Windows Service through `sc.exe`.
- Validate the installed state and delegate environment validation to the
  existing Collector Readiness Framework.
- Validate the existing Operations Database schema and effective Collector
  permissions through read-only metadata queries before readiness or start.
- Preserve diagnostic reports and rollback material.

## Out of Scope

Inventory execution, database migrations, ManagedServer changes, target-wide
transactions, CollectorRun integration, Active Directory mutation, gMSA
creation, production logging redesign, and Enterprise Runtime Hardening are
excluded.

## Architecture Constraints

- .NET 10 and Windows Authentication are mandatory.
- SQL Authentication and raw connection strings in files or reports are
  prohibited.
- `ConnectionStrings:OperationsDatabase`, delivered with the `PSM__` prefix,
  is authoritative.
- Configuration is read at process startup; a service restart is required to
  inherit a changed Machine variable.
- The service identity is a pre-existing, locally usable gMSA.
- Deployment tooling validates the existing schema but never applies migrations.
- Windows Server 2022 or later is required for production certification.
  Server 2019 is usable only under an approved, non-certifying lab exception.
- The deployment package does not change independent module persistence
  boundaries or other Collector runtime behavior.

## Required Roles and Approvals

An approved deployment operator must have local administrative rights. The
change approver authorizes every service or filesystem mutation. The rollback
owner verifies backup and restoration evidence. An AD owner resolves gMSA
authorization failures separately; deployment scripts never modify AD.

## Prerequisites

- Approved Collector Host and change window.
- Repository commit and publish artifact hash approved for deployment.
- PowerShell 7 or Windows PowerShell 5.1, .NET 10 SDK for publishing, and the
  target .NET runtime for framework-dependent execution.
- ActiveDirectory PowerShell module, installed gMSA, and successful
  `Test-ADServiceAccount` on the Collector Host.
- Existing Windows Integrated Authentication connection value supplied as a
  `SecureString`, or already present at Machine scope.
- Authoritative `tools/readiness/Invoke-CollectorReadiness.ps1`.
- Writable, access-controlled deployment, backup, readiness, and evidence
  locations.

## Required Inputs

The operator must record the repository root, project path, package path,
Collector Host, installation path, executable and service names, gMSA,
SQL Server and database metadata, environment-variable scope, readiness
paths, backup root, expected hashes and commit, operator, approver, rollback
owner, and change reference. Do not infer missing environment values.

Approved secure configuration methods are:

1. Set the Machine variable in an approved interactive session by passing a
   `SecureString` to `Set-PSMWindowsCollectorConfiguration.ps1`.
2. Use a pre-existing Machine variable and omit the connection value from
   deployment commands.
3. Use an approved secret-delivery system to create a `SecureString` in
   process. The secret-delivery command and its output must not be logged.

The deployment manifest records only provider, scope, key, and presence.

## Publish Procedure

1. Review the repository commit and project path.
2. Run the publish command first with `-WhatIf`.
3. **OPERATOR ACTION — APPROVAL REQUIRED:** run
   `Publish-PSMWindowsCollector.ps1` without `-WhatIf`.
4. Review the generated manifest, SDK version, repository commit, and SHA-256
   hashes for the executable and primary DLL.
5. Approve the immutable package path and expected artifact hash.

Publishing invokes `dotnet publish` for the actual Windows Collector project,
defaults to Release, `win-x64`, `net10.0`, and framework-dependent output. It
does not modify source configuration or contact infrastructure.

## First Installation Procedure

1. Run the orchestrator in `Validate` mode and resolve blocking input errors.
2. Review `Install -WhatIf`; verify every reported target path. Database and
   readiness gates are reported as planned and are not contacted by WhatIf.
3. Confirm the package, commit, hash, gMSA, backup/evidence locations, and
   secure configuration source.
4. **OPERATOR ACTION — APPROVAL REQUIRED:** invoke `Install` without
   `-StartService`. The operation copies the approved package, applies the
   configuration, grants only `ReadAndExecute` to the gMSA on the installation
   directory, and creates a demand-start service.
5. Review infrastructure/service metadata validation while the service remains
   stopped.
6. Review `PSMOperationsDatabaseValidation.json` and `.md`. Continue only for
   `READY`, or an explicitly approved non-blocking `WARNING`.
7. Run and review CollectorHost readiness. Continue only for `READY`, or an
   explicitly approved `WARNING`.
8. Review the deployment and validation reports.
9. **OPERATOR ACTION — APPROVAL REQUIRED:** start the service only in the
   later approved execution window by explicitly supplying `-StartService`.
   The same invocation must request readiness; database and readiness gates
   complete before the start action.

Repeated installation is idempotent. An unexpected account correction requires
explicit `-Force`; otherwise deployment stops.

## Upgrade Procedure

For repeated updates of an already installed service, operators may use
[`scripts/deployment/Deploy-Collector.ps1`](../../scripts/deployment/Deploy-Collector.ps1)
under the [WP-006.8 Safe Collector Deployment guide](WP-006.8-Safe-Collector-Deployment.md).
That workflow discovers the current path and preserves the existing service
definition and gMSA identity. It does not support fresh installation and does
not replace the database-validation and readiness gates defined by this
runbook.

1. Validate the installed service and confirm its executable is under the
   approved installation path.
2. Review `Upgrade -WhatIf`.
3. Verify the timestamped backup destination does not exist.
4. **OPERATOR ACTION — APPROVAL REQUIRED:** invoke `Upgrade`.
5. If running, the service is stopped with a bounded wait, the current files
   are backed up, and the approved package is copied.
6. The previous running state is restored only when explicitly requested with
   `-StartService`; a previously stopped service remains stopped by default.
7. While the service remains stopped, review service metadata, database schema
   validation, then CollectorHost readiness.
8. Start or restore the previous running state only after both gates pass.
9. Review before/after hashes, service metadata, database validation,
   readiness, and rollback state.

Backups are never overwritten or automatically deleted.

## Validation Procedure

Run `Test-PSMWindowsCollectorDeployment.ps1` locally. It reads installation
files, SHA-256 hashes, service metadata, environment-variable presence, ACLs,
runtime metadata, readiness reports, and manifest consistency. It does not
start or stop a service, contact a target, or mutate SQL. A value mismatch is a
blocking result; configuration values remain redacted.

## Operations Database Validation Procedure

`Test-PSMOperationsDatabaseSchema.ps1` is the authoritative narrow schema
validator. It uses Windows Integrated Authentication and read-only `SELECT`
metadata queries. Its repository-owned expectation is
`tools/deployment/PSMOperationsDatabaseSchemaExpectation.json`. Static
validation requires the exact ordered migration set through
`20260729191745_WP0088ExecutionHistory` and rejects missing, duplicate, stale,
or unexpected migration identifiers before database access. Live validation
checks the current implemented configuration, collection, inventory,
capability, decision, execution-plan, runtime-state, monitoring, operations,
existing audit-log, and six-table Execution History persistence scope together
with critical keys, constraints, indexes, and effective collector permissions.
It does not expect a new Audit subsystem or monitoring-history persistence.

```powershell
.\tools\deployment\Test-PSMOperationsDatabaseSchema.ps1 `
  -OperationsDatabaseConnectionString $approvedSecureString `
  -SqlServer '<APPROVED-SQL-SERVER>' `
  -DatabaseName '<APPROVED-DATABASE>' `
  -RepositoryRoot '<REPOSITORY-ROOT>' `
  -ReportPath '<EVIDENCE-PATH>\PSMOperationsDatabaseValidation.json'
```

Results are `READY`/0, `WARNING`/1, or `NOT_READY`/2. A missing database,
migration history, required migration, schema, table, constraint, index, or
runtime permission is blocking. A permission result that cannot be proven
conclusively is a warning and requires explicit approval.

The required operator order is:

```text
Deploy -> Infrastructure validate -> Database validate
       -> CollectorHost readiness -> Optional service start
```

### When schema validation fails

1. Stop; do not start the Collector service.
2. Preserve the validation and deployment reports.
3. Generate or obtain the approved migration script.
4. Have an authorized DBA/deployment identity review and apply it under a
   separate change.
5. Rerun database validation.
6. Rerun CollectorHost readiness.
7. Start only after all blocking gates pass.

If a failed migration script may have partially modified the disposable
smoke-test database:

1. Inspect `dbo.__EFMigrationsHistory`; do not infer completion from existing
   tables or columns.
2. Prefer recreating the disposable smoke-test database through its separately
   approved procedure instead of attempting automated repair.
3. Have the authorized DBA review and apply the newly generated idempotent
   script.
4. Rerun `Test-PSMOperationsDatabaseSchema.ps1`.

Never use this recovery guidance to recreate or repair a production database.

The deployment package never runs migrations or repairs schema.

### Repository-supported migration script generation

Run EF tooling on a development or build machine where the full repository,
.NET SDK, and `dotnet-ef` are intentionally installed. Do not run migration
generation from the Collector host unless the repository and tooling are
intentionally present there.

Set `ConnectionStrings__OperationsDatabase` in the tooling process to an
approved Windows Integrated Authentication connection string. The design-time
factory rejects SQL Authentication and does not connect merely to build the
model or generate a script. Never place the value in command history, source,
reports, or the generated SQL.

```powershell
dotnet ef migrations list `
  --no-connect `
  --project .\src\PSMOperationsPlatform.Infrastructure\PSMOperationsPlatform.Infrastructure.csproj `
  --startup-project .\src\PSMOperationsPlatform.WindowsCollector\PSMOperationsPlatform.WindowsCollector.csproj `
  --context OperationsDbContext

dotnet ef migrations script `
  --idempotent `
  --project .\src\PSMOperationsPlatform.Infrastructure\PSMOperationsPlatform.Infrastructure.csproj `
  --startup-project .\src\PSMOperationsPlatform.WindowsCollector\PSMOperationsPlatform.WindowsCollector.csproj `
  --context OperationsDbContext `
  --output '<APPROVED-REVIEW-PATH>\OperationsDatabase-Migrations.sql'
```

`--no-connect` lists repository migrations without querying a database.
Generating the idempotent script neither connects to nor changes a database.
Confirm that it checks `dbo.__EFMigrationsHistory`, contains every repository
migration in order, and contains no connection string or credentials.

Generating a script is not authorization to execute it. An authorized DBA or
deployment identity must review and apply the approved SQL under a separate
change. Then rerun `Test-PSMOperationsDatabaseSchema.ps1`, rerun CollectorHost
readiness, and start the service only after both gates pass. Never use
`dotnet ef database update` in this procedure.

## Readiness Procedure

When `-RunReadiness` is explicitly supplied, deployment invokes the
authoritative script with `-Mode CollectorHost`, the actual installation path,
service name, expected account, and requested output directory.

- READY / exit 0: success.
- WARNING / exit 1: success only with `-AllowWarningReadiness`.
- NOT_READY / exit 2: failure.

The deployment package does not reproduce or reinterpret readiness checks.

## Rollback Procedure

Upgrade failure preserves the original error and attempts rollback only after
a valid backup has been captured. It restores backed-up files and previous
service configuration where safe. Rollback failure returns exit code 4 and is
never hidden.

**OPERATOR ACTION — APPROVAL REQUIRED:** if automatic rollback is incomplete,
stop further changes, preserve all evidence, and execute the rollback owner's
approved recovery plan.

## Uninstall Procedure

Review `Uninstall -WhatIf`. Without `-Force`, interactive confirmation is
required. The default stops a running service gracefully and removes only the
service definition. Files, logs/evidence, backups, environment configuration,
database objects, and the gMSA are preserved.

**OPERATOR ACTION — APPROVAL REQUIRED:** use `-RemoveFiles`,
`-RemoveConfiguration`, or `-RemoveBackups` only when each removal is approved.
`FullDeployment` never invokes uninstall.

## Evidence Collection

Retain the deployment manifest, reports, repository commit, artifact hashes,
publish manifest, service before/after metadata, ACL summaries, readiness
reports, backup path, rollback result, and operator approvals. Hash the final
evidence set and store it with restricted access. Never delete validation
evidence during cleanup.

## Stop Conditions

Stop for a non-approved host; unsupported certification OS; unexpected commit,
hash, account, service path, or target path; incomplete package; unusable gMSA;
SQL Authentication; unsafe configuration delivery; failed backup, ACL, service
stop, creation, update, validation, or restoration; NOT_READY readiness;
unapproved WARNING; rollback failure; or suspected secret disclosure.

## Security Considerations

The service receives no password for a gMSA. No script creates a gMSA,
installs it, changes group membership, queries a target, runs migrations, or
stores a connection string in reports. The gMSA receives inherited
`ReadAndExecute` on the installation directory only. Readiness output and
backup directories remain operator-controlled; no gMSA access is added because
the Collector does not write them. The repository defines no dedicated file
log sink, so this package creates no log directory or log ACL.

## Troubleshooting

- Missing AD module or failed `Test-ADServiceAccount`: stop and ask the AD
  owner to establish local gMSA usability outside this package.
- Service path/account mismatch: verify approval; account correction requires
  `-Force`.
- Environment configuration rejection: confirm Integrated Security and remove
  all SQL Authentication keys.
- Readiness WARNING: record the report and obtain explicit approval; the
  Server 2019 exception never provides production certification.
- Rollback failure: preserve the backup and reports, do not retry destructive
  steps, and escalate to the rollback owner.
- Database `NOT_READY`: keep the service stopped. Do not use `Force`. Have the
  authorized DBA apply the approved migrations, then rerun database validation
  and CollectorHost readiness.

## PSMLense Lab Example

The following values are examples only: Collector Host
`PSMLense.ae.local`, installation path `C:\PSM\WindowsCollector`, service
`PSMWindowsCollector`, account `AE\gmsaSPWorker$`, SQL Server
`mydb01.ae.local`, and database `PSMOperationsPlatform_SmokeTest`.

**OPERATOR ACTION — APPROVAL REQUIRED:** review only; do not execute until the
approved lab window. The first real command must retain `-WhatIf`.

```powershell
.\Invoke-PSMWindowsCollectorDeployment.ps1 `
    -Mode Install `
    -CollectorHost 'PSMLense.ae.local' `
    -CollectorInstallPath 'C:\PSM\WindowsCollector' `
    -CollectorServiceName 'PSMWindowsCollector' `
    -ServiceAccount 'AE\gmsaSPWorker$' `
    -SqlServer 'mydb01.ae.local' `
    -DatabaseName 'PSMOperationsPlatform_SmokeTest' `
    -PackagePath '<APPROVED-PUBLISH-PATH>' `
    -ReadinessScriptPath '<AUTHORITATIVE-READINESS-SCRIPT>' `
    -ReadinessOutputDirectory 'C:\PSM\ReadinessReports' `
    -DatabaseValidationReportPath '<APPROVED-EVIDENCE-PATH>\PSMOperationsDatabaseValidation.json' `
    -BackupRoot '<APPROVED-BACKUP-ROOT>' `
    -DeploymentManifestPath '<APPROVED-EVIDENCE-PATH>\deployment.json' `
    -Operator '<OPERATOR>' `
    -Approver '<APPROVER>' `
    -RollbackOwner '<ROLLBACK-OWNER>' `
    -ChangeReference '<CHANGE-REFERENCE>' `
    -RunReadiness `
    -StartService:$false `
    -WhatIf
```

Supply the connection value separately through an approved secure method. Do
not place it on a recorded command line.

## Exit Criteria

- The approved package, commit, and hashes match.
- The service exists once, points to the quoted approved executable, uses the
  expected gMSA, and was not started unless explicitly approved.
- The authoritative environment key is present at the approved scope and
  validates as Windows Integrated Authentication.
- Required files and least-privilege ACLs validate.
- Operations Database schema validation is `READY`, or a non-blocking warning
  is explicitly approved.
- Readiness is READY, or WARNING is explicitly approved for the lab exception.
- Deployment, rollback, and evidence reports contain no secrets.
- Live deployment remains pending until a separate operator approval.
