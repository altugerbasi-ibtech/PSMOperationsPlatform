# WP-007.3 Processor and Memory Inventory

Status: **IMPLEMENTED — INTEGRATION PENDING**

## Module contracts

Processor and physical Memory are independent plural current-state modules.
Each owns its CIM projection, normalization, key generation, validation, and
mapping contract. They share only the target-scoped WinRM session and core-run
context. No broad hardware DTO or cross-module raw-result dependency exists.

| Module | CIM source | Empty result |
|---|---|---|
| Processor | `Win32_Processor` | Invalid |
| Memory | `Win32_PhysicalMemory` | Valid only after a successful, parsed query returning zero rows |

Both use read-only `Get-CimInstance` with explicit properties and structured
output compatible with Windows PowerShell 5.1.

## Processor ownership and key

Persisted fields are `Id`, `ManagedServerId`, `InventoryRunId`,
`ProcessorKey`, `DeviceId`, `Name`, `Manufacturer`, `Description`,
`SocketDesignation`, `ProcessorId`, `CoreCount`, `LogicalProcessorCount`,
`MaxClockSpeedMhz`, `CurrentClockSpeedMhz`, `AddressWidth`, `DataWidth`,
`Architecture`, the three provider virtualization-capability flags,
`CapturedAt`, and `RowVersion`.

Key precedence is:

1. `DEVICE:<normalized DeviceId>`;
2. `SOCKET:<normalized SocketDesignation>`;
3. `PROCESSORID:<valid normalized ProcessorId>`;
4. `FALLBACK:<SHA-256-derived value>:<deterministic occurrence>`.

Display casing is preserved in fields while key inputs are normalized.
Placeholder Processor IDs include all-zero/all-FF values, `Unknown`,
`Default string`, `To Be Filled By O.E.M.`, and `Not Specified`.
Duplicate explicit keys fail validation; they are not merged.

Core and logical counts must be positive when supplied, and logical count
cannot be lower than core count. Clock values are non-negative. Address and
data widths are 32 or 64 when supplied. Virtualization capability flags are
parsed from CIM and never inferred from CPU name or manufacturer.

## Memory ownership and key

Memory remains one row per physical module. No aggregate or `legacy-total`
row is produced by collection. Persisted fields remain the approved plural
contract documented in the engineering handbook.

Key precedence is normalized Device Locator, Bank Label, valid Serial Number,
then a SHA-256-derived deterministic fallback with occurrence index. The
explicit placeholder set includes all-zero/all-FF serials, `Unknown`,
`Default string`, `To Be Filled By O.E.M.`, `System Serial Number`,
`Not Specified`, and `None`. Short or numeric serials are not rejected merely
for their shape.

Capacity must be positive. Speed values are non-negative when present.
Optional manufacturer, part, serial, speed, form-factor, and memory-type
values remain null rather than being invented. Any invalid row fails the
complete collection.

## Persistence, idempotency, and traceability

All Processor and Memory collection and validation completes before the core
database transaction begins. Successful collection replaces both current
collections inside the all-core transaction. Valid-empty Memory clears its
previous collection; invalid-empty Processor preserves all previous current
state because persistence never begins.

Every inserted row receives the complete run's shared `InventoryRunId` and
capture timestamp. `InventoryVersion` increments once after successful commit.
Rollback publishes neither new rows nor a new run ID. Sorting and fallback
keys are stable across input-order changes; repeated runs create no duplicate
or unbounded rows.

Safe module logs include target, run, raw and normalized counts, validation,
empty-result status, duration, failure category, and atomic persistence
status. Raw CIM output and Processor ID are not logged.

## Architecture Review

The implementation preserves module independence, the shared Kerberos session,
collect-before-transaction ordering, EF Core persistence boundary, current
state only, and read-only target behavior. No new architecture abstraction was
introduced.

## Implementation Review

The production atomic orchestrator calls the same independent normalizers used
by deterministic module tests. Entity validation and EF configuration mirror
the normalized contracts. Processor ID is persisted for operational identity
but excluded from logging.
