# WP-002 — Core Persistence Layer

## Status

Approved for implementation.

## Objective

Establish the first durable SQL Server persistence model for PSM Operations Platform and provide the EF Core 10 infrastructure required by later Web and collector Work Packages.

This Work Package SHALL implement only the persistence foundation. It SHALL NOT implement collector behavior, Blazor management screens, remote discovery, command leasing workers or privileged infrastructure actions.

## Business value

The platform requires one controlled and durable source of truth for managed servers, collector registration, collector health, collection runs, inventory snapshots, queued operations and audit records.

Completing this Work Package provides a stable database baseline on which later inventory, monitoring and operations features can be built without duplicating persistence concerns in individual host projects.

## Context

The approved architecture uses:

- .NET 10
- EF Core 10
- SQL Server 2022 or later
- Windows Authentication
- gMSA process identities
- one central SQL Server database
- controlled deployment migrations

The architecture baseline originally described WP-002 as the configuration and infrastructure foundation. This Work Package refines that implementation boundary to the core persistence layer agreed for the first database increment.

The durable command queue is included here only as a database contract. Leasing, retries, execution workers, dead-letter processing and command-specific behavior remain subject to later dedicated Work Packages.

## In scope

WP-002 SHALL include:

- Core domain entities required by the first persistence model.
- EF Core `DbContext` implementation in `PSMOperationsPlatform.Infrastructure`.
- Entity type configurations.
- SQL Server schema mapping.
- Design-time DbContext factory for migration tooling.
- Initial migration named `InitialCreate`.
- Controlled database creation and migration instructions.
- Persistence tests for mappings, constraints and basic read/write behavior.
- Documentation of the initial entity-relationship model.

The following entities are included:

- `ManagedServer`
- `CollectorNode`
- `CollectorHeartbeat`
- `CollectorRun`
- `InventorySnapshot`
- `CommandQueueItem`
- `AuditLog`

## Out of scope

WP-002 MUST NOT include:

- Windows, IIS or SQL discovery logic.
- WinRM communication.
- SQL DMV collection.
- Windows Service inventory.
- Event Log collection.
- Certificate collection.
- Performance Counter collection.
- Blazor CRUD pages.
- Command leasing implementation.
- Command retry workers.
- Dead-letter processing.
- SignalR notifications.
- Alerting or notification delivery.
- Privileged infrastructure actions.
- Windows Action Executor implementation.
- Runtime plugin loading.
- SQL authentication or stored credentials.
- Automatic migration during application startup.

## Required design

### Database schemas

| Schema | Responsibility |
|---|---|
| `configuration` | Managed targets and platform configuration |
| `collection` | Collector registration and collection execution |
| `monitoring` | Collector health and heartbeat history |
| `inventory` | Durable inventory snapshot metadata and payload |
| `operations` | Durable command queue contract |
| `audit` | Security and operational audit trail |

### Entity identifiers

- Primary keys SHALL use `uniqueidentifier` values generated by the application.
- Entity identifiers SHALL be immutable after creation.
- Foreign keys SHALL use the same identifier type as their parent entity.

### Time handling

- Date and time columns SHALL use `datetime2(3)` unless a later accepted ADR requires a different precision.
- Application code SHALL use the accepted Türkiye local-time standard consistently.
- Date and time values SHALL not be silently converted between local time and UTC inside entity mappings.
- Time values SHALL be created through one application time abstraction rather than direct scattered calls to `DateTime.Now`.

### Common persistence rules

- EF Core lazy loading MUST NOT be enabled.
- Automatic migration during Web or collector startup MUST NOT be implemented.
- Migrations SHALL be produced and applied as controlled deployment artifacts.
- Connection strings MUST NOT contain usernames or passwords.
- Sensitive connection-string values MUST NOT be written to logs.
- Entities SHALL not expose EF Core-specific types or attributes from the Domain project.
- Fluent API configurations SHALL be used for table names, schemas, constraints and indexes.
- Cascade delete SHALL be avoided unless explicitly stated in this Work Package.
- Parent records referenced by historical records SHALL use restrictive delete behavior.

### Concurrency

- Mutable coordination entities SHALL contain a SQL Server `rowversion` concurrency token.
- In this Work Package, `CollectorNode` and `CommandQueueItem` SHALL use `rowversion`.
- Concurrency failures SHALL surface as explicit persistence errors and SHALL NOT be silently overwritten.

## Contracts and data model

The authoritative ER model is documented in:

`docs/database/WP-002-Core-Persistence-ER-Model.md`

### ManagedServer

Represents a Windows server known to the platform. It is intentionally general and is not limited to IIS or SQL roles.

| Property | SQL type | Required | Notes |
|---|---|---:|---|
| `Id` | `uniqueidentifier` | Yes | Primary key |
| `Fqdn` | `nvarchar(255)` | Yes | Canonical server identity |
| `DisplayName` | `nvarchar(255)` | No | Operator-friendly name |
| `Environment` | `nvarchar(50)` | No | Development, Test, Production |
| `IsEnabled` | `bit` | Yes | Controls future collection eligibility |
| `CreatedAt` | `datetime2(3)` | Yes | Türkiye local time |
| `UpdatedAt` | `datetime2(3)` | Yes | Türkiye local time |

Rules:

- `Fqdn` SHALL be normalized before persistence.
- `Fqdn` SHALL have a unique index.
- Deleting a server that has historical runs, snapshots or queued commands SHALL be restricted.

### CollectorNode

Represents one installed collector service instance.

| Property | SQL type | Required | Notes |
|---|---|---:|---|
| `Id` | `uniqueidentifier` | Yes | Primary key |
| `Name` | `nvarchar(200)` | Yes | Stable registration name |
| `CollectorType` | `nvarchar(50)` | Yes | Initially Windows or Sql |
| `HostFqdn` | `nvarchar(255)` | Yes | Collector host |
| `InstanceKey` | `nvarchar(100)` | Yes | Distinguishes instances |
| `Version` | `nvarchar(50)` | No | Application version |
| `IsEnabled` | `bit` | Yes | Administrative enablement |
| `RegisteredAt` | `datetime2(3)` | Yes | Registration time |
| `UpdatedAt` | `datetime2(3)` | Yes | Last metadata update |
| `RowVersion` | `rowversion` | Yes | Optimistic concurrency |

Rules:

- `(HostFqdn, CollectorType, InstanceKey)` SHALL be unique.
- Collector type SHALL be a Domain enum stored as a readable string.
- Registration SHALL not contain credentials.

### CollectorHeartbeat

Stores append-only collector health observations.

| Property | SQL type | Required | Notes |
|---|---|---:|---|
| `Id` | `uniqueidentifier` | Yes | Primary key |
| `CollectorNodeId` | `uniqueidentifier` | Yes | Parent collector |
| `ObservedAt` | `datetime2(3)` | Yes | Heartbeat timestamp |
| `Status` | `nvarchar(30)` | Yes | Healthy, Degraded, Unhealthy |
| `Message` | `nvarchar(1000)` | No | Sanitized detail |
| `ProcessId` | `int` | No | Collector process ID |
| `WorkingSetBytes` | `bigint` | No | Optional process metric |

Rules:

- Heartbeats SHALL be append-only.
- A composite index SHALL exist on `(CollectorNodeId, ObservedAt DESC)`.
- Retention is not implemented in WP-002.

### CollectorRun

Represents one bounded collection execution against one managed server.

| Property | SQL type | Required | Notes |
|---|---|---:|---|
| `Id` | `uniqueidentifier` | Yes | Primary key and correlation identifier |
| `CollectorNodeId` | `uniqueidentifier` | Yes | Executing collector |
| `ManagedServerId` | `uniqueidentifier` | Yes | Collection target |
| `CollectionType` | `nvarchar(50)` | Yes | Windows, IIS, SQL |
| `Status` | `nvarchar(30)` | Yes | Pending, Running, Succeeded, Failed, Cancelled |
| `StartedAt` | `datetime2(3)` | No | Execution start |
| `CompletedAt` | `datetime2(3)` | No | Terminal completion |
| `ErrorCode` | `nvarchar(100)` | No | Stable error identifier |
| `ErrorMessage` | `nvarchar(2000)` | No | Sanitized detail |
| `CreatedAt` | `datetime2(3)` | Yes | Record creation |

Rules:

- A run SHALL reference exactly one collector and one managed server.
- `CompletedAt` SHALL be null until a terminal state.
- Error text SHALL not contain credentials or connection strings.

### InventorySnapshot

Stores one durable inventory result associated with a collector run.

| Property | SQL type | Required | Notes |
|---|---|---:|---|
| `Id` | `uniqueidentifier` | Yes | Primary key |
| `CollectorRunId` | `uniqueidentifier` | Yes | Parent run |
| `ManagedServerId` | `uniqueidentifier` | Yes | Denormalized target reference |
| `SnapshotType` | `nvarchar(100)` | Yes | Versioned contract name |
| `SchemaVersion` | `int` | Yes | Payload schema version |
| `CapturedAt` | `datetime2(3)` | Yes | Capture time |
| `PayloadJson` | `nvarchar(max)` | Yes | Serialized payload |
| `PayloadHash` | `char(64)` | No | Optional SHA-256 digest |

Rules:

- `PayloadJson` SHALL contain valid JSON.
- A SQL check constraint SHALL use `ISJSON`.
- Payload contracts SHALL be explicitly versioned.
- Generic JSON SHALL not become the permanent query model for all future inventory.
- Duplicate `(CollectorRunId, SnapshotType, SchemaVersion)` records MUST be rejected.

### CommandQueueItem

Defines the first durable command queue table contract. Worker leasing remains out of scope.

| Property | SQL type | Required | Notes |
|---|---|---:|---|
| `Id` | `uniqueidentifier` | Yes | Primary key |
| `CommandType` | `nvarchar(100)` | Yes | Versioned command name |
| `TargetCollectorType` | `nvarchar(50)` | Yes | Intended collector family |
| `ManagedServerId` | `uniqueidentifier` | No | Optional target |
| `PayloadJson` | `nvarchar(max)` | Yes | Versioned payload |
| `Status` | `nvarchar(30)` | Yes | Pending, Completed, Failed, Cancelled |
| `Priority` | `int` | Yes | Lower value is higher priority |
| `NotBefore` | `datetime2(3)` | No | Earliest eligible time |
| `CreatedAt` | `datetime2(3)` | Yes | Submission time |
| `CreatedBy` | `nvarchar(256)` | Yes | Windows identity |
| `CompletedAt` | `datetime2(3)` | No | Terminal completion |
| `FailureCode` | `nvarchar(100)` | No | Stable failure identifier |
| `FailureMessage` | `nvarchar(2000)` | No | Sanitized detail |
| `RowVersion` | `rowversion` | Yes | Optimistic concurrency |

Rules:

- `PayloadJson` SHALL contain valid JSON.
- WP-002 SHALL not implement leasing, retries or dead-letter behavior.
- `CreatedBy` SHALL use an authenticated Windows or trusted service identity.

### AuditLog

Stores immutable security and operational audit events.

| Property | SQL type | Required | Notes |
|---|---|---:|---|
| `Id` | `uniqueidentifier` | Yes | Primary key |
| `OccurredAt` | `datetime2(3)` | Yes | Event time |
| `Actor` | `nvarchar(256)` | Yes | Windows or service identity |
| `Action` | `nvarchar(150)` | Yes | Stable action name |
| `EntityType` | `nvarchar(100)` | No | Affected entity type |
| `EntityId` | `uniqueidentifier` | No | Affected entity identifier |
| `CorrelationId` | `uniqueidentifier` | No | Cross-component correlation |
| `Outcome` | `nvarchar(30)` | Yes | Succeeded, Failed, Denied |
| `DetailJson` | `nvarchar(max)` | No | Sanitized structured detail |

Rules:

- Audit records SHALL be append-only.
- Audit detail MUST NOT contain credentials or connection strings.
- When present, `DetailJson` SHALL be valid JSON.

## Security requirements

- SQL connectivity SHALL use Windows Integrated Authentication.
- The platform MUST NOT persist usernames, passwords, certificates, private keys or reusable authentication material.
- Database permissions SHALL follow least privilege.
- The migration identity MAY have DDL permissions that runtime identities do not have.
- Runtime identities SHOULD receive only required schema permissions.
- JSON payloads and error fields SHALL be sanitized before persistence.
- SQL connection strings MUST NOT be included in operator-facing exceptions.

## Error handling

- Persistence operations SHALL expose stable platform error codes.
- Connectivity, timeout and database-unavailable failures SHALL use
  `persistence.unavailable` when they can be classified safely.
- This mapping applies to `SaveChanges` and `SaveChangesAsync`. Constructing
  `OperationsDbContext` does not open a database connection; direct
  `Database.OpenConnection*` calls are outside the WP-002 persistence save
  abstraction and require caller-owned handling if introduced by a later Work
  Package.
- Unique-constraint violations SHALL become deterministic conflict results.
- Concurrency conflicts SHALL be explicit.
- Invalid JSON payloads SHALL be rejected.
- Foreign-key violations SHALL not be hidden.
- Migration failures SHALL stop deployment.

## Logging and observability

The implementation SHALL log:

- DbContext creation failures.
- SQL connectivity failures without secrets.
- Migration start, completion and failure.
- Concurrency conflicts.
- Constraint violations with stable event identifiers.

Runtime persistence logging uses stable event identifiers 2100 through 2107 for
context creation, save start/success, concurrency, constraint, unavailable,
append-only and unexpected-failure events. Log messages contain operation type,
stable error code, exception type and counts only. They do not include connection
strings, SQL text, JSON payloads or credentials.

Migration start, completion and failure logging is owned by the controlled
deployment pipeline or operator tooling because migrations do not run in
application startup.

The implementation MUST NOT log:

- Credentials.
- Full connection strings.
- Raw sensitive payloads.
- SQL authentication fallback attempts.

## Acceptance criteria

1. Domain contains the approved entities and enums without EF Core dependencies.
2. Infrastructure contains the EF Core 10 DbContext and fluent configurations.
3. All seven entities map to approved schemas.
4. Required keys, foreign keys, constraints and indexes are present.
5. `rowversion` is configured for `CollectorNode` and `CommandQueueItem`.
6. `InitialCreate` migration is generated successfully.
7. The migration creates an empty database from zero. Controlled manual SQL
   Server evidence is recorded in
   [`../verification/WP-002-SQL-Server-Validation.md`](../verification/WP-002-SQL-Server-Validation.md).
8. Migration is applied explicitly and not at application startup.
9. Build succeeds without new warnings.
10. Required persistence tests pass. Provider-specific controlled validation is
    recorded in
    [`../verification/WP-002-SQL-Server-Validation.md`](../verification/WP-002-SQL-Server-Validation.md).
11. No collector logic, Web CRUD UI or command worker is introduced.
12. No credential storage or SQL authentication is introduced.

## Required tests

Tests SHALL verify:

- Model creation.
- Expected table and schema mapping.
- Required properties.
- Unique `ManagedServer.Fqdn`.
- Unique collector registration key.
- Foreign-key enforcement.
- Restrictive historical deletion.
- SQL Server JSON check constraints.
- Duplicate snapshot rejection.
- `rowversion` concurrency.
- Basic create, read and update.
- Audit append and query.
- Migration application against SQL Server.

Provider-specific behavior SHALL be tested against SQL Server and MUST NOT be considered proven by EF Core InMemory.

Domain constructors reject undefined enum values before persistence. EF Core
continues to store approved enum members as readable strings.

The generic repository intentionally does not expose an unbounded `ListAsync`.
High-volume reads for `CollectorHeartbeat`, `AuditLog` and `InventorySnapshot`
require query-specific paginated APIs in the Work Package that introduces those
read use cases. WP-002 does not define that future API.
